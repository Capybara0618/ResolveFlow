### 实际缺陷与对应模块

1. **来源领域选择不足**：共享隐私、默认接收人、接续原核查单，被理解成OTHER/needs=[]或错误POLICY。D07/2–3已发布错误私密建议，D08/2和D14/2因读错知识领域后缺政策引用被拒绝。指南本来可读；这不是政策没召回，而是该用GUIDE时没选对。`Orchestration.required`只对APPLICATION/HANDOFF兜GUIDE，当前OTHER仍依赖模型needs。
2. **页面解释与操作合同未对齐**：D03/1、D08/1、D10/2已读资料且候选含有正确解释，但非APPLICATION/HANDOFF焦点没有程序next_steps，正文页面标签又触发旧校验，最终不发布。`compose`按intent装步骤，`render_navigation`按正文标签要求步骤，两端语义不一致。
3. **最后呈现丢解释**：`render_navigation.guide_only`按引用仅GUIDE判断整段为纯步骤，替换全文。D06/2流式候选里正确回答“目前没有已提交核查记录”，最后结果却只剩通用流程。共9个成功轮次有至少一段投影被最终程序替换，其中7轮无任何完整模型正文段保留；这会造成流式与最终内容跳变。
4. **上下文被提供不等于被采用**：D09/1没有读取长历史原文，待共享摘要遗漏尾部关键纠正；D04/2旧照片陈述未随假设澄清处理。相对地，D13实际完成PAUSE→OPEN/旧猜测SUPERSEDED→RESOLVED，说明已有生命周期和原文锚点机制能工作，但覆盖仍不足。
5. **理解协议和政策条件的完整性**：D10/3两次APPLICATION＋MERCHANT_REVIEW组合冲突；D11/2用CLARIFY表达澄清，但该事件实际只允许新状态NEEDS_CUSTOMER，修正反馈未使模型改用合法事件。D11/1、3实际取到了完整未发货条款，仍漏版本1及ORDER_PAID，属于回答省略，不是检索缺失。
6. **明确人工诉求未闭合成可确认产物**：D13/3恢复调查但只建议联系承运商，没有商家核查下一步；D14/3仍LOGISTICS/EXPLAIN，仅正文写摘要，没有结构化确认共享能力。

下一轮优先修前3项共同合同：让流程知识选择及可信接收对象稳定；区分解释性页面引用和实际操作；保留对用户问题的直接解释，避免按引用类型删全文。然后补上下文纠正采纳、关键政策前提及明确人工摘要的完成检查。先用本批保存响应离线复现及针对性测试，之后如需真实确认应另立输入/版本；不改本批分数或自动付费重跑。现有证据不支持把问题归咎于RAG检索慢，或通过新增多Agent解决。

“稳定正文”必须是最后未reset的投影段，且**整段文本实际包含在最终答案**；多段分别匹配，不能要求插入程序事实后仍整段拼接相同。30轮从原ProgressReporter的本地HTTP接收时刻计，7轮纯模型正文均被程序替换，只能用最终结果返回时刻；7个无正式回答的失败轮不伪造首正文，仍在44轮完成分母。原始`stream_times.first_retained_ms`只表示最后attempt首delta，不等于最终有效正文；本批正式指标用后处理的`projection`，原记录不改。

上述是服务端实测，含原持久化和本地计量开销，不含Java/SSE代理、浏览器DOM和公网客户端。只衡量本机、同一串行批次，不能称生产p95；语义不正确但正式发布的回答仍保留在37轮延迟分布，不能借过滤失败夸大质量。最长整轮8.07s；当前等待主要在多个串行模型请求，政策工具并不是秒级等待来源。9轮最终文本替换需优先处理，不能仅以首次候选流畅宣称体验完成。
