## 暴露的根因

**答复状态与事项生命周期混在一起。** U05首轮仍需要客户排查，却标ANSWERED；DialogueState初始化过滤ANSWERED，下一轮before为空。用户要求暂停、恢复、找到包裹撤回时，模型仍引用原t1，但状态机认为没有可操作旧任务。保存的PAUSE/CANCEL可离线复现相同拒绝；第三轮即使修好原句，还存在CORRECT已终态等后续阻塞。此前脚本都先给NEEDS_CUSTOMER/NEEDS_MERCHANT，所以没有暴露真实模型提前结束任务的路径。

**引用原文接口要求模型填写精确字符位置，负担过高。** 本次引用多为真实原句片段，但省略offset后默认0；实际位置分别是9、10、15。memory与对话事件共用这一问题，反馈后仍重复错误。第三轮还有把H3旧原文当本轮ADD的情况，不能仅修一个位置就声称该轮已通过。离线诊断逐项记录实际匹配位置，不修改原始模型输出或放行本轮草稿。

**来源类型齐全不等于字段含义用对。** U02订单来源O1明确status=PAID，物流O2为LOST，回答却说订单行也LOST。这是订单/物流事实表达混淆；U04归OTHER后没有读取流程指南，说明有限意图来源检查尚不能覆盖全部语义目标。

下一步应先区分“本轮已答复”与“事项仍开放/暂停/结束”，并处理再次讨论已答复事项；再把原文定位改成有歧义检查的程序定位，减轻模型数Unicode位置的负担；同时明确投影订单付款与承运状态的字段。上述是本轮发现后的建议，**本批没有实施，也没有再启动第二轮收费确认**。不优先换框架、增加Agent或继续堆RAG算法。
