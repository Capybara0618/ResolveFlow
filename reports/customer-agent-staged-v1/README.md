# 客服Agent职责拆分试验：工程链路通过，真实质量尚未比较

2026-10-22。按[开发方案](../../docs/customer-agent-staged-v1.md)完成公共事项保留、动作接口减负和可选两阶段模式。**本批没有调用真实模型；结论是新结构能运行、恢复并处理保存失败中的确定性问题，不能据此宣称实际回答质量提升。**默认仍是single，新模式需服务端显式选择staged-v1。

## 实际变化

1. **会话事项不再等同于本轮答复列表。** task_state.tasks保存会话事项，focus_ids标明本轮答复覆盖集合；插问可仅回答新问题，原调查不被删除，当前轮也可显式暂停非焦点旧事项。后轮沿用Java既有前轮任务透传，不新增DB迁移。旧事项不带旧O/P引用和答复原句。仍最多8事项，超过明确拒绝，不暗删。
2. **事件只表达一次。** PAUSE/CANCEL/RESOLVE由程序派生展示状态，不再要求模型同步两个枚举。当前客户原句、合法前态、显式重开仍校验；原始模型输出不改。READ_TOOL可带限长purpose说明，它不进入执行参数，其他未知字段/主体参数/工具权限仍拒绝。
3. **分阶段模式先理解、再自主调查与答复。** 首次TURN_UNDERSTANDING仅声明焦点、所需依据类别、当前事件和客户陈述。程序原子接纳后，后续调用只选工具或分项回答，不再重复生成事项与记忆标注。两段提示和上下文分别组织，同一模型、同一AgentScope循环、同一预算/一次纠错/调用账；不是多Agent或第二个SDK外模型循环。
4. **依据需求可以组合。** 一个物流焦点也能声明SHIPMENT+GUIDE，附带操作指引须同时引用两类当前依据。主intent为APPLICATION/HANDOFF仍强制指南，ELIGIBILITY仍强制政策。引用验证依赖已读来源，不允许旧run编号。

显式装配入口：`SupportRuntime(database, config, architecture="staged-v1")`，默认`architecture="single"`；两个模式共享上述事项/协议基础。架构、stages.py和两段提示写入run manifest。未结束run改变架构会拒绝，不静默切换阶段、预算或版本。此次没有修改默认网页启动或部署新模式。

## 仍然需要验证的事情

理解阶段是否漏诉求、错误关联原事项或漏标GUIDE，目前只有脚本接线证据。分阶段能减少同次输出职责，不保证模型语义识别一定正确。程序验证来源类别/引用存在和状态，不能证明自然语言每句都与来源一致，也不自动证明页面路径正确。调查/答复仍在同一自主循环，尚未独立增加第三个生成模型或审查模型。

v1理解一旦接纳便锁定焦点，尚无调查后重新进入理解阶段的机制；长历史虽然保留索引和后续读回，但理解阶段不调用历史工具，复杂指代可能需要澄清。8事项容量及单次运行窗口/迭代上限仍有效，不能把它当无限会话平台。

后续真实对照应以新冻结比较公共基础single和staged-v1，使用相同模型、事实、问题和业务标准，记录完整会话、误分类/漏项/错误指引、调用次数和延迟。两阶段还增加了显式依据需求检查；若要把提升归因于“拆阶段”本身，需要额外控制这一检查差异。现阶段只能比较整体候选方案，不能将差异全部归于多一次理解调用。不直接引入多Agent/大小模型或继续收费重跑。
