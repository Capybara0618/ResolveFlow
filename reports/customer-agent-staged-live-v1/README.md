## 实际改变了什么

两阶段在U05第2轮正确生成 `PAUSE(t1)` 与新入口事项 `ADD(t2)`：原签收事项留在集合中且为PAUSED，本轮只回答入口，实际读取指南后给出「我的售后」。单阶段同轮先漏t1事件，修正又生成非法 `SUSPEND`，整轮失败。因此“事项保留”和“理解/答复分开”有实际可观察的局部收益，不能再把本次单阶段失败解释成旧事项被程序删除。

两组U02均真正检索到本店R-LOST-001。单阶段经完成反馈后读取订单、物流、政策和指南，明确PAID与LOST属于不同字段，并完整回答条件/入口；两阶段读取物流、政策和指南，但needs漏ORDER，没有核查当前订单付款状态。它没有把订单说成LOST，但未完整证明原第一条件，且给出129元实付金额时缺ORDER来源。这揭示自报needs仍可能漏项，结构完整不等于回答事实均有充分依据。

两组独立人工咨询都给出无需退款金额、请商家核查→预览编辑→确认，且没有声称已提交。两组找到包裹后也都正确结束。两阶段结束首理解却复用了上一轮原句，实际一次修正后才成功，不能描述为每轮一次理解都准确。

## 完整多轮为什么仍失败

1. **单阶段：状态事件协议与失败后的恢复。** 暂停首答漏事件，反馈修正将PAUSE写为SUSPEND。因为暂停整轮失败，后轮真实t1仍OPEN；模型两次要求RESUME，状态机拒绝。这是接口枚举/事件理解与失败历史处理的问题，不能通过假补暂停成功解决。
2. **两阶段：客户记忆接口仍让模型承担引用管理。** 第3轮正确选择原t1、RESUME及SHIPMENT+GUIDE；但把supersedes先写成字符串，修正后写成“之前助手建议”的文本。实际之前客户陈述集合为空，supersedes要求较早同主题有效客户陈述的ID。其本意是“客户已经问过，不再追问”，却被记忆结构错误阻断整个理解阶段。拆阶段没有自动解决记忆协议设计。
3. **来源需求与反馈仍不够具体。** needs由模型生成，漏ORDER时现有检查不能验证未声明需求；记忆错误反馈也没有直接给出可用旧陈述ID/空集合及正确追加方式。增加更多Agent并不直接消除这些接口问题。

[离线诊断器](../../scripts/customer_agent_staged_live_diagnose.py)对保存响应复现5组机制检查：[结果](diagnosis.json)。38响应中35个语法合法，3个类型/枚举错误；合法语法仍可能被状态或记忆规则拒绝。仅在离线副本清空无效supersedes后，原第3轮陈述可按offset15追加，原RESUME也可独立通过。**这只定位原因，绝不算原真实轮成功，原raw没有改动。**

## 下一步建议

保留可选两阶段与默认单阶段。优先让模型只表达本轮客户陈述/变化及原句，由程序分配陈述ID；只有确有旧客户陈述时才提供可选替代目标，空集合走追加，助手建议不能成为替代目标。对状态错误反馈提供实际前态和合法动作，对金额等明确事实补足独立来源要求。先做保存轨迹与不同问法/前态的离线验证，再决定下一批真实验证；本批未实施这些建议、未增加多Agent或切换模型、未自动继续付费。
