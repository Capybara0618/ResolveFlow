# 客服 Agent 评测准备 v1

2026-10-21。12 类合成会话、每类 3 个连续用户输入，共 36 轮；目前没有运行正式模型评测，没有质量分数。实现与验收口径见 [本批设计](../../docs/customer-agent-readiness-v1.md)，进度仅看任务账本。

## 数据与评分

`scenarios.json`包含物流、混合资格/办理、签收争议、商品损坏假设、个人原因、独立人工咨询、消息对象、已解决接续、长历史纠正、503、政策完整条件与商家绑定。6 类开发、6 类验收变体；均由开发者可见，明确是合成且不是独立盲测/真人客服记录。每轮业务条件需要对照原文语义复核，不用关键词命中代替正确性。

事实及政策 pins 复用此前 v3 的合成快照，问题/会话身份是新版本。D07/D08 的会话状态为显式合成系统快照，正式运行应与冻结状态一致；不冒充 Java 数据库中的真实票据。D09 用重复背景和早期尾部纠正制造上下文压力，是边界样本，不代表自然客户的消息分布。前轮助手内容必须来自本组实际运行结果，不能把预期答案写入历史。

`prepare_turn(case, turn_index, completed)`构造下一轮：核对前轮 run/conversation/input_version，带入实际回答、完整原文档案、最近20消息和前轮任务提示。`criteria`、分组及 gold 不进入请求。失败记录保留且会话计入总分母；传输未知先确认原请求，不能填一个假的成功回答继续。

主评分：会话全部轮次/必要子诉求完成才计完整；同时报告逐轮完整/部分/失败和故障原因。引用、政策版本/事件/例外、客户纠正、来源缺失、办理步骤和未授权动作均复核。缺少正确政策、出现语义遗漏、拒绝本可回答的问题均不是正确完成。

## 固定流程对照与 RAG

固定组用相同模型、上下文、来源、版本和总预算：先从对话生成一次政策 Query，再依次读取订单、物流、指南和检索政策，最后回答/必要追问；不按已知样本省掉失败工具，同参数可重试上限与生产一致。模型真实请求/工具读取分别记账，固定组可能比 Agent 模型轮次更少，不预设 Agent 在所有成本项胜出。新 Agent 按观察决定动作。两组各自使用本组前轮实际回答，种子历史、每轮用户输入和事实保持相同。

RAG 复用被冻结的 [60题本地知识集](../customer-rag-v5/README.md)及 [外部政策对照](../../reports/customer-rag-v2/README.md)，不改旧问题/Gold/结果。生产仍为按商家/manifest/generation绑定的单 Query 三路 RRF；上下文补全 Query 由 Agent 同次决策生成。正式评测时同时保存实际 Query、完整召回依据及必要条件覆盖。RAG 排名与最终答案完整性分别评分，缺答案题单列；CE 不是本批默认路径。

检索热态、预热、首次请求、完整接口和模型时间分开；先核对压缩后事实/纠正保留，再解释 token。没有运行新测量，不把旧 13/17→16/17、6/12→11/12 改称本批成果。

## 无模型预检

仓库根目录：

```powershell
agent/.venv/Scripts/python.exe scripts/customer_agent_readiness.py --check
agent/.venv/Scripts/python.exe scripts/customer_agent_readiness.py --check --database --output tmp/customer-agent-readiness-v1/preflight.json
```

第二条需要已有 PG 55433，只做只读 generation/归属/全表hash核验，不加载 embedding、不调用模型、不迁移业务库。输出采用独占创建，避免覆盖前次证据。`manifest.json`冻结输入、相关生产代码、原始快照、知识资料和准备脚本的 hash；版本变化应另建准备版本，不改旧 hash 让历史结果通过。

该入口只负责预检和轮次构造，不执行真实模型双组调度或自动语义评分。正式评测阶段需使用既有实际 ASGI/调用账测量方式逐轮执行上述协议，并保留每轮请求/答案/失败；本批停止在此之前。三轮 API/AgentScope/PG 工程冒烟使用脚本输出，不能作为客服效果成绩。
