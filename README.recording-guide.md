# ResolveFlow 手动录屏操作指南

2026-10-30。由作者自行录屏、剪辑和配乐；助手仅提供实际操作路线。主线为同一笔耳机订单：购物 → 查询物流 → 确认退款申请 → 商家核验与审批 → 买家查看结果。片尾可加约10秒平台运行记录，不使用已否决的服务节点动画。

## 开始前准备

真实产品入口是 `http://127.0.0.1:5174/#/shop`；`http://127.0.0.1:8766/sample/` 是样片播放器，不是业务系统。

当前业务服务已停止。最近一次完整启动遇到Windows保留端口覆盖PostgreSQL的55433，需要先处理并确认完整启动和真实Agent可用，再录本指南的咨询/调查流程。此前为样片启动的部分商城服务不能代替完整启动。启动方式见 [运行指南](docs/local-runtime.md)。本指南编写没有启动服务或新建交易。

开三个独立标签页，提前分别登录；当前会话按标签页保存：

| 标签页 | 账号 | 用途 |
| --- | --- | --- |
| 买家 | demo_showcase，显示名卡皮巴拉 | 商城、订单、咨询、退款结果 |
| 商家 | admin01，松间数码 | 发货、售后工单、核验、审批 |
| 平台（可选） | platform | 客服运行记录 |

演示账号资料已配置，登录过程放在开录前。买家现有展示订单已退款完成；本次重新买一笔，保留旧记录，不把旧完成结果接到新订单视频里。

全程固定窗口尺寸、系统显示缩放和浏览器缩放。先录5秒并回放，检查文字、鼠标和按钮；读清金额后再正式录。页面可以正常滚动，角色切换时保持相同录制范围。

本次固定商品：**松间数码 / 无线降噪耳机 / 黑色 / 1件 / 329元**。样片中的银色349元和数量3只是操作测试，本次不沿用。

## 成片顺序

| 顺序 | 页面 | 建议成片停留 | 观众看到什么 |
| --- | --- | --- | --- |
| 1 | 商城首页 → 商品详情 | 15–20秒 | 商城完整度、商品、店铺与规格 |
| 2 | 确认订单 → 模拟付款 | 10–15秒 | 地址与金额核对、付款完成 |
| 3 | 买家售后咨询 | 25–35秒 | 自然提问、实际查询与答复 |
| 4 | 原会话内退款确认 | 20–25秒 | 329元、编辑原因、买家主动确认 |
| 5 | 原会话内核查进展 | 3–5秒 | 提交后进度可见 |
| 6 | 商家售后工单 | 30–40秒 | 材料、政策、核验与最终审批 |
| 7 | 买家原会话退款结果 | 10–15秒 | 模拟退款完成与329元 |
| 8 | 平台客服运行记录（可选） | 8–12秒 | 实际工具查询与答复过程 |

以上是剪辑后时长，实际录制可以更长。按段保存，段间暂停；金额、正文和按钮停稳后再点击，结果保留至少5秒。没有必要在一次录制里把所有等待拍完。

## 第一段：商城选购

1. 买家标签页进入商城首页，停留2–3秒。
2. 点击“无线降噪耳机”。详情页已删除独占一行的“返回商城”；左上角ResolveFlow可回首页。
3. 在商品页停留，展示商品图、松间数码、329元。
4. 确认规格为“黑色”、数量为1。
5. 点击“确认购买”。

商品图库第二张图片可选看一次，拍完回到第一张再买，避免为了展示图片产生长时间滚动。录制主线不需要展示所有参数与账号功能。

## 第二段：确认订单与付款

1. 在“确认订单”页核对已有示例收货地址。没有选中时，从地址选择器选择；资料编辑放在开录前完成。
2. 展示黑色1件和应付329元。
3. 点击“提交订单”，进入待付款的订单。
4. 点击“确认模拟付款”。
5. 等页面确认已付款，保留约3秒，然后暂停录屏。
6. 在买家订单详情展开“查看交易编号”，复制“订单”后的完整ID。它是本次商家发货、丢件设置和工单查找的对应标识；金额与商品相同不能代替订单身份一致。

## 暂停录屏：准备同笔订单的发货与丢件事实

这段属于场景准备，不必放进成片。成片后期加一句“发货后，包裹出现配送异常”即可；交易和物流为项目模拟场景。

### 商家发货

1. 切到商家标签页，点击左侧“交易订单”。
2. 点击“刷新订单”，找到刚付款的耳机订单；按付款时间、黑色1件、329元初步定位，点“查看订单”，展开“查看订单编号”核对完整ID。
3. 点击“模拟发货”。
4. 在对话框点击“确认模拟发货”，等页面确认发货完成。

### 设置包裹丢失

现有网页没有修改物流情景的入口，使用已有脚本。PowerShell在仓库根目录运行，下列代码只针对填入的新订单：

```powershell
$recordOrderId = '这里填本次新订单的完整ID'
$recordPython = '.\agent\.venv\Scripts\python.exe'
$recordInspectText = & $recordPython scripts/logistics_simulator.py inspect --order-id $recordOrderId --merchant-id M-1001
if ($LASTEXITCODE -ne 0) { throw '订单物流读取失败，请先检查上面的错误。' }
$recordLogistics = $recordInspectText | ConvertFrom-Json
$recordVersion = [int]$recordLogistics.fulfillment_version
$recordRequestKey = [guid]::NewGuid().ToString()
& $recordPython scripts/logistics_simulator.py advance --order-id $recordOrderId --merchant-id M-1001 --expected-version $recordVersion --scenario LOST --request-key $recordRequestKey
```

成功结果应包含本次订单和LOST/丢失事实。若命令响应不确定，先inspect；需要重试时沿用刚才的request key和版本/载荷，不重新执行整段生成新key。此设置是模拟物流事实，不是修改退款结果。脚本说明见 [物流场景工具](docs/logistics-simulator.md)。

## 第三段：买家咨询物流

1. 回买家标签页，点击顶部“售后咨询”。
2. 点“选择订单”或空页面的“选择订单商品”，选刚购买的黑色耳机；按订单尾号区分旧订单。
3. 开始录屏，在咨询输入框输入并发送：

> 耳机还没收到，帮我看看物流到哪里了？

4. 拍到助手正在查看和实际答复。长等待可在后期剪短，保留过程提示与最终正文。
5. 看到丢失事实后停留3–5秒，便于观众读清。助手实际用词随模型变化，不要求逐字复现旧样片。

## 第四段：在原会话确认退款申请

1. 继续输入并发送：

> 我没有收到耳机，请帮我准备退款申请，金额和原因我核对后再确认。

2. 若原会话已经出现退款摘要卡，直接核对；否则点击输入区下方“申请退款”生成摘要。本段走退款申请，不点击顶部“请商家核查”，后者会进入独立咨询核查流程。
3. 确认商品黑色1件、金额329元。
4. 点原因旁“编辑”，填写：

> 这件耳机一直没有收到，申请退还本件商品实付款。

5. 点“保存原因”；若卡片要求“核对申请摘要”，先按该按钮重新核对摘要。
6. 等329元和原因稳定显示，停2–3秒，再点“确认提交申请”。
7. 拍3–5秒原会话中的“正在核查”等实际进展，然后暂停录屏。

确认后只跟随当前申请。模型调查可能需要更多时间；刷新读取当前进度即可，不重复确认创建新申请。

## 第五段：商家核验与审批

### 打开对应售后工单

1. 切商家标签页，点击左侧“售后工单”，不是“咨询核查”。
2. 把处理阶段切为“全部工单”，在“搜索工单”中输入本次完整订单ID，点击“查询”。
3. 打开对应工单，核对商品、黑色1件、329元和买家申请原因。
4. 等当前调查结束，再开始录这段；可先拍到调查状态，再暂停等待。

### 如页面显示“核验申请陈述”

1. 点击“核验申请陈述”，打开完整记录。
2. 查看本单订单与物流记录，确认LOST/丢件、无签收记录。
3. 在“核验理由”输入：

> 已核对本件耳机付款及物流记录：承运商确认包裹丢失，没有签收记录，与客户未收到的陈述一致。

4. 找到买家未收到商品的原始材料，在该材料的核验按钮中点击“确认”。先填写理由，再点材料的确认，不选“驳回”或“无法判定”。理由要与本轮实际记录一致。
5. 提交后会产生新材料版本并重新调查。暂停录屏，等新调查完成，回到工单概要查看当前建议。旧版本建议仍可能留在历史记录中。

如果当前页面已经提供可用的“批准退款”，按页面当前权限继续审批，不重复提交同一核验。

### 批准当前退款

1. 恢复录屏，先展示当前调查建议；打开引用的政策条款，停2–3秒，再收起。
2. 核对当前建议、商品和金额；“批准退款”可用时点击。
3. 在“批准理由”填写：

> 已核对付款、丢件记录和客户材料，同意退还这件耳机全部实付款329元。

4. 点击“确认批准”，等页面进入执行或显示模拟退款成功。

如显示需补充说明，按当前问题补证后继续；如显示调查失败、旧建议失效或按钮不可用，暂停在该页面处理，不用“其他处理方式”的人工方案替代原定Agent调查镜头。本指南沿用已跑通的丢件场景，真实模型结果仍以本次页面为准。

## 第六段：买家查看结果

1. 切回买家原来的咨询会话，等待结果更新；必要时点“刷新进度”或“刷新记录”。
2. 原会话显示“退款完成”和329元后，停留至少5秒。
3. 可补拍一次顶部“消息”中的本次处理提醒，点击后进入同一申请，再停留2–3秒。
4. 此处已经完成主线，不必为了片尾再追问模型；使用页面已有、可核对的结果。

## 可选片尾：平台记录

1. 平台标签页点击“客服运行记录”。
2. 刷新，按刚才的时间与M-1001定位本次咨询，打开一条对应运行。
3. 拍8–12秒：订单/物流查询、答复记录，以及页面已有的实际调用信息。
4. 用与主片一致的擦除转场接入，最后回到商城或以品牌与源码地址收尾。

## 推荐保存的原始片段

`01-商城与下单`、`02-买家咨询`、`03-买家确认申请`、`04-商家核验`、`05-商家审批`、`06-买家结果`，可选 `07-平台记录`。核验后重新调查可能耗时，所以商家核验与最终审批分开录最省事。

动图从最终视频截取“咨询答复 → 买家确认 → 商家批准 → 买家退款结果”，不用再独立跑一笔订单。现有旧素材保留作参考，成片主线始终使用本轮同一订单。
