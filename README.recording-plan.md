本文件是录制方案，不是已完成素材或新业务验收记录。当前只提交内容稿与分镜；用户审核后才准备新订单、调用真实模型并录制，不沿旧退款重付、不删除旧数据或重写历史答复。

## 1. 想让访客记住什么

一个人把可交互商城、Agent 咨询、人工决策与模拟退款做成了能连续使用的系统，并提供源码与本地运行入口。界面体验用实际操作证明，技术能力用职责边界、实现和可核对的测量支撑。

首屏文案建议：**从购买到售后，把一次真实操作体验完整做出来。** 不写无人审批、真实到账、商用高可用或所有问题都能自动解决。

固定商品建议：松间数码无线降噪耳机，黑色、1件。当前价格329元仅作脚本示例，录制时以页面与 Java 实际金额为准，不改价格凑字幕。

使用新演示订单和属于本次演示的会话。买家与商家分开标签登录，平台另用标签；保持同一店铺、商品规格、订单行与申请。旧示例订单及错误历史继续保留。若选用已有买家账号，截图范围需避开无关历史，不能通过删历史获得干净画面。

先确认三 Java、Agent、消息系统、政策索引及前端健康，确认没有意外待运行任务。录制浏览器约1280×720或1440×900，保留100%缩放；选择一个尺寸贯穿，不用缩小字号塞入首屏。预查该尺寸下买家确认按钮、商家操作与结果均可见。

## 6. 参考输入与成功判断

以下是自然语言参考，不写死模型输出、不改变问题以掩盖失败：

- 查物流：“耳机还没收到，帮我看看物流到哪里了？”
- 准备申请：“我没有收到耳机，请帮我准备退款申请，金额和原因我核对后再确认。”
- 编辑原因示例：“这件耳机一直没有收到，申请退还本件商品实付款。”
- 完成追问：“现在这笔退款办好了吗？退了多少钱，还需要我做什么？”

预期是与当前事实一致的通俗回答，不要求逐字复现。缺失事实允许补查或转人工，不能用笼统“运行成功”替代实际答复质量。完成后金额取Java当前结果；未知结果不能展示成功。

商家演示核验只能确认自己实际查到的本地事实，例如“模拟承运记录LOST且无有效签收，与本件商品及客户未收货材料一致”。商家审批仍使用当前有效建议/授权与页面操作，不修改数据库把工单推成可审批。

## 7. 物流场景的可复现准备

购物并模拟付款本身不会自动制造LOST。新订单先通过商家正式页面模拟发货；再用已有工具读取本次订单当前版本，只推进该订单的物流，不清库。

仓库根目录的 PowerShell 模板如下，**本稿不执行**。订单id来自新订单，版本来自inspect结果；请求key在第一次提交前生成并记录，丢响应时不得重新生成key或修改payload：

```powershell
$demoOrderId = '<本次新订单id>'
$demoMerchantId = 'M-1001'
.\agent\.venv\Scripts\python.exe scripts/logistics_simulator.py inspect `
  --order-id $demoOrderId --merchant-id $demoMerchantId

# 核对inspect输出中的实际版本后再填写，不默认任何固定版本。
$demoExpectedVersion = '<当前物流版本>'
$demoRequestKey = [guid]::NewGuid().ToString()
.\agent\.venv\Scripts\python.exe scripts/logistics_simulator.py advance `
  --order-id $demoOrderId --merchant-id $demoMerchantId `
  --expected-version $demoExpectedVersion --scenario LOST --request-key $demoRequestKey
```

工具由本地Docker环境操作模拟物流，面向维护者准备演示，不是买家可修改承运事实的产品入口。若不存在订单、未付款/未发货、版本不匹配或主体不符，按实际拒绝处理。
