# 审查员工作台、RAG 与 Agent 待优化方案

2026-09-28。本文整合审查员端现状分析与 RAG / Agent 优化意见，作为后续实施的设计输入。本次只交付文档，不启动业务开发、数据库迁移或模型调用。

本文中的现状是本次源码核查及既有报告的结论，不代表重新完成端到端验收。待优化项不等于已实现项；执行进度只在 [tasks/todo.md 顶部](../tasks/todo.md)维护。本文不替代 C00–C13 账本，不自动改变 C12 的评测、预算或提交安排。

## 1. 目标与范围

审查员的核心工作是：**查看原始信息 → 核对 Agent 建议及依据 → 完成人工决定 → 跟踪处理结果。**

Agent 负责整理资料、按需调查、查找政策、识别矛盾和缺失信息、提出有依据的建议；审查员负责人工判断；Java 继续负责权限、金额、授权和执行硬约束。本文聚焦进入人工处理的工单，不以此取消既有自动处理规则。

目标是让审查员打开任一典型工单后，知道发生了什么、建议依据是什么、现在可以做什么，以及操作后如何查看最终结果。参考图指导布局、层级和视觉质量，不能直接成为新增业务规则的依据。

范围沿用 [core-scope](core-scope.md)：单订单行全量模拟退款、物流异常与商品损坏、单 Agent、现有三个 Java 服务与 Python Agent。用户端页面暂不优化；补证闭环所需的服务端契约仍需保持兼容。

本轮路线不引入多 Agent、全套售后管理后台、真实支付、补发、库存、图像真实性识别、政策管理平台或完整观测集群。会员体系、优惠券规则、个人审批额度和媒体附件链路列为后续范围决策，不自动实施。

## 3. 必须优先修复的审核断点

### 3.1 无待审授权时也要有合法的人工处理路径

区分“有待审授权”“无方案”“方案过期”“旧授权已失效”“执行已消费”等状态。前端不得仅凭工单为 PENDING_REVIEW 就显示可批准，也不能只留一句无法审批的提示。

- 有有效待审授权：沿用批准、拒绝、请求补证及版本校验。
- 无有效方案或授权：提供人工形成方案入口；金额由 Java 重算，依据必须可核查。
- 无授权时拒绝或要求补证：先定义独立业务动作与状态迁移，再补契约及入口；不能伪造授权来复用现有审批接口。
- 已消费或退款结果不确定：冻结输入，展示进度与原因，禁止换 ID 重付或重新审批绕过执行状态。

建议由服务端给出当前允许动作及不可用原因；该信息用于界面提示，写入时仍重新校验权限、状态和版本。

### 3.2 材料变化后形成新的审核依据

显示“本次核验会更新材料修订，旧方案/授权可能失效”。材料提交后应明确呈现旧建议过期、新调查状态或人工方案入口。新结果必须对应当前 input_revision；迟到结果不能覆盖当前建议，也不能悄悄替换审批弹窗已确认的版本。

### 3.3 决定之后仍能找到工单

在轻量工作台中补齐待审、待补证、处理中、需关注、已结束视图，明确各视图对应的领域状态。按业务需要支持工单/订单编号及状态筛选，不默认增加派单、团队绩效或运营平台。

退款详情区分别表达已授权、执行中、结果不确定、成功和明确失败。失败返回人工处理时，说明原因及允许的后续动作；不提供无条件重试按钮。

## 4. 审核数据与接口优化

不推倒数据库重建。现有交易核心偏重一致性，需要补充面向审核的查询数据，而不是削弱现有约束。

| 层次 | 调整方向 | 必须保留的边界 |
| --- | --- | --- |
| 权威业务数据 | 保留工单、证据修订、方案、授权、账本、执行结果及事件 | Case/Commerce/Python 的所有权不变，金额与授权不能由 UI 或模型推导 |
| 审核详情 | 汇总原始信息、方案、核验、政策引用、执行摘要及允许动作 | 不跨服务直接读对方数据库；来源、版本和不可用状态明确 |
| 展示字段 | 盘点商品名称/规格/图片、支付时间等数据归属，按审核必要性逐项补齐 | 无数据不编造；支付渠道/流水没有提供时明确缺失 |
| 证据与引用 | 保留来源、时间、版本/hash、核验人及理由等必要元数据 | 原始材料、人工核验、模型推断分开；按主体授权读取 |
| 演示样本 | 可重复创建完整场景，标明合成业务、模拟支付、mock/live 来源 | 不清旧库或删卷；避免重复生成和混用历史调试工单 |

建议先定义审核详情的字段契约及空值语义，再同步 Schema、类型、生产者、消费者与 fixture。数据库确需扩展时只追加迁移。未知、缺失、不适用、读取失败应分别表达，不能统一画绿勾。

## 5. RAG：让政策成为可核对的审批依据

优化重点是正确政策、适用条件和可追溯引用。审查员应能从建议直接打开对应政策原文，查看版本、关键条款、适用条件、例外及关联事实。

1. 保留商户、类别、manifest 和历史版本硬过滤；按既有政策绑定规则检索，不能为了命中换成最新版本。
2. 检查分块是否保留完整条件与例外，避免只检索到“可以退款”而丢失前置条件。
3. 将引用编号转换为可读条款，支持跳转到对应原文及事实来源；读取接口继续校验权限与绑定版本。
4. 将“检索相关”“模型认为适用”“Java 规则校验结果”分开呈现。相似度不是资格，模型解释不是授权。
5. 找不到依据、政策冲突、索引未就绪或引用失效时明确显示缺口，按现有规则等待、补证或转人工。

例如，政策要求物流确认丢失时，客户“没有收到”的陈述不能替代物流确认；输出应指出还缺哪项事实。

本次核查时，账本记录的历史 40 条查询中两组 Recall@5 均为 1，dense Top-1 为 30/40、BM25 为 31/40。该小样本没有证明 dense 更优，也不能证明最终建议正确；本文未重跑该实验。

评测复用 [policy-rag](policy-rag.md) 与 [evaluation](evaluation.md) 的规模和分组：覆盖近似条款、例外、无适用依据、跨商户及历史版本。保留冻结 test，不用测试错例反复调参；新增诊断样本与正式对照分开标记。不默认增加 hybrid、RRF、rerank 或更换模型。

## 6. Agent：交付可审批的调查结论

Agent 的价值应体现在替审查员完成有用调查，而不是增加聊天窗口或显示不可验证的置信度。

### 6.1 建议的结果结构

以下为待设计字段组，不代表现有 API 已提供。复用现有 proposal/observation/run 数据，避免另存一套相互矛盾的结论。

| 字段组 | 应表达的内容 |
| --- | --- |
| 建议动作与摘要 | 建议退款、拒绝、补证或人工判断，以及简短理由 |
| 已确认事实 | 每项关联原始来源；明确系统记录或人工核验 |
| 模型判断 | 与事实分开，说明使用了哪些依据 |
| 冲突与缺失 | 客户陈述与记录差异，尚缺材料，以及是否影响决定 |
| 政策依据 | 条款、版本、原文入口、适用条件和例外 |
| 调查状态 | 进行中、已完成、失败、过期或转人工及原因 |
| 结果归属 | case/input_revision/run、方案来源及 mock/live 标识 |

输出示例（预期格式，非真实调查结果）：客户称未收到商品；物流记录显示已签收，尚无丢失确认。现有依据不足以支持按丢失退款，建议补充签收争议材料，并列出原始物流记录与相关政策。

### 6.2 调查行为与页面呈现

- 模型按实际 Observation 决定下一步；不为演示写死完整工具调用顺序，不要求每个工单调用全部工具。
- 有充分依据时结束调查；缺证据时提出具体、有限的问题；冲突或失败时说明转人工原因。
- 展示已经持久化的工具/检索事件及结果摘要，如读取订单、核对物流、检索政策。不得编造进度或把内部思维过程作为审核证据。
- 界面用“结论 + 关键依据 + 待确认事项”组织建议区；引用可定位材料或政策，完整技术轨迹按需展开。
- 保留权限、预算、引用校验、fence、恢复和 strict 回放规则；Agent 仍无审批、退款或政策修改权限。

### 6.3 真实效果验证

先证明真实业务数据读取、检索、引用和结果回传能贯通，再评价建议质量。mock 接线、真实模型、人工方案分别记录；服务启动不等于调查启用，更不等于 live 已验证。

复用 C12 的预算、费用账本及评测安排，不新开未计费实验。指标包括建议是否有来源支持、政策是否适用、缺证时是否正确停下、补证是否有针对性，以及调用次数、延迟和费用。审查时间和建议采纳率只有实际人工测量后才能报告，不预设提升比例。

## 7. 建议实施顺序与验收

下列编号仅用于本文设计引用，不新建第二份执行账本。每项在实施前按契约、服务端、界面等依赖继续拆成通常 3–5 个核心文件的子步；必要失败测试随实现进行，按用户要求在功能批次集中验收，不每个样式小步要求人工确认。

| 顺序 / 优先级 | 交付项 | 依赖 | 验收标准与验证方式 |
| --- | --- | --- | --- |
| A / P0 | 审核状态与数据契约 | 无 | 列出所有典型状态的允许动作、原因、字段来源及版本；通过契约/fixture检查，保留原接口兼容 |
| B / P0 | Agent/RAG 真实接线样例 | A | 一条代表性人工审核工单可追溯到真实工具、政策检索和持久方案；分别记录 mock 与受控 live 验证，不能互相替代 |
| C / P0 | 无授权人工接管 | A | 证据与政策可选择引用，人工方案经 Java 校验生成待审授权；拒绝/补证的无授权语义有测试与页面入口 |
| D / P0 | 核验后更新流程 | B、C | 核验后旧建议显示过期，新结果对应当前修订；旧审批、迟到回调和消费后修改均被拒绝 |
| E / P1 | 工单列表与执行结果 | A | 待补证、执行中、异常、已结束均能查询；批准后可跟踪到最终结果，UNKNOWN 不显示为失败或成功 |
| F / P1 | RAG 依据展示 | A、B | 点击引用能打开正确主体/版本的条款和事实；覆盖例外、缺依据及读取失败，不能以相关性代替资格 |
| G / P1 | 结构化调查结论 | B、F | 事实、推断、冲突、缺口分开；无依据输出被拒绝或明确降为不可执行建议；契约与渲染测试通过 |
| H / P1 | 难例诊断与质量优化 | D、G | 复用冻结对照，报告建议支持性、政策适用、缺证处理和成本；失败如实记录，不扩大现有实验规模 |
| I / P2 | 展示数据与视觉收口 | C–G | 补齐必要商品展示字段及稳定样本；正式页面接真实接口，参考图布局在桌面和窄屏可用，无假按钮或假核验标识 |

批次检查点：A–D 检查人工审核闭环及调查来源；E–G 检查工单跟进和依据可读性；H–I 检查实际效果及视觉交付。无需每个子步重复全量测试或人工验收；新增失败和未决风险仍需及时验证。

## 8. 代表性验收场景

| 场景 | 必须看到的结果 |
| --- | --- |
| 满足政策、已有待审授权 | 有依据的建议，人工批准后可跟踪模拟退款结果 |
| Agent 无法形成方案或转人工 | 原因可见，人工可根据材料和政策形成新方案 |
| 客户称未收货但物流显示签收 | 显示矛盾，不把客户陈述当丢失确认；补证或人工判断 |
| 商品损坏仅有单方描述 | 不能自动核实；人工核验后旧建议失效并形成当前修订的依据 |
| 缺适用政策或引用旧版本 | 显示缺口或拒绝无效引用，不静默换政策 |
| 等待补证及收到新材料 | 列表可找到；问题与答复关联，新旧建议明确区分 |
| 并发审批或旧弹窗提交 | 拒绝过期版本，刷新后重新审阅，不静默替换已审版本 |
| 退款 UNKNOWN、明确失败、成功 | 各自展示准确状态；不重复退款、不误报到账 |
| 跨商户访问 | 工单、证据、政策及执行摘要均不可越权读取 |

样本由受控种子或现有 API 准备；不依赖用户端界面改造。为每次验证记录实际命令、输入样本、模式、通过/失败/未运行及报告。前端使用现有 `pnpm --dir web test`、`pnpm --dir web build`；Java/Python 采用受影响测试与既有可执行验证入口，不将尚未实现的 suite 算作通过。

## 9. 实施前需明确的设计事项

- 无授权时拒绝/补证的事件、并发控制及终态语义，与既有追问轮数和超时规则对齐。
- 材料更新后由现有调查调度重启还是在特定失败状态提供受控入口；重试不重置同 run 预算或绕过输入冻结。
- 审核查询的聚合位置、字段所有权及故障表达，优先复用已有服务，避免新增平台或跨库耦合。
- 原始资料与调查快照同时存在时，清楚显示各自时间和版本，不能把当前变化追写为历史依据。
- 商品展示字段按必要性补充；媒体上传、客户画像、支付流水和个人审批额度如需实施，应先另行明确范围。

以上事项属于后续实施中的设计工作，不要求现在逐项向用户提问。范围内选择结合现有规范自行落实；实质业务范围变化才单独说明。

## 10. 完成标准

审查员能看懂原始信息，核对 Agent 的事实和政策依据，识别不确定性，完成允许的人工操作，并找到后续结果。不能处理时，能看到真实原因和下一步。

RAG 的价值以政策引用正确且适用来体现；Agent 的价值以减少资料整理、发现冲突和提出有效下一步来体现；视觉质量以正式业务页面为准。已有安全与资金不变量持续成立，未完成能力如实标记。
