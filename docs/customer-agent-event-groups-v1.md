# 客服对话变化：显式事件分组

2026-10-21，用户要求继续处理任务与对话事件一致性。上一批真实混合题能提出三个任务，却只给一条task_id=t1的ADD，纠错后仅重发工具动作。完整轨迹保留，不能把这一格式失败称RAG效果差。

## 取舍

tasks描述当前事项/回答状态，dialogue_events描述客户本轮引起的变化及来源。两者含义不同，暂停/恢复/撤回不能仅从最终状态猜测；但同一次新增的三个事项反复复制同一句客户原文没有必要。本批支持一条显式事件用task_ids数组关联多个任务，共享change与原文定位。旧task_id单项保持兼容，两种目标形式二选一，1–8个不同的合法ID。

程序只展开模型明确给出的ID，逐项验证已存在的任务、前后状态与本轮客户原文，内部仍保存每任务的事件记录。不会给缺项自动补ADD/CONTINUE，不会自动标ANSWERED，不猜暂停/撤回意图。组中一项非法、组间重叠、未来/旧消息来源或任务覆盖缺失，整次动作拒绝且此前状态不污染。

首次标注与新增事项缺少覆盖时，反馈列出missing_task_ids，要求完整tasks/dialogue_events重发，说明可共享task_ids及CURRENT/0/原文。仍只有一次纠错，模型原始输出不重写。首请求示例与SYSTEM同步使用分组语法；未给任务的首次动作仍拒绝。

本批仅改变Python内部模型标注协议，公开会话API/Java/商家数据协议不变，领域输出仍逐任务事件；不改RAG、资金权限、模型参数、1024输出或120秒预算。旧输入/Gold/冻结清单不改，新运行须独立冻结。来源绑定证明结构一致，不能证明模型对当前原句的语义理解正确。
