# 聊天退款确认与真实流式体验开发方案

2026-10-23。用户认可“退款意愿→摘要卡片→编辑确认→创建申请→会话查看进度”，并要求Agent响应快、真实流式、现代聊天体验。本批先交付设计和可交互预期稿，不修改业务代码、发起模型调用或启动原项目。唯一进度仍在tasks/todo.md顶部；生产冻结基线为426f08c，本次属于明确授权的新产品能力，实施需新manifest，不回写旧冻结结果。

预期稿见[桌面交互稿](ui-chat-refund-stream-v1/index.html)，交互说明见[图册说明](ui-chat-refund-stream-v1/README.md)。图中文案、金额、时间和动画均为合成设计样例，不能作为真实耗时/交易/效果证据。

## 1. 用户可感知的目标

用户发送后立即看见自己的消息和助手接收状态；查物流/政策时看见真实简短进度；进入回答生成后正文随供应商实际增量出现，来源随后补齐。收到退款意愿时，在同一会话展示可编辑申请卡片，用户点“确认提交申请”才创建正式申请，随后卡片切换为当前进度。用户不用重新讲一遍情况或跳转填同一段表单。

保持已认可的三栏布局：左侧商品咨询，中央会话和卡片，右侧订单/物流/依据。按钮区和输入框不随流式抖动。用户向上阅读时不强制滚到底部，出现“有新内容”按钮；贴近底部时跟随新文本。来源按需展开，页面不展示工具参数、JSON、模型思维链、fence或内部错误码。

商家继续使用现有售后工单/核查工作台。用户确认退款申请时共享的是申请原因与明确选中的材料；商家看不到流式草稿或未共享的助手私聊。无需新增商家聊天Agent、实时坐席或第四个Java服务。

## 3. 两条完整产品链路

### 3.1 自然对话与流式

1. 发送后先在当前会话追加本地“发送中”消息；服务端回执后成为已保存消息，出现助手接收态。
2. 连接当前会话事件流。只展示真实节点：“已收到问题”“正在查询物流”“正在核对本店政策”“正在生成回答”；没调用的工具不能用定时器伪造完成打勾。
3. 理解及工具选择仍采用原两阶段。只有已识别为ANSWER_PARTS的`parts[].text`内容增量进入聊天气泡，非回答决定不向客户流式展示。
4. Provider真正返回文本时，逐批发送`answer.delta`，气泡显示轻量“正在生成”与光标。不能等完整结果后再逐字播放，也不能新增一次专门打字的LLM总结。
5. 当前完整决定校验通过后，由Java发布持久助手消息和`answer.committed`，客户端以最终权威文本/引用/卡片替换同一个气泡，清除生成状态。程序补入的事实/固定步骤可以与草稿长度不同。
6. 单次修复时，用`answer.reset`清除这一attempt的未接纳文本，在同一气泡显示“正在完善回答”，随后新attempt增量替换；不能把错误草稿累加到最终答案或提交到历史。最终失败/过时发`answer.failed`/`answer.stale`，撤下本轮生成视图并展示原有重问/核查入口。

流式生成视图不作为历史、证据、申请摘要、分享报告或自动操作依据。半截占位符、未读O/P、金额、未完成JSON和reasoning_content都不直接暴露；具体增量转换见[协议与实现约束](customer-chat-stream-contract-v1.md)。草稿可能在终局修正，最终读回必须与Java持久消息一致。这是为兼容真实token流与现有结构化Harness的必要区别，不是把供应商原始JSON发给用户。

### 3.2 聊天内正式退款申请

1. 用户说“我要退款”时，模型整理当前商品的问题摘要，可在最终答复提出`REFUND_APPLICATION`及申请原因建议。模型不生成case_id、金额、建单结果或业务写动作。
2. Java按当前本人订单行核对`can_apply`、已有申请、权威实付金额和数量，形成持久申请草稿。模型建议可辅助填原因；失败时用户仍可手动填写，不需要额外模型调用。
3. 卡片显示商品/规格/数量、整行申请金额、原因、将提交的材料摘要和“提交后等待核查”。金额只读，当前范围仅整行全量模拟退款；用户编辑原因，可取消继续聊。
4. 用户确认才调用确认端点。确认请求绑定草稿revision、会话版本与幂等键；Java重新核对本人/店铺/订单行、资格和金额，不相信浏览器金额或模型confidence。网络查询在事务外，创建/关联/提交回执在短事务完成。
5. 创建成功，同一张卡片显示申请编号和当前状态；在“我的售后”也能看到同一个申请。重复点击/同请求重试返回原case_id；已有申请显示“查看申请”，不偷偷另建一单。
6. 会话中的进度来自客户专用Case投影，区分申请已提交、核查中、待补充、待审核、退款处理中、结果待确认、退款完成/未通过。只有实际成功结果才显示退款完成。请求补充可进入原申请详情回复，首版不在聊天中重新实现所有补证/撤销操作。

人工咨询核查单与正式退款申请分别显示；要求人工帮助不默认退款，聊天内提交退款也不把全部私人历史交给商家。用户编辑并确认的原因进入正式申请；原咨询关联供本人追溯，商家只能读取原有客户投影允许的材料和已确认共享内容。

## 4. 性能验收目标（目标，不是已测成绩）

最新四轮Agent接口3.35–6.39秒，平均约4.94秒；不包含完整网页排队/派发/轮询，原8秒页面轮询可能进一步拖慢。本次目标针对已预热、单用户正常网络的桌面基线，先固定语料测量，未达标时报告实际瓶颈，不用虚假动画掩盖。

| 计时 | 起止点 | 第一版目标 |
| --- | --- | --- |
| 本地发送反馈 | 点击→自己的消息/等待态绘制 | p95 ≤100ms，不等模型 |
| 服务端接收反馈 | 点击→服务端确认保存及turn.accepted | p95 ≤500ms |
| 首次真实处理进度 | 保存→worker领取/真实读取开始 | p95 ≤1s；不伪造工具执行 |
| Provider回答首增量 | 最终回答调用发出→首个content delta | 单独记录供应商耗时，不等同用户首反馈 |
| 首段有效正文 | 点击→首个可读正文字符 | 普通查询目标p95 ≤4s；多来源目标p95 ≤6s |
| 增量转发 | Provider delta收到→浏览器绘制对应内容 | p95 ≤250ms，无固定逐字定时播放 |
| 整体完成 | 点击→权威答复/可用卡片 | 普通目标p95 ≤6s；多来源/一次修复目标p95 ≤9s |
| 申请确认 | 确认按钮→case_id及关联落库回执 | p95 ≤1s（本地已有依赖，不含退款执行） |

至少30次固定单用户样本分别报告p50/p95/最大值，按简单/多来源/修复分组；预热、冷启动、Java派发、模型各轮、工具读取、首流、渲染分别计时。首次预热发生在服务ready前，不能让客户第一条承担9秒模型加载；状态接口必须体现真正就绪。必要时先优化派发唤醒、事件查询/转发和重复文本，不为了速度取消理解阶段、来源检查或恢复预算。没有凭4条旧结果宣称p95达标。

## 5. 开发拆分与验证

按纵向小步，每步通常3–5核心文件，先关键失败用例、同步契约/类型/fixture，验证后独立commit/push。大步骤再拆子步，不一次铺完十几个核心文件。

| 顺序 | 交付 | 必验项 |
| --- | --- | --- |
| S1 传输spike | 隔离Provider真实增量读+JSON正文增量解析；不接页面 | UTF-8跨块、转义/半截字段、usage尾帧、流中断、一次发送一次计费；先合成分块，有限真实调用另按授权执行 |
| S2 进度纵向链路 | Case事件追加/读取→Gateway SSE→前端当前会话 | 拥有者/跨店404、Bearer、事件有序/去重/断线续读、心跳/flush、旧版本/fence拒绝、轮询降级不重发用户消息 |
| S3 真实正文流 | Python观察器→Case事件→气泡增量/重置/最终提交 | 首delta早于完整响应；facts/引用隐藏与终局替换；一次修复不重复气泡；旧turn不显示；流断不自动重付 |
| R1 申请草稿 | Java本人行资格/权威金额、原因编辑、草稿revision/过期 | 无模型金额/跨主体覆盖、已有申请/已退款、编辑取消、旧版本确认拒绝；仅draft不建Case |
| R2 确认建单 | 复用CaseService业务及本地原子关联、回执 | 同键重试/载荷冲突、双击/竞态/网络未知、只一case、原款/授权约束；初始原因不再二次独立追加造成半成功 |
| R3 会话进度 | 读取客户Case投影、消息中的申请卡片、商家既有入口 | UNKNOWN不冒充成功、已有申请恢复、商家仅见可见材料、刷新同申请、咨询和退款状态不混 |
| A1 集中验收 | 桌面实服务+固定真实对话+计时报告 | 四类卡片状态、无8秒跳变、真流trace、补读修复、新输入/切商品/重连、创建同单、已有退款链复核 |

先实现S1–S3并验证真实流，再做R1–R3；用户可以先受益于等待体验。首轮文档/预期稿不称S1已完成。真实评测/页面截图/模拟退款执行分别记账，旧报告/原数据不覆盖。保持三个Java进程与Python，不新增MQ、Redis流平台或重选依赖。
