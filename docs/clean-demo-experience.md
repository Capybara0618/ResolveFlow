# 在浏览器体验 ResolveFlow

本机当前使用2026-10-03新基础环境：3家店、30种商品、45个SKU、14个账号。账号已合并为买家、商家、平台三种身份，六个专员不再使用。角色升级保留后续交易；当前另有三店各一笔标注“合成集中验收”的退款成功记录，可用于查看终态。旧基础报告中的ID仍是历史证据。日常启动保留之后手动产生的数据。

## 启动

启动Docker Desktop，在项目根目录打开PowerShell：

```powershell
cd 'E:\Code\Agent+Backend'
.\start.ps1
```

浏览器打开 http://127.0.0.1:5174 。商城入口为 http://127.0.0.1:5174/#/shop 。启动默认读取用户环境变量 `Deepseek_API_KEY`，包括新申请的真实 Agent 调查和政策检索，不需要选择运行模式；缺密钥明确失败。新调查会产生模型用量，商城、模拟付款和发货本身不需要模型。正式启动/停止/状态与首次配置见[本机运行说明](local-runtime.md)。

```powershell
.\status.ps1
.\stop.ps1
.\start.ps1 -SkipBuild   # Java源码未变且已构建时
```

首次构建较慢。停止后再启动保留账号、商品、购物车、订单和工单，不自动重复初始化。不同角色各开一个浏览器标签，标签会话独立；刷新后重新登录。

## 第一次走通退款

1. `buyer01`进入商城，任选一家店的商品，选择规格和数量，直接购买或加入购物车。购物车按店结算，确认报价并完成模拟付款。
2. 在“我的订单”打开已付款商品，申请退款，写明“尚未发货，申请退款”。每次只申请一条商品行的全额退款；其他行仍可单独申请。
3. 在另一个标签登录对应商家，例如松间数码用`admin01`。进入“售后工单”找到新申请，查看原始陈述、订单/履约事实、Agent建议和政策引用。工单自动归属本店商家，无需领取。
4. 确认当前建议与事实一致后批准；审批是人工决定，模型不能直接退款。需要更多材料时请求补证，买家回答后等待新调查；人工核验材料也会使旧建议失效。
5. 买家回到申请和订单详情，查看退款成功及金额。Java执行的是本地模拟退款，账本显示已退金额；同一行只能有一次成功退款。

先体验未发货退款最直接。商家“交易订单”可以模拟发货；发货后应按真实履约事实与相应政策判断，不能仍将订单视为未发货。

## 维护基础数据

`platform`登录后有“商家管理”和“买家账号”：创建商家时同时创建商家账号，创建买家，启停以及买家密码重置。停用和重置会使旧登录失效。目录同步失败显示待同步，用原商家重试；不要用另一个ID重新建店。

商家`admin01`–`admin03`的“商品管理”支持本店新建/编辑、规格和价格、上架/下架。价格在页面按元输入，后台按整数分保存；改价不修改已有订单和待付款草稿快照。旧报价发生冲突时需重新确认。同一账号通过“交易订单”发货，通过“售后工单”审批；没有专员或人员管理入口。

三家初始化商店已准备当前有效政策和真实检索索引。**新建第四家商店仍需受控导入政策并建立索引**；当前页面只提示政策待准备，没有开放自助政策发布。平台创建商家是最小开通能力，不是公开商家入驻申请/审核系统。

## 再次清空

仅在你明确想放弃后来产生的本地演示记录时执行：

```powershell
.\demo.ps1 reset -ClearDemoData
```

命令停止所属应用，检查固定隔离项目，备份后重建基础环境并以不调用收费模型的模式启动。重建属于维护操作；完成后先`.\stop.ps1`，再`.\start.ps1`，恢复全部功能。

备份保存在`tmp/reviewer-demo/backups/<时间>/`，含数据库、旧消息和运行资料、校验清单及恢复说明；不提交Git。正常`start`不清空。`verify`在新基础环境用于核验**初始空白基准**，手动产生交易后不再满足空白条件，日常查看服务用`status`。

本次清理前的原数据备份是`tmp/reviewer-demo/backups/20261003-104641-179070`，后续验收重建的备份不替代这份原备份。共享开发环境、源码、历史提交和历史报告保留。
