## 读取与上下文

复用五个只读工具，不增加服务、模型权限或固定取证路线。`get_order_context` 仍读取绑定订单行的 Commerce `/internal/v1/order-lines/{line_id}/context`。一个 SQL 同时连接订单行、实际 payment_ledger、行退款槽和 order_fulfillment，新增可选 `payment_version`、`fulfillment_status`、`fulfillment_version`。履约仅来自明确主记录；历史没有该记录就省略，不能从物流 NOT_FOUND 推断 NOT_SHIPPED。模拟付款原本已经创建 NOT_SHIPPED 的行物流及 ORDER_PAID 事件，本批不重复生成。

OpenAPI core、Java生产/消费类型、共享fixture和测试同步。旧构造器保留兼容测试/历史适配，MyBatis明确使用完整构造器。旧协议文件和已执行迁移不改。

新 Observation source_version 合成 `order-{行版本}:payment-{账本版本}:fulfillment-{履约版本或missing}`，极长组合用SHA256满足64字符上限；content_hash仍覆盖完整原始响应。身份来源地址不变。缺失组件明确missing，绝不伪造版本。旧响应没有新字段仍使用原行版本，旧已存Observation不改。

P2精确保留付款时间/金额/CNY、实际 `order_status`、付款/履约版本、整单实付/已退/预留及当前行槽，P3去除同一保护事实的重复，原文可以读回。修正旧抽取把真实 order_status 当 status 的偏差，status仅兼容旧Observation。新manifest版本阻止旧run静默套用新规则恢复。

## 结论检查

模型仍自主选择下一行动，以下仅控制终止建议，不自动发起工具、不代替语义判断：

- 引用 `R-UNSHIPPED-001` 退款：须引用最新成功订单Observation；PAID、付款时间、CNY正整数实付及实际账本版本齐全，明确NOT_SHIPPED/版本1，行槽FREE且订单剩余金额覆盖本行全部实付。已读取但冲突/失败的物流和占用退款槽不能通过省略引用被隐藏。
- 后读的新状态或失败刷新使同源旧订单不能继续作为当前依据；历史原文仍在。没读过物流并不阻止有明确付款/履约依据的未发货建议。
- 未发货条款是正向退款资格；已经发货只说明本条款不适用，不能据此拒绝整个申请。应继续检索其他适用条款或转人工。引用这个条款的REJECT被拦截。
- 其他REJECT保留上一批保守门槛：真实引用、检索过的政策、当前订单及已知物流、没有自报缺证。此门槛不宣称已覆盖损坏/签收的所有语义或人工核验条件。
- REFUND仍必须有引用且不能同时缺证；Java重新计算金额、核对本案例商家/客户、当前政策和未发货行事件，并由商家独立审批。Python结果不授予执行权限，UNKNOWN及幂等边界沿用。
