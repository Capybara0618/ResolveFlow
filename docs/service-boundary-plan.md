# 商城与售后服务边界调整

2026-11-02，用户批准按本轮架构讨论实施。本文规定目标与分步验收；实际执行状态只记录在 `tasks/todo.md` 顶部。

## 目标

保留 Gateway、Case、Commerce 三个 Java 进程及唯一 Python Agent，不更换依赖锁、不迁移已有交易数据。Gateway 按明确公共接口分流；Commerce 拥有商城公共 API 与资源授权，Case 拥有咨询、工单、材料、审批与授权。Case 按需读取交易事实，退款继续沿用 MQ、Outbox/Inbox 与 Commerce 资金约束。

账户、会话、主体绑定、资料与地址作为独立逻辑能力，暂部署在 Case。其他服务通过受保护的内部协议使用，不直接读取 Case 数据库；用户 JWT 与服务 JWT 不混用。实时身份校验仍依赖该进程时，不宣称受保护交易已经实现 Case 故障隔离。账号停用、身份版本及旧会话失效语义保持，不能以只验 JWT 签名替代。

## 实施顺序与验收

1. 公共目录：商品/店铺列表与详情、展示资料、公开评价、无写入报价直接进入 Commerce。保持 URL、请求与响应结构；只开放明确方法/路径，不把 `/internal/**` 整体暴露。验证 Case 不参与目录请求、身份伪造头移除、错误语义、私有入口和 SSE 不受影响。
2. 认证与交易：先定义当前会话、可信主体范围及地址快照的内部协议，验证无凭证、用户/服务身份混用、停用、旧版本和上游失败；再迁移购物车、下单、付款、订单、评价与商家交易接口。Commerce 自己匹配资源归属，身份服务不代读交易数据，外部网络不进入长事务。
3. 清理与集中验收：移除失去用途的 Case 商城转发代码；保留真正的售后聚合与兼容所需内部客户端。同步契约、启动接线与架构说明，验证购物与售后原链路。

每个独立小步先关键失败测试，验证通过后中文提交并普通推送；不等待整包完成。依赖未解的接口保持原路径，不提前切流。

## 已核实的迁移依赖

- `CoreRoutes` 当前将整个 `/api/v1/**` 发送到 Case。
- Case `RequestPrincipalResolver` 不仅验 JWT，还读取持久账号与身份版本；`BuyerScopes` 提供有效商家绑定。
- Case `PresentationController` 保存商品图片文件及归属，Commerce 保存商品图片引用与发布状态。目录数据可先直达 Commerce，图片字节入口暂保留 Case，不能把已有图片误当 Commerce 本地文件。
- 跨店列表的分页、游标绑定和归并现位于 Case，迁移须保留完整语义。

原退款不变量、授权消费前后边界、Agent 权限、运行 fence、历史数据及冻结评测保持。此批不新增模型调用、收费评测或公网部署。
