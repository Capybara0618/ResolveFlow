# 售后客服 Agent 调研与 ResolveFlow 设计建议

调研日期：2026-10-09。用户要求先学习客服 Agent 的公开经验，再逐步设计 Agent/RAG 重构。本文是资料核查及设计建议，不代表功能已实现、框架已实测或实验假设已成立。执行进度仅维护在 [todo 顶部](../tasks/todo.md)。

## 1. 结论与当前入口

已有框架覆盖对话状态、知识检索、工具调用和人工接续；真实业务效果仍取决于数据、工具语义、对话处理和评测。ResolveFlow 继续使用 AgentScope 2.0.8 唯一生产循环，学习其他项目的机制，不启动框架替换。

用户最新入口决定覆盖此前“从订单行进入”的选择：打开售后聊天窗口 → 后端展示本人订单 → 用户选择具体订单商品 → 自然语言咨询 → 按需创建或接续售后案件。近期订单优先，同时可查看已收货订单、全部订单及已有售后。最终处理对象是订单行。

业务沿用 [core-scope](core-scope.md)：单订单行全量模拟退款、物流异常、商品损坏及人工核验。咨询与创建工单的衔接属于待设计能力；图片理解、补发、库存、真实支付及完整客服平台仍未纳入本轮。

### 2.1 对话自然性与业务流程可以结合

Rasa 的[官方课程](https://learning.rasa.com/rasa-pro/introduction-to-calm/)将业务逻辑、对话理解和对话修复分开。其[对话修复课程](https://learning.rasa.com/rasa-pro/deviations-from-happypath/)覆盖用户纠正、插入其他话题、澄清及人工接手。示例 [patterns.yml](https://github.com/RasaHQ/rasa-calm-demo/blob/main/data/flows/patterns.yml)提供 correction、clarification 等实际配置。

项目建议：描述办理所需条件，并允许用户自由提供、修改或插入信息。不要把“固定流程”理解成只能按固定问法逐项填表；对照组可以具有明确分支、跳过已知信息及基本对话修复。动态 Agent 的价值要在这种合理基线下验证。

### 2.2 会话状态不能只靠完整聊天记录

Dify 的[Variable Assigner](https://docs.dify.ai/en/cloud/use-dify/nodes/variable-assigner)区分跨轮会话变量与单次执行变量。ResolveFlow 已有 [FactsView](../agent/src/resolveflow/harness/facts.py) 和 [ContextBuilder](../agent/src/resolveflow/harness/context.py)，可以复用事实及来源记录，再设计会话目标、问题与回答关联、未完成事项。

项目建议：conversation 表达用户当前咨询；case 表达正式售后案件；run 表达一次调查执行。三者是待定义的职责关系，不预先规定新增三张表或三套服务。用户纠正其陈述，应保留旧记录及新说法，不修改系统订单、物流事实；咨询结束也不等于退款完成。

### 2.3 多轮 RAG 先解决问题理解，再比较排序

Dify 的[检索节点](https://docs.dify.ai/en/cloud/use-dify/nodes/knowledge-retrieval)明确区分查询、知识库、检索设置和元数据过滤。[Flowise Agentic RAG 教程](https://docs.flowiseai.com/tutorials/agentic-rag)展示结合问题与历史生成查询、检查相关性并在需要时重新检索。RAGFlow 则可作为文档切分与引用定位的参考。

项目建议：保存用户原话与实际搜索 query；把“那超过时间呢？”解析为当前商品/售后原因对应的期限问题。查政策走 RAG，查订单/物流/退款事实走业务工具。以必要条件及例外是否覆盖判断补查需求，不能只把相似度当充分依据。初步检索后仍缺条件时允许有界补查；问题清楚且依据齐全时直接回答。不同机制分别比较，不预设重排或多轮检索一定更优。

### 2.4 人工接续也是任务结果

[Chatwoot 仓库](https://github.com/chatwoot/chatwoot)是客服界面和订单关联的参考。[Flowise Agentflow 文档](https://docs.flowiseai.com/using-flowise/agentflowv2)描述等待人工输入与持久状态接续。ResolveFlow 已有问题/回答及商家审批链路，可在其上组织交接内容。

项目建议：交给商家的信息包含诉求、已查事实、用户回答、政策依据、缺口及下一步。当前必须人工核验的案件，以“完成调查并形成可用交接”评价 Agent 阶段；商家审批及模拟退款结果另行评价。可以独立解决的咨询被无理由转人工，不算完成。

## 3. 最值得学习的评测方式

### 3.1 τ-Bench：参考路径不等于唯一正确路径

实际阅读了[领域结构](https://github.com/sierra-research/tau2-bench/blob/main/src/tau2/domains/README.md)和[评测说明](https://github.com/sierra-research/tau2-bench/blob/main/docs/evaluation.md)。领域将工具、环境、用户数据、任务与政策分开。标准 retail 等领域用参考动作推导目标业务状态，允许其他动作序列产生相同结果；个别知识任务另有动作约束。

本项目不能直接照抄数据库 hash 评分：咨询答案、调查依据和人工交接都需要验收。建议同时检查当前案件状态/合法副作用、回答或建议的事实与政策依据、必要交接内容；具体轨迹用于解释成本和失败。已有退款故障测试继续负责模拟退款执行验收。

### 3.2 生产经验：模块化上下文与评测驱动迭代

2026-06 的 Nubank [研究论文](https://arxiv.org/html/2606.08867v2)描述客服指令、办理指引、工具说明及工作记忆的模块化组织，并通过明确评分标准、评判一致性和线上验证连接迭代。论文也指出只把难例交给人工会影响自动处理率与满意度的关系。

本项目借鉴：分别调整和比较组件，给自动判定项与语义复核项明确口径。合成数据上的评分不能称真实客户满意度，模型评价也不等于独立人工标注；无需复制其线上规模或训练体系。

### 3.3 AgentScope 的追问示例

官方样例中的[chatbot](https://github.com/agentscope-ai/agentscope-samples/tree/main/conversational_agents/chatbot)展示带工具的 ReAct 多轮对话。[Learn2Ask README](https://raw.githubusercontent.com/agentscope-ai/agentscope-samples/main/tuner/learn_to_ask/README.md)是医疗追问训练例，不是售后框架；其学习目标区分是否继续提问与问题的信息覆盖。

本项目只借鉴评测拆分：已经充分时及时停止，缺信息时问到必要内容。当前不引入训练、医疗数据、Tuner 或 Runtime；样例 main 分支也没有核验与本地锁定 SDK 的兼容性。

## 4. 对我们此前设计的具体调整

1. 场景清单之外，增加对话行为维度：一次提供多个信息、含糊回答、纠正、插问、恢复原话题、已有材料及进度跟进。
2. 先设计咨询会话与正式工单的衔接，避免政策咨询一开始就生成退款工单。用户选择订单行只建立服务对象；不自动表示申请退款。
3. 固定流程基线允许分支和基本对话修复；动态组在同一业务环境中选择调查行动。自然语言入口对两组一致。
4. 数据构造先定义完整案件，再将信息分配给用户、工具和商家；用户回答规则能处理等价问题，而非只认固定关键词。工具条件及用户可见信息对两组相同。
5. 会话修复与业务证据补充分别定义。询问一句话的含义不必自动消耗现有两轮工单补证次数，但具体计数及状态衔接需要在实现规格中明确，不能直接放宽旧约束。
6. 政策咨询、调查阶段、人工审批、退款执行使用各自的完成条件；因读取失败停止不能直接包装成有效人工交接。

以上是建议，未冻结新功能范围、数据规模、测试阈值、字段或接口。用户最新入口已经确认；其余按讨论逐步收敛。

## 5. 候选实验与简历指标

| 要验证的问题 | 最小对照思路 | 数据需要什么 | 候选主指标 |
| --- | --- | --- | --- |
| 动态调查是否值得 | 合理分支流程 vs 单 Agent，模型/工具/RAG/信息规则相同 | 简单与交互案件并存；初始信息充分与缺失配对 | 按任务类型统计完成率及差异，同时报告总体请求/token/耗时 |
| 对话修复能否改善接续 | 当前策略 vs 显式维护目标、修正与未完成事项 | 含纠正/插问/返回原问题的独立变体；同一案件整体归入同一数据划分 | 新信息处理正确率、重复询问率、必要信息覆盖率 |
| 多轮检索是否改善依据 | 同一检索器下单次检索 vs 按需补查；排序比较另做 | 条件/期限/例外跨片段；自然追问、依据充分和无答案样本 | 必要依据完整率、政策适用正确率、检索次数和延迟 |
| 人工接手是否有用 | 当前摘要 vs 结构化交接 | 本就需要人工的损坏/签收争议及真正读取失败 | 必要交接信息完整率；失败恢复情况与有效交接分开 |

重复询问按已提供且仍有效的信息判定，必要确认及状态变化后的更新读取另列。必要信息覆盖只统计影响该任务完成的事实，避免以提问数量奖励冗长调查。外部政策文档仍用于独立 RAG 实验，商家采用条款必须明确来源/版本，不能自动把外部政策变成业务承诺。

实验样本、预期结果及可接受替代路径在运行前定义；开发与正式评测分开。先做小样例检查任务可解性和评分口径，后续真实模型运行范围另由用户确定。这里没有预设提升百分比，现有[正式 Agent 对照](../reports/resume-quantification-v1/agent/README.md)及原失败/报告保持。

## 6. 下一步讨论材料

先定义六类候选任务（政策咨询、未发货退款、物流异常、签收争议、商品损坏、已有售后跟进）与上述对话行为的代表性交叉，不建立全组合工程矩阵。每个样例写清初始表达、完整事实、信息分布、可接受结果和测量口径；再画入口/咨询/办理/接续预期图，最后推导实现计划。

当前仓库已有事实/来源、唯一 SDK 循环、五 MCP、问题回答、新 revision、新 run、人工核验/审批及退款执行，继续复用。优先讨论新增咨询会话的职责、对话修复与补证的关系、完整任务评分；不立即开发多 Agent、通用客服平台或重复迁移。
