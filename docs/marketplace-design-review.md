# 多商家购物上游：参照审查与设计修正

日期：2026-10-03。用户明确要求同一个买家可以买多家商家的商品。本文件取代[原单店铺上游草案](upstream-commerce-plan.md)作为下一轮设计依据；多商家方向已明确，下面的功能深度和实施批次是供用户审查的建议，不代表接口已经实现。既有售后五批成果继续复用，完成情况只看[todo顶部](../tasks/todo.md)。

后续用户已授权生成整套多商家预期图，交付[图册](ui-marketplace-v1/index.html)及[图文合同](ui-marketplace-v1/README.md)，13个选定视图包含两处导航校正。下面第5节关于5张单店铺图的暂停记录是历史；新图册已生成供集中审查，上游功能仍未实施。

## 1．先纠正产品模型

此前“客户绑定一个商家、只看本店、固定买一件、不需要购物车”的建议过度沿用了现有售后演示身份。这会让购物入口变成单店订单生成器，无法呈现平台购物体验。不是换几张商品图就能解决，需要先区分买家身份与商家工作范围。

新的目标是：**一个平台买家账号，浏览多商家商品、购买不同店铺、统一查看本人订单与售后；每个商家只处理自己的交易、政策和工单。** 保留 ResolveFlow 的售后调查 Agent 与可靠模拟退款作为核心，增加可用的购物上游，仍是桌面网页个人项目，不扩成完整电商运营平台。

| 主体或资源 | 新设计要求 |
| --- | --- |
| 平台买家 | 不固定归属于一家商家；同一登录可向 A、B 两店购买，只能查看自己的私有交易和申请 |
| 商家及店铺 | 商品、订单、政策和工作人员各自归属一个商家；首批继续使用两个受控演示商家 |
| 售后专员、商家管理员 | 仍固定在本商家工作；管理员是商家管理员，不因此获得全平台用户或订单权限 |
| 订单与工单 | 一个商家订单归属一个商家与一个买家；工单由订单行确定对应商家，不由前端切换店铺指定 |
| Agent / RAG | 每次调查仍限定该工单的订单、商家政策和有效版本；不能浏览买家的其他店铺交易 |

同一买家可向多店购买，同一店也有多个买家，这构成购买关系上的多对多。每笔商家订单、每个工单的归属仍明确，不把多对多实现为跨商家共享审核队列。

## 2．实际参考了什么，以及没有验证什么

2026-10-03查阅可公开访问的京东官方购物、订单及售后资料，尝试访问京东、天猫桌面首页。首页遇到重定向或加载超时，没有登录、真实下单，也没有实测登录后的完整交互。因此以下是已核实的公开业务参照与本项目的设计判断，不能当成当前京东/天猫完整界面的复刻评测。

| 官方参考 | 可用于本项目的结论 | 证据限制 |
| --- | --- | --- |
| [京东：如何购买下单](https://help.jd.com/user/issue/34-18.html) | 商品选择、购物车、数量调整、核对订单、提交、订单中心构成连贯流程 | 页面标注2016-01-26；参考业务结构，不把旧截图当成2026年的视觉规范 |
| [京东：订单为什么会被拆分](https://help.jd.com/user/issue/57-127.html) | 发货方等不同会导致订单拆分；平台购物与商家订单是两个层次 | 页面标注2018-11-14；不是本项目跨店支付或拆单事务的现成实现方案 |
| [京东自助服务](https://help.jd.com/user/service.html) | 订单查询、售后申请及售后进度应有清楚入口 | 公开帮助入口，未验证登录后所有状态 |
| [京东售后政策](https://myjd.jd.com/afs/help/afshelp.action) | 自营与第三方卖家有不同售后入口及规则；不能把所有卖家政策混成一份 | 公开页面有历史样式，仅参考卖家责任和规则分界 |

上述来源没有被用来证明本项目已具备购物能力。多商家平台身份是根据用户需求作出的产品决定；以下的简化方案、字号、页面布局和开发顺序是我们的建议。

## 3．哪些保留，哪些简化，哪些暂不做

| 模块 | 决定 | 本项目落地边界 |
| --- | --- | --- |
| 多商家商城首页、商品搜索及分类 | 必须保留 | 汇集已启用店铺的上架商品；关键词、类别、价格排序即可，不加推荐算法或搜索集群 |
| 商品详情与商家店铺页 | 必须保留 | 看清商品、规格、价格、购买数量和销售店铺；可进入该店继续浏览 |
| 商品数量 | 保留 | 使用数量选择器，服务端设置明确上限；不再无业务理由固定为1。退款仍按选中订单行全量，不做行内部分数量退款 |
| 购物车 | 纳入目标设计，分批实现 | 同一买家可保存多店商品，按店铺分组、增减数量、移除；首版按一家店铺结算，不做跨店一次付款 |
| 立即购买 | 保留 | 使用同一报价、草稿、支付和订单发布路径，不能另造一套简化账本 |
| 确认订单与收货信息 | 简化后保留 | 显示本次店铺、各行商品、数量、服务端总价；使用明确标记的合成收货信息，不要求输入真实个人地址 |
| 支付、发货及物流 | 模拟实现 | 持久模拟付款、一次受控模拟发货、可读轨迹；不接第三方支付或真实快递，不重复塞模拟提示到每个角落 |
| 统一个人订单中心 | 必须保留 | 一次登录看到本人在各店的订单，按状态及店铺筛选；显著显示每单店铺，不要求重新登录另一个商家账号 |
| 售后申请、进度和结果 | 保留并衔接现有 | 从具体订单行发起退款，沿用补证、Agent建议、人工审批和模拟退款；个人列表汇集自己的各店申请 |
| 已付未发货退款 | 需要补齐业务规格 | 常见交易阶段不能直接跳过；设计保留申请入口，实施前追加相应政策及资格规则，仍走已有人工审批和资金执行，不伪造物流丢失依据 |
| 商家交易订单与发货工作区 | 保留 | 本商家订单列表、详情及模拟发货；售后作业仍遵守负责人和审批权限 |
| 商品运营后台 | 暂缓 | 先受控种子商品及上架状态；绘图不放未承诺实现的批量运营、营销配置按钮 |
| 优惠券、积分、会员、秒杀、拼团、金融、广告流 | 暂不做 | 去掉这些功能及入口，保持主要流程清晰 |
| 库存扣减、采购入库、真实退货换货 | 暂不做 | 不展示可用库存、抢购成功、已入库等假事实；仍明确是模拟履约与退款 |
| 跨店合并付款、优惠分摊、商家结算 | 暂缓 | 本阶段没有平台总订单或跨店支付事务；买家可分别向不同店铺结算，统一查看订单 |
| 平台运营超级管理员、商家自助入驻 | 暂不做 | 两个演示店铺足以验证多商家购物和商家隔离；不新增企业平台角色体系 |

购物车可以有 A 店和 B 店的商品，但结算动作明确属于一家店铺，未结算店铺的条目继续留在车中。不要放一个跨店“全选支付”按钮再在后台偷偷只结算一店。完整跨店合并付款可以后续独立扩展，不能借当前退款账本强行实现。

单店一次结算多种商品是目标建议，需要核对多行订单退款规则后实施。现有表允许多行，不代表业务已经支持“另一行已退款后继续申请”“多行同时预留”。如果当前资格限制不允许，先补正式规格与回归，不能删约束或把整单退款状态覆盖成某一行的状态来凑图。

## 4．网页应怎样长，如何避免小字堆积

商城浏览区采用顶部品牌、搜索、购物车和个人入口，下面是分类筛选与商品卡片。首页可同时展示 A、B 店商品，商品卡保留图片、商品名、价格、店铺四项主要信息；不套用售后工作台的左侧管理菜单，不加大面积营销轮播或密集标签。

商品详情突出商品图、名称、规格、价格、数量和购买按钮；店铺及退款政策有明确入口。购物车以店铺分组，确认订单突出收货信息与待购行。个人订单与售后可用账户侧栏，商家工作区继续用现有后台布局。

正式网页正文、表单、状态和操作文字建议16–18px，主标题28–36px，关键金额24–32px；关键事实不低于16px。预期图按画布比例放大，最终仍须在1280/1440/1680桌面视口检查，不能用缩小整页掩盖溢出。

长编号、技术时间戳、hash和调查内部版本进入详情展开区；重复说明删去，次要字段按需展开。模拟环境说明在页面顶部清楚出现一次，支付操作附近保留必要的模拟付款标签。错误、金额、卖家、政策依据和真实状态不能被当成装饰小字删掉。可读性通过信息取舍和层级实现。

## 6．现有系统怎样接通，而不是绕开权限

源码核对确认：[AuthenticatedPrincipal](../java/shared-kernel/src/main/java/com/resolveflow/shared/security/AuthenticatedPrincipal.java)要求所有角色携带merchantId；[V19身份迁移](../java/case-service/src/main/resources/db/migration/V19__persistent_identity.sql)也将账号固定到商家。因此同一平台买家的设计需要真实身份与权限改造，前端增加“切换店铺”按钮不够。

建议区分平台买家身份和商家工作人员身份。旧商家身份约束继续保护工作人员；新买家读取私有订单时，服务端验证实际订单所有人，再由订单解析商家作用域用于内部调用。商品公共目录可以跨店查询，不等于订单、工单、人员或政策原文都可跨店读取。请求体的merchant/customer不是认证授权来源，不使用通配租户令牌，不取消所有查询的商家过滤。

迁移采用追加方式，保留原账号、密码hash、启停及身份版本、历史订单/工单/actor。不能假定不同商家的customer_id全局唯一，也不能凭相同显示名合并客户。应定义平台买家ID与原(merchant_id, customer_id)的可信映射，核对历史归属；关联只能由受控迁移或已认证流程建立，不能允许客户端认领任意旧客户。旧演示账号不自动合并，另准备一个明确授权购买两店的新演示买家。工作人员的本商家账号管理不得获得全平台买家停用/重置密码权限。

Commerce继续拥有商品、购物车、草稿、交易、支付与模拟物流；Case持有账号与工单并提供已验证身份的交易门面；Python调查和现有AgentScope循环保持。公共目录只返回已上架公共字段，私有交易写入口仍需要精确主体与服务权限。沿用三个Java进程，不加新的库存、营销或平台管理服务。

原[Commerce V1](../java/commerce-service/src/main/resources/db/migration/V1__commerce_order_read_model.sql)中订单与行paid_at非空。未支付单用新草稿表示；模拟支付成功在同一Commerce本地事务写草稿结果、付款尝试、原已支付订单与各行、总额账本及各行FREE退款槽。多行金额之和必须等于账本支付额，不能先显示成功后补账本。复用原幂等、整数分、并发锁序和退款执行路径，草稿不得伪造支付时间混入旧表。

新工单仍从权威订单行读取商家、客户、实付和支付时间，按该商家政策钉版本。补证、调查引用、人工归属、授权消费、UNKNOWN同operation及行最多一次成功退款保持；买家跨店订单汇总不扩大Agent权限。已支付未发货的取消原因需要新增正确政策覆盖，不能修改既有政策版本/历史manifest。新支付日期同样要核对政策有效期。

## 7．建议实施依赖与本轮核验

先依据本稿审查功能深度与图文合同，再修正式规格和范围文件；不直接根据历史单店铺草案开工。

1. 平台买家身份与可信历史映射：同一账号能查看本人在两店的交易，商家工作人员权限不扩大；保留旧账号/订单，验证横向越权及人员管理边界。
2. 多商家商品与直接购买：全站目录、店铺、商品详情、数量、服务端报价与草稿；保留从一件单行开始的可运行切片，不把它当最终商城范围。
3. 模拟支付与个人订单：原子发布原资金模型、到期/取消/响应未知；新订单进入统一个人中心，金额和归属服务端确定。
4. 购物车与单店多行结算：按店分组、每店独立下单；重点验证各行退款并发与订单总资金上限，以及另一行退款后剩余行资格，不能只验购物车增删。
5. 模拟履约与售后衔接：商家只发自己订单、持久不可随意改的合成轨迹、适配未发货退款政策和当前日期；复用现有客户/专员/管理员流程。
6. 正式网页集中验收：同一买家购A/B、A专员看不到B工单、各自政策与退款正确、个人结果统一可见；保留历史数据，mock/live分别报告。

本轮只有公开资料核对、源码只读核对及设计文档修正；未实施上述批次、运行迁移、修改运行数据或重跑业务测试。执行本地Markdown链接与`git diff --check`核验，实际结果记录于todo顶部；已存在的业务通过记录不计作本轮验证。Git精确提交并普通push，原工作区历史工程/verify/Commerce测试及日志不夹带。
