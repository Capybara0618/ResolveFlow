# 首场景规格 v1：物流异常与签收争议

2026-10-20。依据[双端/多租户设计](customer-agent-multitenant-v0.md)及用户已确定的入口、人工咨询、确认退款和商家工作台方式。本文定义预期行为与验收，不代表客服功能已实现。真实模拟物流样本见[运行报告](../reports/customer-agent-design-v1/README.md)；进度只看[todo顶部](../tasks/todo.md)。

## 1. 入口、任务与来源

用户打开售后窗口，看到本人跨店订单，选择具体商品进入/恢复独立咨询。顶部持续展示店铺、商品、数量、实付和实际物流状态；切换商品保留各自历史。订单归属由后端确认。

当前支持咨询订单物流、解释适用政策、核查未收到/异常、提交人工咨询、确认退款申请及接续处理；本场景不增加真实快递联络、承诺到账/送达时间、补发/退货入库或图片核验。用户不需要先选“物流/退款”菜单，诉求可以在聊天中变化。

| 信息 | 来源与使用方式 |
| --- | --- |
| 商品/实付/已退款与占用 | 当前订单/行只读工具；历史商品快照不被目录改价覆盖 |
| 物流结论与节点 | Commerce模拟物流，source_version及事件时间可追溯；查询503与UNKNOWN是不同结果 |
| 未收到/代收/后来收到 | 客户原文及其补充/纠正，不自动当作承运商或商家核验结论 |
| 退款/人工核验条件 | 本商家按订单支付时间适用的政策版本与原文；已建Case使用其绑定版本 |
| 核查结果/补充问题 | 商家明确提交的记录；Agent整理不能冒充商家回复 |

7个已创建样本只提供物流/交易事实。签收争议中的“未收到”、人工核查内容和示例回复均为后续开发样例，不写成已发生事实。

## 2. 办理指引

指引规定任务目标及需要的依据，不固定完整工具顺序。Agent根据客户当前问题和Observation决定下一动作。

| 情况 | 办理目标 | 不足信息与下一步 |
| --- | --- | --- |
| 仅问物流 | 说明最新可得状态及必要节点 | 工具已能查询的订单号/付款/物流字段不重复问客户；不强制查退款政策 |
| 报告延迟 | 区分异常延迟、长时间无节点、明确丢失 | 只有IN_TRANSIT/DELAYED不能声称LOST；政策没有阈值时不自创“三天可退” |
| 明确LOST且无签收 | 解释适用退款条件，客户希望申请时准备摘要 | 保留人工审批及当前金额/资格复核，客户确认前不创建退款工单 |
| 有签收，客户否认收到 | 保留冲突，整理需要商家核查的事项 | 不因签收直接认定客户亲收，也不因客户否认直接退款；是否补问取决于已知信息与政策，非固定“问家人/驿站”脚本 |
| UNKNOWN/记录缺失 | 说明尚无明确结论，必要时人工核查 | 缺失系统字段由系统/商家补查，不能要求客户提供数据库字段或证明系统故障 |
| 查询503 | 说明当前查询暂不可用，按既有预算有限重试/接续 | 不把503说成包裹未知/丢失；已保存旧事实可说明其时间，不称最新状态 |

客户提出插问时回答当前问题，保留原任务及已知信息。客户纠正情况后更新当前诉求，保留前后陈述的来源；未确认的旧申请摘要作废/需重新生成。新消息到达时，旧生成结果不能发布到另一订单或冒充针对最新输入的回复。

## 3. 三条用户路径

### 普通咨询

直接得到有依据的回答即可结束本次问题。用户可继续询问，未提交的咨询只属于本人；不自动生成商家待办或退款申请。

### 人工咨询

用户明确要求人工，或接受Agent提出的商家核查建议后，展示转交卡片：当前商品/店铺、问题摘要、已查事实、待核查事项、将共享的客户材料与相关原文范围。用户可以修改摘要、补充材料并点击“转交商家”；无需选择退款金额/原因。已授权共享的记录形成快照，后续增补单独记录。

提交咨询核查单后，商家在本店工作台接续；客户在原会话看到待处理/处理中/待补充/已回复/已解决等明确状态。这里是业务状态草案，字段与枚举在契约设计冻结。

商家回复、补充问题与核查结论带明确作者。已回复不等于已解决：建议客户确认问题解决后结束，客户继续追问则接续同单；第一版不自动超时关闭或承诺客服在线时间。咨询补充不套用原退款工单“两轮补证”规则。

等待商家时输入区默认“补充给商家”，已发送内容进入该咨询单；同时允许显式切到“询问智能助手”，处理进度/政策问答仍可进行。两种接收方在输入区可见，防止客户不知道消息给了谁；具体布局以[图文合同](ui-customer-agent-v1/README.md)为准。

### 退款申请

用户明确希望退款，展示商品/整行数量/本行实付/当前申请诉求及材料摘要，客户确认后调用实际Case创建/接续。提交卡片显示“申请退款”，不是“确认退款成功”。已有适用退款工单优先接续，避免为同一请求重复建单。

直接申请退款可进入原Case调查/商家审核，不必须先创建咨询核查单。人工咨询后再希望退款时另行确认，建立咨询单与退款Case关联，复用有效材料并重查会变化的事实。商家一句“可以申请”不自动代客户提交。

## 4. 商家体验

现有工作台提供“咨询核查/退款申请”两类待办，仍为每店一个商家账号；当前商家不设置Agent聊天窗口。

案件详情先展示客户诉求及下一步，随后展示客户共享原文、系统事实、适用政策与Agent建议；事实、客户陈述、Agent整理和人工核验分栏/标识，依据可以展开定位。商家不默认看到客户未共享的全部咨询或其他店订单。

咨询核查可记录核查结果、回复客户、要求补充信息、标记已回复；退款申请继续原核验/方案/审批/执行。审批通过、退款执行中和执行成功分别显示。案件发生新补充或事实变化时，旧建议明确标为需要重新核查。

## 5. RAG与多租户

先用本店适用规则组织完整条件/例外，再讨论检索算法。首场景重点为现有合成政策R-INTRANSIT-001、R-LOST-001、R-SIGNED-001及R-MONEY-001；来源是[本店基础政策](../fixtures/demo-foundation/policies/policy-foundation-m1001-2026.10.yaml)及[B店版本](../fixtures/demo-foundation/policies/policy-foundation-m1002-2026.10.yaml)，正式输入仍通过后端选择/绑定，不能按文档中的ID硬编码工具路径。

“那能退款吗”应结合当前签收争议生成检索问题，保留客户否认收到的关系；不得改写成客户已亲收。召回前限定商家/政策版本与manifest，回复展示与结论有关的政策出处。两店当前核心规则相似，不为了展示差异修改政策或假称两店规则相反。

相同买家可看到两店本人订单列表；每个咨询只读所选订单行、当前店政策与相关售后。切换B商品后，A的摘要和异步结果不能写入B；Agent运行上下文独立，执行框架和模型客户端可共享。

## 6. 样例与评分

[12个开发样例](../evals/customer-agent-v1/dev-dialogues.json)绑定7个真实模拟样本，示例中的自然语言为预期客户输入/行为，不是实测客服日志。它们用于开发、界面状态和调试，不作为留出测试宣称泛化提升；后续正式评测另冻结未用于开发的表述及业务变体。

| 指标 | 统计规则 |
| --- | --- |
| 任务完成率 | 每例所有必要条件满足且无禁止行为；按咨询/人工转交/退款/纠正与隔离分别报告分子分母 |
| 重复询问 | 再次索取已有效提供或可直接查询且仍有效的信息；必要的歧义澄清单独标注 |
| 纠正采纳/过时回复 | 纠正后回复与摘要采用最新有效诉求，不覆盖真实工具记录；生成期间新输入另验 |
| 政策完整与引用支撑 | 命中/回答包含所需条件和例外，结论能由当前店/版本的引用支持；单纯命中任意条款不算成功 |
| 人工接续 | 已实际创建/接续核查记录且商家可读；仅回复“已转人工”不算已提交。商家回复到客户会话另行验收 |
| 成本/体验 | 每任务模型请求/token与业务读次数、完整回复p50/p95；首个提示不当作完整回复 |

确定性字段、HTTP动作、归属与对象数量自动核对；解释与必要条件按评分表复核，不以模型自评代替全部事实验证。固定流程与动态Agent共用模型/RAG/业务事实，基线有合理分支及对话修复，预期提升由留出实验确定。

## 7. 接口设计之前的交付与边界

本轮交付场景规格、开发样例、运行样本及双端可切换预期图。页面状态、按钮与接收方在图文合同映射；原型不访问业务API，不会创建真实咨询单/退款单。

下一实施批次需冻结conversation/turn/support_ticket/case/run关系、共享原文快照、回复/补充/结束状态、未建Case咨询身份、事件回写及版本语义，然后按纵向链路实现。暂不把本规格中的任务/状态名直接加入现有OpenAPI枚举。
