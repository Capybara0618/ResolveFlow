## 1. 已确定的产品选择

- 打开售后聊天窗口，后端展示本人订单；用户选择具体订单商品后自然咨询。近期订单优先，同时能查已收货订单、全部订单及已有售后。
- 客户表达退款申请意图后，展示申请摘要，客户确认后才创建退款工单。单纯咨询/询问政策不自动创建退款工单；用户请求人工可转交独立咨询核查单，无需申请退款。
- 转人工接现有商家售后工作台；客户在会话中查看进度、补充材料。第一版不新增商家实时聊天产品。
- 换商品进入/恢复独立咨询，入口保留本人历史；客户转交前预览摘要和材料，商家仅取得相关交接及可追溯原文。
- 第一条完整链路为物流异常与签收争议，之后扩展其他场景，共用会话与 Agent 机制。
- 沿用 AgentScope 2.0.8、当前 Java 三进程、既有事实/政策/恢复机制；固定调查流程为 Agent 主对照，模型及 RAG 共用。RAG 检索主实验沿用外部原始政策文档，商城政策作业务补充验证。

## 2. 第一条链路的预期行为

入口是用户选中的订单行。Agent 根据客户诉求，读取所需订单/物流/已有售后，必要时检索适用政策；回答进度与规则、询问客户才能提供的缺失信息，或准备申请摘要/人工交接。不会要求客户逐次按预设顺序提供已经可查的信息。

| 场景 | 期望行为 | 结束依据 |
| --- | --- | --- |
| 仅问订单到哪了 | 查询当前物流并说明状态，信息够时直接回答 | 回答与工具事实一致，说明必要下一步；无申请意图则不建工单 |
| 长时间未更新/未送达 | 结合物流时间与适用政策解释，缺少客户可提供的关键事实再追问 | 完成解释，或准备符合条件的申请/交接；不编造承运商调查结论 |
| 系统显示签收，客户否认收到 | 同时保留签收记录和客户陈述，按业务规则补充必要信息或交商家核查 | 完成可追踪交接及问题摘要，不能把签收记录直接当作客户亲自收货证明 |
| 中途询问退款条件 | 回答政策问题，保留原诉求与已取得的信息，允许继续原问题 | 条件和例外有依据，恢复原问题时不重复索取已知信息 |
| 客户纠正“后来收到了” | 更新客户陈述及当前目标，重新判断还需不需要申请 | 客户可见回复跟随最新输入，未确认的旧申请摘要不继续提交 |
| 客户希望申请退款 | 展示订单商品、诉求、相关陈述和当前申请内容，确认后建/续工单 | 真实工单关联正确，后续审批和执行进度可查；聊天确认不等于退款审批 |
| 客户只希望人工核查 | 展示交接内容，提交/接续本店咨询核查单，商家从工作台回复 | 已有实际可追踪接续和回复入口；不强迫客户申请退款 |

上表不替代商家实际政策。资格与必要事实由现有适用政策和业务工具决定，不能按场景标签强行返回统一退款结论。签收争议允许正确转人工作为本任务的完成结果。

## 3. Agent 与业务职责

办理指引为每类任务提供目标、必需事实、可用工具、关键分支及结束条件。它不指定完整工具路径；Agent 根据 Observation 与客户消息决定查询、检索、澄清、回答或准备交接。

目标能力包括：直接回答、选择所需业务查询、检索政策、必要追问、准备申请摘要和交接说明。这里是职责描述，不表示这些动作已加入当前生产 ABI；正式协议设计须同步现有类型、fixture、生产者/消费者。

用户输入可一次给全、逐轮补充、插问及纠正。上下文区分订单/物流工具事实、客户原始陈述、模型整理与政策依据；保留来源和版本。切换订单行时使用独立咨询上下文，同一聊天入口可回看历史，具体会话归属规则在契约阶段细化。

Java 继续拥有咨询核查记录、退款工单、授权、金额和执行状态；Python 继续拥有 Agent 执行与调用结果。退款申请创建通过当前业务接口/校验，确认前展示摘要，已有活跃售后按当前业务规则接续；独立人工咨询需要新增非资金业务契约。人工回复与处理结果回到客户会话。

## 4. RAG 的作用与开发顺序

先组织可用知识：适用商家/版本、规则主题、条件、例外、原文位置及来源。订单进度等实时事实从工具读取；RAG 提供政策解释和办理依据。

检索输入由当前诉求、对话所指对象、工具取得的必要事实和适用政策范围构成。例如“已经签收，客户说没收到，是否需要核查或可以申请”应保留问题中的争议，不改写成“客户已收到”。仅问物流位置时，不为了展示 RAG 强制检索退款条款。

检索先沿用当前生产能力，检查客服问法能否命中完整条件和例外；外部原文检索比较与商城业务效果分别报告。BM25、dense、混合/RRF及重排可以作为后续受控候选，生产算法选择留到基线测量后，不在本草案声称已经部署或敲定新的收益。

## 5. 技术结构建议

建议在 Case Java 服务中持久保存咨询会话、消息、选中的订单行和工单关联，复用现有身份/订单查询。此建议尚未冻结数据表或接口。Redis只作按需缓存；会话记录和业务状态仍须持久化。

长期 conversation、当前 turn 和调查 run 分开。未建工单的咨询执行需要独立入口/身份契约，不伪造 case_id 来调用旧 run 协议，也不新增另一套独立 Agent 循环。正式案件的 revision、追问及恢复规则继续复用；咨询轮次不能直接套用案件“两轮补证”的额度含义。

新消息/纠正到达后，当前回复发布时检查是否仍基于有效输入；旧摘要确认时重查当前诉求和业务状态。已有 run fence 保护执行者权限，会话输入版本保护回复语义，两者不能混为同一个机制。

会话历史、客户可见消息、内部调查记录和工单审批分别组织；前端展示简短查询状态及最终回复，不把原始工具日志或模型内部推理当聊天内容。

## 6. 数据与验收草案

先定义结果标准，再编写开发样例。建议起步用12个开发对话，覆盖状态/诉求/表达方式交叉变化，再准备独立保留样例；数量在首个场景规格中确定。这些为合成业务对话，不是商用客服记录。

数据至少覆盖一次给全、分轮补充、插入政策问答、纠正事实、只咨询不申请、申请前改变主意。设计同话术不同业务状态、同事实不同表达的配对，避免只测试某一种固定问法。每例记录初始业务事实、客户可提供信息、正确政策范围、必要结论、允许的终点和不应出现的行为；不要求唯一工具顺序或原句答案。

| 指标 | 评分定义 |
| --- | --- |
| 当前任务完成率（Agent 主指标） | 是否满足该类任务的必要结论/实际动作；咨询、申请和人工交接分别设标准并分场景报告，不能用 run COMPLETED 代替 |
| 重复询问、客户需答轮次 | 是否再次索要已经有效提供/可查询的信息；必要澄清单独标注，不用越少越好作为唯一目标 |
| 纠正采纳与过时回复 | 回复和申请摘要是否使用当前事实、对象及诉求；生成期间补充消息另外检验 |
| 检索完整性与引用支撑（RAG 主指标） | 检索是否覆盖回答所需条件/例外，回复结论是否由引用支持；原文检索与商城回答分别评分 |
| 成本与体验 | 模型请求/token、业务读取次数、完整回复p50/p95；即时进度提示另计，不冒充完整答复 |

固定流程和动态 Agent 使用同模型、RAG及业务数据，基线有合理分支/基本对话修复。可确定字段/动作自动核对，解释与必要条件按评分表复核；首批复核规则写明，不只依赖模型自评。提升幅度由后续实测决定，数据构造用于检验假设，不以让 Agent 必胜为目的。

## 7. 进入开发的顺序与每步产物

1. **场景规格与样例**：完成物流异常/签收争议的事实清单、办理指引、政策依据、对话样例和评分标准，明确开发/保留样例边界。
2. **预期图**：画订单选择、持续聊天、申请摘要确认、人工处理进度/补充材料四类界面状态；标清触发行为和前后状态。
3. **契约与数据设计**：明确 conversation/turn/咨询核查单/case/run 关系、身份/订单绑定、消息/人工回复/申请确认接口、未建退款工单工具范围、新输入后的发布语义；再拆实际文件和迁移。
4. **最小纵向链路**：本人订单选择 → 持久会话 → 单 Agent 查询物流并回复 → 摘要确认 → 关联真实 Case → 现有商家处理 → 客户查看进度。按小步实现并验证，不整包重写。
5. **对话与检索完善**：基于首批样例完成补充/插问/纠正、政策检索和人工交接，再扩其他业务场景；首批工程验收通过后，明确真实模型验证范围。
6. **对照测量与文案**：固定配置运行留出样例，报告质量/成本/失败，再决定 RAG 候选及下一步改进。旧实验、Gold、简历数字保持原有归属，新功能实测后另写新报告。
