# 客服回答事实渲染 fields-v1

2026-10-24，用户批准修正事实标注与正文占位符重复表达的问题。范围仅客服回答协议、渲染和流式一致性；不改 AgentScope 主循环、RAG、退款确认/核验/资金权限。实际进度只看 tasks/todo.md 顶部。

## 协议

内部模型动作 ANSWER/ANSWER_PARTS 根级可声明 `fact_rendering: "fields-v1"`。各 part 的 `facts` 继续为 `{field, source}`，字段限 PAID_AMOUNT/ORDER_STATUS/SHIPMENT_STATUS/CARRIER_CONCLUSION，不接受模型 value。正文是解释，不能混用占位符；模型无需重复权威字段的值。程序按已读来源生成带标签的事实段落，并合并引用。无 facts 不增加事实段。

示例：`{"kind":"ANSWER_PARTS","fact_rendering":"fields-v1","parts":[{"task_id":"t1","status":"ANSWERED","text":"请结合记录进一步核验。","facts":[{"field":"SHIPMENT_STATUS","source":"O1"}]}]}`。若当前行来源状态为 LOST，最终正文为“请结合记录进一步核验。\n\n物流状态：丢失。”。中文标签由程序固定映射；未知合法字符串按来源原值显示，不猜测含义。承运结论不等于用户已认可收货或商家已确认退款。

没有 fact_rendering 的动作仍走原占位符协议，缺少对应占位符仍失败，不能自动把旧失败升级为新协议成功。未知版本拒绝。保留原候选、原始模型请求/响应、已完成结果；不更改旧 run 的 manifest、预算或结果。新代码/提示 hash 和显式协议版本进入新 run manifest；未完成旧 run 的 manifest 不匹配继续失败，不静默迁移。

## 校验与流式

重复 field、未读/错误类型/错误订单行/无版本/失败来源、字段缺失仍拒绝；金额仍取当前 ORDER 的整数分/CNY，正文具体金额校验保持。程序段落扩展后仍限每 part 4000 字/8引用。引用由既有绑定工具产生，租户/本人范围不由模型参数指定。

解释正文沿用现有候选流式通道；事实在完整动作通过来源检查后进入最终回答，固定追加到解释正文后，不在前缀插入。候选可撤回、最终发布仍走完整检查。页面操作继续由已有指南渲染器生成，纯办理段既有替换规则保持。不把候选首字计作正式答案完成时间。

这不是任意自然语言语义裁判：保留现有金额和发布检查，但不能据四字段渲染宣称所有自由解释或摘要均无幻觉。通过真实新样本单独核验用户体验。

## 验证顺序

先新格式红测，验证 LOST/IN_TRANSIT/DELIVERED、订单金额与商品价区分、单段/多段、错误来源/金额、重复字段/未知版本/混用占位符/扩展长度；原宏断言不删。再用保存的真实候选做只读离线诊断，原格式仍拒绝，新格式副本单独标记为协议迁移实验，不算真实模型成功。

同步实际提示与纠错反馈，验证 SDK 调用/修正次数不增加、退款摘要与指南引用保持；真实临时 PG + 模拟 SSE 验证解释前缀、最终事实、失败撤回、已完成 run 零新调用复用及 manifest 不匹配。通过后仅一笔新合成订单/一轮新客服问句作有限真实确认，单独保存失败和全部用量，不重发旧题追分，不自动进行退款调查或收费矩阵。
