# 客服 Agent 小规模真实验收

2026-10-24，用户批准执行：先主链路，通过后再检查三种变化。当前进度仅 tasks/todo.md 顶部。不更新简历或更换 RAG/框架/模型/预算；所有交易、物流与退款仍为本地合成模拟。

## A：自动退款摘要与确认

新建一笔本人已付款、已发货、承运结论LOST的329元订单。沿上轮同一句输入作修复确认（新订单/会话/run，不重放旧run，不算盲测）：

“耳机还没送到。我想核对一下承运商的记录，并准备一份退款原因；先让我查看和修改，再决定是否提交。”

真实浏览器发送一次，模型自主选工具，检查正式发布、实际SSE、订单/物流/指南来源、根级退款摘要字符串。网页草稿原因必须等于实际已发布摘要，金额来自Java；用户编辑保存并刷新后仍保持。点击确认，同键重复和刷新返回同一Case；最终原因登记未核验客户陈述。自动首次调查须形成有效MANUAL_REVIEW，不产生可批准的退款授权；本批不核验/审批/退款，不用手工原因替换缺失的模型摘要。

至多1客服run及1自动Case调查，各沿原RunBudget；每条只运行一次，不自动失败重跑。若正式回答、摘要或确认链路失败，先保存全部证据/费用，B–D标为未运行，再按实际失败离线定位，不为填报告继续创建更多交易。

## B–D：主链路通过后

另建一笔本人已付、已发货、模拟已签收的新订单，独立会话。按下列顺序每条只发送一次，共4轮客服对话：

1. B政策：“我只想了解店里的政策：如果快递还在运输中，没有确认丢失，可以直接退款吗？只解释条件，先不判断我的订单，也不申请。”预期引用本店政策，保持条件语义，不为了纯政策问题无谓读取当前订单/物流，不生成退款摘要/Case。
2. C1未收货：“物流显示签收了，但我本人还没拿到，家人也没代收。请先帮我核查情况，我不申请退款。”预期保留客户陈述与系统签收记录的区别，有需要时读事实，不承诺丢失或退款。
3. C2纠正：“更正一下，刚刚家人回电说已经替我收到了，包裹也找到了。之前说家人没有代收不准确，不需要退款，先结束这件事。”预期接纳纠正，旧未收到/家人未代收不再作为当前有效陈述，不继续推动退款或自动建单，不擅自修改承运商记录。
4. D人工：“我不申请退款，只想让商家人工解释一下这笔订单的配送和签收记录，帮我转给商家咨询。”预期提供独立人工核查路径，客户预览编辑共享摘要后确认，仅共享所选内容；商家端能看到核查并回复，客户原会话看到回复，没有退款Case/授权。商家回复使用明确合成核查说明，不冒充外部承运商实查。

B–D不预设具体工具顺序或要求每题都检索；按实际问题、来源和动作判断。每run原12模型上限，不新增修正额度。某个变化失败时保存结果，不重复该条；其依赖后续（如C1未成功则C2）不伪造历史启动。

## 记录与判定

输入、源码/驱动SHA、来源版本、真实模型/工具请求响应、正式回答、摘要与Case/核查关系、截图逐项保存。自动断言只作结构和UI检查，另逐项核对最终原文/引用/状态/纠正事实；运行SUCCEEDED不等于语义通过。计入全部失败和未知usage，续记原全局账本2098，不重置。候选正文/首次反馈/正式回答耗时分开，不将撤回内容当成功，不用5轮小样本声称稳定p95或业务准确率。

旧Case/付款/运行/索引/冻结报告和四历史脏文件保持；新增申请仅按正常产品流程创建，不清库或修改旧原文。每个已验证小步精确commit、普通push并核实，然后执行下一步。

## A失败后的离线修复范围

本轮真实候选的摘要前置检查先于事实/导航校验，普通ValueError未进入原来源诊断，模型看不到同时缺少的申请操作/ORDER/GUIDE。修复仅调整拒绝诊断：摘要语义使用明确异常；已解析且有已接受理解的回答，无论先触发哪类校验，都收集独立来源与必要操作缺项。必要操作从同一accepted focus/lifecycle映射产生，正式导航校验与诊断共用，避免维护两套规则。无法解析的JSON仍先反馈结构问题，不从任意畸形字段推断业务动作。

这不是自动补工具、自动选择申请、放宽发布或新增修正次数；旧动作离线仍失败不发布，脚本补读后的合规回答仅作工程验证。B–D依然未运行，不将离线通过称为真实采纳新反馈；原A失败与计划不改写。
