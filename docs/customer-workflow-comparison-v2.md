# 独立基础客服 Workflow 与完整 Agent 的评测设计

2026-10-25，按用户要求设计。目标是展示从基础LLM客服到完整Agent的工程收益。旧固定全读基线继承Agent模块，适合比较调查调度，保留原成绩；本版本采用独立基线和对外业务评分，不覆盖旧协议、判据或结果。本文件规定设计，实际实现/进度只看tasks/todo.md顶部。

## 1. 一个主对照、一个主指标

- 对照：完整客服Agent（待修复已知调用缺口后固定版本）与独立基础Workflow。
- 主指标：24个复杂售后场景的完整处理成功率，比较百分点差；8个普通场景及全部32场景分别报告。
- 辅助：首正文/最终耗时、模型请求与token、业务接口调用次数；不要求Agent每项都赢。
- 首次正式测量只运行一次完整配对：32场景×2系统=64会话、100客户轮。额外重复另列，不把重复次数当独立场景。预计约250次模型请求，建议新请求上限400，均非本轮授权或实测；实施完成后公开实际范围再执行。

数据偏向项目擅长的纠正、插问恢复、诉求切换、事实冲突、工具故障及复合请求，每类4场景，另8普通。结论限于这类模拟售后咨询，非真实用户总体分布；不声称所有工作流不如Agent。材料来源已见、旧32输入已被调试，不称独立盲测。

## 2. 基线独立实现边界

固定链路：原始历史和当前输入→一次LLM路由/信息提取→程序执行固定分支→一次LLM回答/摘要。每轮重新路由，不预设用户必须按步骤提问。

| 路由意图 | 固定读取 |
| --- | --- |
| ORDER | 订单/实付 |
| LOGISTICS | 物流 |
| QUALITY | 订单、质量政策 |
| POLICY | 政策 |
| REFUND | 订单、物流、政策 |
| HANDOFF | 使用指南、客户原文 |
| GUIDE | 使用指南 |
| OTHER | 不读业务接口，澄清或回答普通交流 |

ORDER单列，避免基线连普通实付查询都没有正确入口。使用指南同当前Agent作为公共流程资料预读一次，HANDOFF/GUIDE复用该份原始结果，不重复读来增加成本。路由输出intent、customer_description及可选policy_query，政策Query在同一次路由生成。最终回答允许回应所有已有依据覆盖的问题，不强制只回答一个子问题；单意图限制的是本轮取证分支。

基线自己编写路由/回答提示、普通JSON解析、分支调度与摘要生成。只保留原始聊天历史（最近20条，与Agent可见原文窗口相同）；每组使用自己的实际已发布回答，不给基线喂Agent输出。客户可以纠正或回到旧问题，基线靠重读原始历史处理，不另存事项列表、有效陈述或恢复事件。

基线代码不得导入resolveflow.support、resolveflow.harness、resolveflow.runtime、SDK/生产提示词或旧FixedFullInvestigation，不继承/复制其理解、上下文构造、记忆、取证就绪、目标复核、grounding、摘要装配、校验反馈或恢复模块。独立目录内仅用标准库及原锁已有httpx/pydantic等基础依赖。摘要由基线模型直接生成，不由评测器替它补写金额、原话或操作步骤。

可以共用外部资源和中性测量设施：相同模型API/参数、已绑定主体、原始订单/物流HTTP响应、同一政策检索服务/版本、原始使用指南、请求计量/计时/日志、场景加载与评分器。共用的是接口和数据，不是Agent算法。政策服务由评测边界提供，基线以独立客户端调用，不通过Agent的BoundSources/SupportRuntime。事实/检索适配器只能返回真实原始结果，不可注入Gold、焦点、缺失依据、推荐行动或修正建议。

正常每轮2次模型；每阶段最多一次纯JSON格式修正，禁止借此重新规划取证。源接口503/超时可固定重试一次，其余错误直接进入失败说明；订单NOT_FOUND保留未知，不猜金额。最终模型看到原始成功/失败结果，允许解释失败、追问或生成人工摘要，不因缺成功物流强迫沉默。两边同模型DeepSeek Flash、temperature0、非thinking/JSON、120秒/12模型硬上限和原输入输出窗口；实际次数按各自架构计入。基线不添加Agent式取证/答案校验循环。

两边均只读调查或准备草稿，不调用建单/审批/退款/政策写接口。真正用户确认及Java金额/权限职责在业务系统保留，不作为本轮对照的执行动作；这不是新Java/UI退款闭环测试。

## 3. 输入与对两边相同的业务判据

数据为[32场景/50输入](../evals/customer-workflow-comparison-v2/cases.json)，原话、顺序、业务快照、故障覆盖与v1相同，绑定原文件hash。仅另写对外可观察判据，不修改旧Gold。所有business_expectations仅供评审，不进入模型请求。

正式结果需两组都按本协议新执行并同口径源审；旧Agent成绩、旧基线成绩和新基线单次成绩不能拼成一组新对照。Agent旧报告仍提供已知失败及修复线索，不自动按新判据改写旧主分。

每轮三个检查：

1. correctness：订单/物流/金额及政策解释准确，陈述与核验事实分开；条件不冒充当前事实。
2. completion：回答当前全部请求，合理追问/人工核验可以完成相应咨询；请求草稿须实际提供，停止/切换时不得附错误操作草稿。
3. context：回答/草稿采纳当前纠正、保留仍有效信息，继续旧问题不强迫重述；没有相关历史时此项可通过并说明。

不检查task_id是否恢复、ACTIVE/SUPERSEDED/RESUME标记、是否调用特定内部动作或严格的O/P引用编号。内部状态测试仍属于Agent工程回归，不混入对照分数。评分读实际回答、草稿、原话与原始来源/取证轨迹；无需恰好走某条工具路径，但声称当前实时事实须有本轮可信来源，不能只凭客户描述或商品展示猜测。

Q25是“查询打不开时能否判丢”的条件式咨询：可以只解释假设，不强制查询；若声称本次失败则须确实尝试。Q26/27/28明确要求核对本单，须如实处理实际查询失败。此调整在v2结果前确定，对两边一致，旧v1主分/敏感性分析保持。

摘要用中性字段text/refund_summary/handoff_summary，不要求基线产生Agent状态结构。两边输出适配器仅作字段映射、保留原始响应，不补写或纠正内容；字段存在不等于语义正确。泛泛“去找人工”不能代替用户明确要求的调查、政策解释或核查草稿。

每轮三项均通过才成功；一场景所有轮成功才完整完成。格式/超时/预算耗尽/未运行记未完成，失败成本保留，不能换成0耗时发布。少量冗长、措辞差异不直接判失败；重大事实错误、过时陈述、漏主要诉求或缺摘要才影响业务通过。Codex逐轮源审，附证据，不用关键词或LLM自评自动判成功。

## 4. 结果与计量接口

统一runtime记录version、dataset_sha256、state、rows。每轮含case_id/variant/turn/run_id、status、answer（或null）、原始请求/响应证据索引、models、tools、elapsed_ms、first_body_ms。variant为agent/basic_workflow；status为SUCCEEDED/FAILED/TIMEOUT/BUDGET_EXHAUSTED/NOT_RUN。tools逐次记录ORDER/SHIPMENT/POLICY/GUIDE/HISTORY类别，重试也计；models记录真实provider usage，未知单列。

场景编号等仅供驱动关联，模型不看到family/complex/business_expectations/expected_artifact。两边逐场景交替顺序；相同客户消息仅继承各组真实历史。Agent的被接受内部状态可正常保留，基线只有原始历史；评测器不把Agent状态转换成基线记忆。

源审表绑定runtime完整hash和实际run_id；三项布尔判定及evidence逐轮填写。汇总拒绝缺矩阵/重复/未审/身份不符，技术失败或缺目标草稿不能标全通过。主指标复杂完整率、普通/总体完整率与逐轮通过率分开；业务调用全部均值和双方均完成配对均值分别报告。只给有真实可见正文的首正文P50/P95及记录数，不用进度提示或JSON首字符充数；耗时范围注明服务端，未做浏览器测量不宣称页面响应。

简历候选：基于AgentScope构建多轮售后助手，通过上下文管理、事项跟踪与动态调查，在24个复杂模拟售后场景中较独立固定分支Workflow提升完整处理率X个百分点。数字为空，普通分布/完整证据和典型前后对话放报告；调用减少如不成立就不写该收益。

## 5. 实施顺序与本轮边界

1. 本轮交付规格、业务判据、离线数据审计/源审模板/汇总器及其失败测试。不是基线或Live执行器已接通。
2. 独立实现基础Workflow及脚本模型接线，计划文件scripts/evaluation/basic_customer_workflow.py；检查无生产Agent依赖、所有普通分支/故障出口/摘要实际可用，完整跑通中性结果接口。公开普通分支验收，不能把故意不工作的基线当对照。
3. 另一步修复Agent已确认的批量动作等通用缺口，离线验证，不按题号开特例；本轮不改生产。
4. 接通两组真实模型/独立历史、原PG只读政策服务与临时Agent schema，验证计量/停止/导出。计划scripts/evaluation/customer_comparison_environment.py只提供中性原始服务/记录，scripts/customer_workflow_comparison_live.py调度两组；不得再通过继承SupportAgent或patch生产提示构造基线。实现及模型参数固定后才生成新执行manifest，不给尚未存在的执行器盖冻结章。
5. 公布范围/请求上限后执行完整配对一次，保留所有输出和失败，再逐轮源审、生成对比和3个可演示案例。不要把脚本模型通过当效果分数。

已有RAG40题五路径结果保留，不因更换Agent基线自动重跑或重新选主候选。本比较只固定相同政策工具；RAG优化和独立质量/速度证据另行处理，不将不同检索栈效果归于Agent架构。
