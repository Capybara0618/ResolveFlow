## 最终条目写法

统一“问题 -> 方案 -> 验证结果”。示例为待填写模板：

- 面向退款与补发建立统一订单行权益模型，结合资金预留、操作幂等和目标启动校验，在[N]组并发与迟到消息测试中观察到[实测结果]，解决跨动作重复补救问题。
- 通过Outbox/inbox与持久对账处理“退款成功但响应丢失”，在[N]次故障注入中[成功/未决分布]，恢复p95为[值]，保留未知结果占用以避免重复支付。
- 基于LangGraph构建领域Agent Runtime Harness，将模型动态决策与工具权限、预算预占、输出验证解耦，通过MCP调查订单/物流/仓库证据；在[合成test样本数]案例中相较固定工作流取得[质量/成本/时延]结果。
- 实现分层ContextBuilder与证据账本，保留权威字段及来源/版本/冲突，支持历史证据按需读取；在[普通/长轨迹分层]对照中，累计Token消耗为[结果]、动作质量为[结果]，而非只报告单次上下文缩短。
- 结合PG租约/fence、调用日志和不可变运行manifest实现Agent恢复，在[故障次数]次结果落库前后崩溃实验中取得[恢复/未决结果]，明确未持久化模型响应的潜在重复计费窗口。
- 构建版本化ReplayPack和隔离回放器，复现历史失败并定位策略首个分歧；在[完整轨迹包数]个包中严格回放一致率为[结果]，反事实记录覆盖率为[结果]，缺失分支显式阻断且不触发业务写入。
- 为审批绑定输入版本、政策版本与执行载荷，通过授权消费和权益启动两个事务边界防止过期方案执行；在[安全用例数]测试中[违规执行计数]。

没有实验支持时不能把“具备能力”改成“提升X%”。不能把mock支付数据写成真实退款资金、合成工单写成客户工单；不能把单节点部署写成生产高可用。

## 项目展示优先级

必须交付R01–R04、R07–R11、R13/R14，R05/R06/R12同样进入完整交付但先保证核心正确性。若时间紧，缩短前端和业务类型扩展，不删安全/评测来维持名词数量。模型路由、长期记忆、自进化、分库分表等暂不纳入成果池。

14项是完整技术证据池，不要求简历机械写14条。Agent叙事主线是“构建领域Harness，并用上下文、恢复、回放和对照评测证明其价值”；后端主线仍是可靠执行与一致性。最终可合并有关联的能力，但不要将Harness包装成几乎没有实现内容的一个框架名。每条简历主张至少链接代码入口、测试和一份真实报告；当前模板都不能当作既成成果投递。
