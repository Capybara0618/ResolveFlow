# 客服回答与任务状态衔接修复

2026-10-21，用户批准按三步推进：复用真实失败离线测试、改进任务说明与反馈、小规模真实确认后再检查多轮体验。进度只在tasks/todo.md顶部维护。

## 问题与实现

上一批C02已自主读取物流、使用指南和退款条款，两个回答草稿都有依据，但均没有tasks。此前已接受的任务仍为PENDING，纠错后模型也未更新，故最终没有发布回答。修复不能通过程序自动标ANSWERED或删除任务绕过这一问题。

- SYSTEM保留三种完整动作示例，其中ANSWER示例包含同层tasks、实际回答原句response_excerpt和依据字段；明确首次与回答必须提交全量任务，已有id/intent/request沿用。独立事项分任务，最多8项，拆分仍由同次模型决策完成，无关键词路由或额外分类调用。
- 当前存在任务时，每轮请求增加answer_requirements，明确回答必须携带tasks及全部现有任务ID；不提供自动填好的终态，不把旧草稿或未接受状态当事实。
- TaskStateError对PENDING未闭合、删除任务给出机器可读issue及受影响task_ids。一次纠错说明任务字段、合法非PENDING状态、原句定位与已读引用要求；可继续取证，不能为通过校验虚标完成。原子状态提交、一次修正、预算、引用及来源校验继续生效。
- 控制提示开销：完整原文、政策、可信状态和原窗口预算保留，压缩重复说明；不扩窗口或放宽旧指南测试。原始失败轨迹/Gold/已冻结清单均不改。

## 本批验证范围

先保存失败红测：原两条被拒ANSWER、实际发送的回答形状与任务ID提示、三事项模型修正及重复错误仍停止、禁止删任务。结合既有单问题/暂停恢复/撤回/来源/上下文与ASGI-PG恢复测试集中回归。脚本模型验证机制，不证明真实模型会正确拆分。

新冻结确认先复用原D01/D02首轮的原问题/事实/评分，仅换运行身份，单次自主两条，不重复固定组。要求2/2发布且原业务条件完整，混合题逐项覆盖、读取政策/指南；拆分数量与意图另列观察，不按程序强行拆任务。

只有两条均通过业务源审，才追加原D13四轮（未收到→暂停问入口→恢复并纠正→撤回）的单次自主确认，使用真实前轮成功结果，另冻输入与输出。至多两条加四轮，不重跑88轮，不为分数付费重复。失败则保存缺口，本轮停止收费与多轮扩展；不以两个单轮证明多轮通过，不把看到过的合成题当独立泛化数据。
