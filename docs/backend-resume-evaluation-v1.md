## 2. 冻结、隔离与运行规则

### 2.1 正式manifest

开发开始前先保存优化前构建；正式执行前保存：Git SHA/脏文件排除清单、参与源码与JAR SHA256、锁文件hash、镜像版本及可得digest、迁移列表、JVM/CPU/内存/操作系统、连接池/Redis超时、缓存TTL/限流窗口/调度参数、数据生成器hash、seed=42、scenario定义、轮次、并发及顺序、客户端/汇总器hash。

对应实验保存实际请求路径、配置与数据集hash。优化前后分别构建不可变JAR，公共DTO/权限/数据投影必须等价。A/B只改变预先声明的查询/索引/缓存变量。当前workspace与历史list区分报告，不能把旧18.9ms作为当前路径的新成绩。

### 2.2 运行环境

- 使用独立MySQL Case/Commerce库、独立Redis及RocketMQ namesrv/broker，模拟退款提供方使用本轮SQLite；模拟付款仍使用Commerce持久收据表。
- 测试账号/资源全部为合成数据，端口loopback，容器带唯一label，topic/group/run namespace唯一。禁止对原库、旧实验schema、共享Redis执行写入/清理/暂停。
- Java故障用真实自有进程退出和重启；Redis故障使用自有容器/代理；Broker故障只停自己的实例。记录PID命令归属，失败后仍保留资源数据。
- 普通整链经Gateway→Case→Commerce；细粒度SQL诊断直接Commerce的内部作用域入口，明确单列。模型建议/资格桩只用于准备后端场景，表明合成；实际审批、事务、MQ、provider和账本不由桩替代。
- 三Java/MySQL/Redis/MQ及客户端在同机运行，其他评测和编译不重叠。记录负载端CPU/超时/连接数，客户端成为瓶颈时保留无效窗口并先修负载器。

### 2.3 冒烟、执行与中断

每个场景先1轮冒烟；性能每profile先10秒正确性试跑，输出smoke目录，不计正式成绩。正式结果只追加到`reports/backend-resume-v1/<run_id>/`（待实现），原始进程日志、凭据和数据库文件留忽略的tmp。脱敏结果和hash可提交。

正式中途失败保留已发请求、超时、错误及已完成轮；重启续接仅跳过hash和完成标记均匹配的轮，不重新执行未知付款/退款以凑样本。未完成窗口标INCOMPLETE，另存重跑窗口；协议/源码改变用新run_id，不覆盖既有结果。开发调试结果与最终正式批分开，但都可追溯。

## 3. 技术点1：架构与主体边界

固定3店、至少3买家（含一名跨3店买家）、3商家账号及平台管理员；资源至少覆盖商品、购物车、草稿、已付订单/订单行、评价、工单、政策和退款状态。

对每个适用资源记录：本人/本店允许；他人/跨店拒绝；伪造merchant/customer请求字段拒绝或不起作用；无认证/错误角色拒绝。按既有契约核对400/401/403/404，不强行统一所有拒绝为403。Gateway剥离伪造身份头，内部Commerce验证调用服务身份与逐路由scope；Agent身份即使携带退款scope也不能获得资金写权限。

平台买家跨店列表核对每店归属、游标/过滤与同时间排序；一个店铺依赖故障时不得把不完整结果称为完整列表。缓存跨账号、跨商家、过滤条件变化不复用不当结果。

交付resource×actor×action矩阵、实际HTTP结果及允许正例，不预设“隔离100%”容量指标。后续新增路由必须补矩阵。

## 4. 技术点4：交易并发矩阵

### 4.1 固定规模

T01–T08各执行C=10、30两个客户端并发档，各10轮，共160轮。每轮创建独立数据、同步释放请求；C指同时在途的客户端请求，不是订单数。共享目标和独立目标分别报告。每轮保存实际到达/完成时间、发出请求数、主体/key/body hash以及最终实体映射。

| 编号 | 场景与竞争方式 | 成功判定 |
| --- | --- | --- |
| T01 | 同一购物车同revision、C个不同修改 | 一个版本竞争赢家，其余冲突；无静默覆盖，保存值与成功请求匹配 |
| T02 | 同一结算key，C/2相同载荷、其余不同数量/内容 | 一个载荷被绑定；相同内容返回原草稿，冲突内容拒绝；最终一个草稿/快照 |
| T03 | 结算与价格/规格/可售状态更新竞争 | 两种提交顺序各5轮；每轮只更改一种因素（预定轮次按价格/规格/下架轮换），结果为一致旧快照、有效新快照或明确冲突，禁止混合价格/状态快照 |
| T04 | 同草稿同付款key的C个并发请求 | 一个attempt、最多一份成功收据和订单；允许并发返回待确认/冲突，最终原请求查询到同一结果 |
| T05 | 同草稿C个不同付款key并发 | 至多一个付款尝试获得执行资格，其他请求明确拒绝/查询当前状态；无额外成功收据/订单 |
| T06 | 持久付款成功后，独立HTTP代理丢弃首次付款响应；C个查询/原key恢复 | 查询原attempt；最终一个收据/订单，不因新请求重复模拟扣款；记录首次实际响应丢失 |
| T07 | 收据已存、订单发布前终止Commerce，重启后C个查询/原请求与调度竞争 | 原attempt/计划order_id不变，订单行/退款槽/账本完整且各一份；提供方不新增成功收据 |
| T08 | 到期边界C个付款请求与一轮关单竞争 | 每档5轮关单先提交、5轮付款预留先提交；前者无付款收据/订单，后者PAYMENT_PENDING继续恢复且不被关闭 |

T03采用事务门控确保两个顺序确实出现，独立记录是否触发预定窗口。下单快照一旦已接受，后续商品变价不追改已生成快照；先读取现有业务合同，冒烟时发现语义冲突则修订场景，不自行加入新产品规则。

T06在公共HTTP层丢响应；T07的测试配置仅暂停在收据与发布边界，之后真实退出进程，不以直接改成功状态替代。两者证据层次不同，单列记录。

### 4.2 核对与计算

每轮只读核对cart/revision、草稿/快照行、payment_attempt、simulated_checkout_receipt、orders/order_line、payment_ledger、line_refund及主体。设支付成功组的允许结果为一个订单及一份成功收据：

- 重复订单数：按草稿/业务结算组计算`max(0,实际订单数-允许订单数)`后求和。
- 重复模拟扣款数：按付款业务组的不同成功收据/attempt计算多余成功数；接口调用次数不等于扣款次数。
- 原attempt保持率、订单金额/行金额/账本一致率、预期冲突数和意外错误数分别报告。
- 关单赢家允许订单数=0；到期场景的无订单不得混入“成功付款”分母。数据库检查不能只查询预期order_id而漏掉旁生订单。

T01/T03不是付款测试，全部160轮不能叫160笔付款。简历若写“30并发、160轮交易竞争”须说明包含10/30两档；更清晰的是“两档最高30并发、8类160轮”。原数据保存轮数、HTTP数、付款业务组数和成功收据数四种分母。

## 5. 技术点5：授权和退款故障矩阵

### 5.1 授权正确性

复用[已有授权矩阵](../java/case-service/src/test/java/com/resolveflow/caseservice/casefile/ResumeAuthorizationMatrixApiTest.java)的8类×10轮，加消费先提交/随后输入修改10轮。执行前将各V编号与源码分支/动作列成manifest表，不直接照搬旧90次拒绝数；统计实际旧授权尝试、当前有效控制和消费后拒绝次数。

检查输入更新、核验、撤销与审批/消费竞争；无效授权不产生执行命令，有效消费恰好产生一份，消费后输入冻结。资格来源stub明确标记，本部分是Case HTTP+真实MySQL证据，与整链MQ试验分栏。

### 5.2 正式退款故障

每类10轮、每轮新业务数据，共7类70轮；其中F03每轮两个行，其余每轮一行，计划总80个成功退款行。按实际是否执行成功核对分母，不能先填80成功。金额固定为正整数分，F03两行不同金额；订单实付等于行实付之和。

| 编号 | 实际故障操作 | 核对 |
| --- | --- | --- |
| F01 | 同签名退款命令投递10次 | Inbox可重复投递，业务效果/provider成功/账本结算/工单关闭各一次 |
| F02 | 同授权同operation，10个不同event_id并发 | 不能仅依赖event_id去重，仍只有一个有效资金操作 |
| F03 | 同订单两行同时退款 | 行级独立结果、整单额度正确；允许共享账本短事务锁等待 |
| F04 | provider成功持久化后真实断开HTTP，查询延迟可见10秒 | 观察UNKNOWN及原金额占用；查询原operation最终结算，不换ID重付 |
| F05 | Commerce结算已提交、结果Outbox尚PENDING时终止进程并重启 | 发布原持久结果，不重复执行provider资金操作 |
| F06 | 同成功退款结果投递10次 | Inbox收到预定次数，Case终态/关闭事件仅一次，金额不再增加 |
| F07 | 自有Broker停机，真实消费授权并生成命令，停10秒再恢复 | Outbox持续保留待投递记录；Broker恢复后原命令/结果完成；消息恢复与资金最终结果可关联 |

F01/F02可在lab暂停自动命令投递后读取真实Outbox原文精确投递，F02的新event_id使用实验签名密钥；其他业务字段不改。另加1条普通链路冒烟证明自动Outbox模式。F07命令产生前Broker离线，所有应用不重启，验证现有客户端重连/投递；若失败保留，不把人工重投算自动恢复。

每轮在预留后、UNKNOWN或故障窗口、结算后、最终四类边界按适用性记录账本。检查`refunded+reserved<=paid`及非负、单行成功计数、占用/终态。provider持久成功数与业务退款操作去重计算重复，不能只看HTTP200。

F04/F05/F07收敛观察上限各120秒；超时按失败保留，不删样本。恢复耗时分别从查询恢复可见/新进程就绪/Broker恢复可用起计至Case终态，另报端到端总耗时。尚无收据的UNKNOWN另设正确性对照，要求持续保留占用、不自动收费；此对照不计入应收敛成功率。

简历浓缩指标来自同一正式F批：类别数、已完成故障轮数、重复成功退款数和超额订单数。授权结果、收敛率与耗时放详细报告。

## 6. 技术点7：SQL、缓存与限流

### 6.1 固定数据与接口

1. 工作台20000合成工单，其中4000待审，2店，按固定人员归属/状态/时间分布；相同时间戳、下一页、另一商家和不同scope/search均有样本。
2. 商城3店、100买家、10000已付订单、2000未付/待确认/取消/到期草稿，订单每笔1–3行；固定30商品/45SKU，30商品各200条评价，共6000条，每条对应独立已签收订单行。生成器须核对可用行数和所有外键；退款状态含FREE/RESERVED/CONSUMED。
3. 主接口为当前实际workspace审核入口、`GET /api/v1/shop/purchases`、公开商品评价接口；Gateway外层为HTTP指标范围。工作台准确path/query从实际网页/Controller核对后写入manifest，不能用旧list近似替代。

### 6.2 SQL结构计量

用JDBC prepare/execute或生产Mapper实际调用点统计，每个计数说明是SQL执行还是Mapper调用。分别读取1/24/48条订单页（单店/跨店，新旧订单混合），10次固定数据重复，比较优化前后：结果投影、SQL次数、返回行数、跨店内部HTTP数及事务边界。商品列表作为已有批量查询回归，不重复声明新增优化。

执行EXPLAIN ANALYZE记录实际筛选条件、扫描行、排序、索引、loops和执行时间。订单批量化主要比较每页SQL增长；索引主要比较访问计划；单次EXPLAIN耗时不作为HTTP p95。

### 6.3 正常HTTP窗口

| Profile | 条件 | 并发与轮次 | 窗口数 |
| --- | --- | --- | --- |
| P1 工作台 | A优化前访问路径/索引且缓存关，B优化后SQL/索引且缓存关，C优化后缓存开 | 10/30并发，各3轮 | 18 |
| P2 买家订单 | A批量化前，B批量化后；两者无订单缓存，limit24 | 10/30并发，各3轮 | 12 |
| P3 公开评价 | 同一实现缓存关/开，limit10 | 10/30并发，各3轮 | 12 |

共42窗口，每窗口30秒预热+60秒正式采样。预热不计正式延迟；仍保留预热正确性和错误。轮次0用ABC、轮次1用BCA、轮次2用CAB；双条件AB/BA/AB，避免总先测同一条件。并发固定在途请求，timeout3秒，失败不自动重试，单窗口耗时不变。

P1冻结分布为80%本店公共待审首页、10%同过滤下一页、10%第二商家首页，seed42；其他搜索/个人scope的正确性另测，不拿热点结果代表任意搜索。P2为60%全部、20%PAID、20%WAITING_PAYMENT，50名固定买家循环、固定是否筛店比例；空/非空比例写manifest且两条件一致。P3为80%单热点商品、20%其余29商品等概率。

P1的A先冻结开发前JAR与访问计划；若本批未新增索引，不制造无关劣质索引当基线，明确A/B相同、只测缓存增益，最终文案用实际有改动的对照。索引变化仅允许新实验库/副本，不能删除原业务索引。

每请求验证授权范围、过滤、排序、行金额和页面ID投影；稳定合成数据下预计算正确集合，额外抽样逐字段核对。登录在窗口外进行，令牌有效期足够，不将登录耗时混入查询。

### 6.4 缓存故障与限流

P1与P3分别测缓存热点TTL到期、断连、命令超时、自有依赖恢复，每类32并发，各3轮，其中P1四类12窗口，P3选“超时”3窗口，共15窗口；每窗口10秒预热、30秒采样。每窗口使用独立namespace或产品集，不FLUSH共享缓存。控制代理只影响本实验连接，记录实际注入/解除时间。

测真实数据库inflight/peak、成功p95、失败延迟、503比例、恢复时延、请求后inflight是否归零。配置值8不能充当实测峰值；单实例上限8/100ms，双实例另按实例分别计量。热点到期测试记录同一键每轮过期附近的实际加载次数，决定是否需要重建合并；如加合并，作为新候选做同输入对照，不混入原矩阵。

双Case实例Lua单独测：同账号同动作12请求同时均分到两个实例，每个独立窗口预期合计6放行/6限流，WRITE和REPLY、不同账号分别验证；3个完整60秒窗口，不删限流key加速重置，键TTL自动消失。Redis断连时写入503且Commerce未接到写操作，恢复后重新建窗；记录请求、许可和实际业务写入三种计数。此部分不作为查询p95样本。

### 6.5 指标公式与输出

- 延迟：客户端单调时钟覆盖完整HTTP请求；连接异常记录实际耗时，不能用timeout配置值冒充实测。成功p50/p95/p99用nearest-rank；失败延迟及全请求延迟另列。
- 吞吐：成功RPS、总请求RPS均按正式采样实际持续时间计算；意外错误率=意外失败/全部请求。预期业务拒绝在并发矩阵按合同计正确，但不并入成功HTTP吞吐。
- DB/成功请求=正式窗口实际DB执行数/成功响应数；DB/总请求、失败导致的DB次数同时报告，不能用较高拒绝率制造减负收益。
- DB降幅=`1-优化后(DB/成功请求)/优化前(DB/成功请求)`。P1 A→B为SQL/索引，B→C为缓存，A→C为组合；P2/P3各自独立，不把不同接口指标拼成一条。
- 相同并发每条件三轮指标取中位数，保留三轮全值和请求数。最终简历只填一个主接口/负载的配对p95和配对DB降幅，正文若概括多个入口，报告须指出数字对应工作台。
