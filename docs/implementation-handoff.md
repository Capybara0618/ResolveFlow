# 后续实现模型交接

## 已确认意图

用户要一个亮眼且可信的个人简历项目，与惠每实习项目并列。目标岗位：Agent开发、AI应用开发、Java后端。采用电商售后场景，Java微服务+Python Agent，消费者提交诉求、后台自主调查、证据不足追问、高风险人工审批。无需真实用户或支付，用合成数据、真实实现、实验支撑成果。

规格已从讨论整理为v1.1，使用方从T00开始实施。本文档不表示代码已经存在。工作区原有tmp/pdfs属于简历阅读中间文件，与产品代码无关，不导入项目数据或发布物。

本次深化已确定：Agent以领域Harness为核心，不是固定业务workflow。先读[Harness架构](agent-harness.md)，再按任务读取[上下文](context-engineering.md)与[回放](trajectory-replay.md)。T35–T39为必做；T35/T36/T37在T20前完成，T38在完整CI前完成，T39在最终演示前完成。共40个工作包，不可机械按编号从小到大执行。

## 每次任务的工作方式

1. 查看AGENTS.md和todo状态，选择依赖已完成的第一项；读取该项专题规格。
2. 明确本次验收和将修改的模块；通常一个任务一个垂直行为，过大就先拆子任务。
3. 先实现关键行为测试，按既定契约开发。通过测试后更新任务状态与证据记录。
4. 如果发现文档缺少普通字段/错误分支，补充契约与测试一起实现；不得让消费者自行猜字段。
5. 有重大架构冲突时先给最小复现/证据、修订建议和影响；依赖patch、命名、帮助函数等自行决定。
6. 每里程碑执行对应G门槛，再继续后续任务。只改README勾选不等于里程碑通过。

## 无需再问用户的问题

场景、三类岗位、双语言架构、合成数据、模拟支付、单Agent、公开可复现证据已确定。是否使用Kafka、是否拆更多服务、是否换多Agent等已在架构中决定。不要再次访谈这些问题。

## 可能确实需要输入的地方

- live评测需要模型API访问与预算：尽早说明所需环境变量和按实际价格的小样本成本估计，先完成mock及其余独立工作；不能假定用户已授权无限API消费。
- 主要版本组合发生有证据的不可兼容，且涉及大范围框架变更。
- 用户要求公网部署、购买资源、连接真实支付/客户数据时重新处理相应权限。

## 禁止的捷径

- 用内存Map代替关键状态库并称可恢复。
- Java服务共用Mapper跨库读取，或所有“微服务”实际上一个进程却按多服务宣传。
- 假MCP工具、全量固定工作流冒充动态Agent、假embedding。
- 只给LangGraph套一层类名便宣称Harness完成，或按case_type硬编码模型后续所有工具。
- 模型压缩权威金额/状态而没有原始证据，或截断上下文后不记录遗漏与冲突。
- 用新版Prompt恢复旧manifest的checkpoint；回放缺分支却回源Java或让模型编造Observation。
- strict回放访问live模型/业务写入口，或把反事实回放覆盖子集冒充全部case。
- Agent自报confidence直接决定退款；审批令牌只校验签名不校验状态/版本。
- provider超时就release，或UNKNOWN换operation_id再执行。
- Agent crash测试只在安全检查点杀进程，从而声称零重复LLM调用。
- 指标只保留成功样例、调整测试集后隐瞒、mock指标写成live效果。

## 建议直接使用的实施提示

> 请阅读AGENTS.md、docs/implementation-handoff.md与tasks/todo.md，从第一个依赖满足的未完成任务开始实施。按专题规格和JSON Schema开发，每次交付一条可运行行为并执行相关测试。实际命令、测试结果和报告路径写回任务记录。达到阶段门槛后继续推进。保持已确定的业务范围、服务数据归属、权限及资金不变量；普通实现选择自行处理，重大设计冲突提供证据再修订。不要仅生成代码不运行验证，也不要把未执行的实验标记完成。

## 何时需要强模型审查

G2退款闭环后审查事务/未知结果；G3补发后审查取消与start竞争；G4 Agent接入后审查恢复、身份和旧回调；G6最终审查原始指标与简历主张。代码审查不能替代测试，较强模型也不得跳过证据。

GH另外审查：实际模型输入快照、关键事实保真、防循环/预算、记录到执行的对应关系、manifest恢复兼容、REPLAY_MISS与出站隔离。完整实现不以增加多Agent、Skills市场或自进化替代上述深度。
