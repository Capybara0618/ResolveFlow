# 按v2预期图整改项目的实施说明

日期：2026-10-02。用户认可[v2图册](ui-targets-v2/index.html)的方向，并询问按图整改的实施方式。本文件把图册对应到现有代码、接口依赖及批次验收，沿用[双端补齐方案](product-completion-review.md)和[原五批计划](../tasks/plan.md)，不另起一套业务路线。实际完成/暂停状态只在[todo顶部](../tasks/todo.md)维护。

## 1. 开始方式

先有业务方案、预期图和实施对应关系，再按完整功能批次构建。本文补齐第三项；不用重写全部规格，也不用再画一轮图。遇到具体新增接口/字段/协作规则时，在该批实现前同步专题规格、核心OpenAPI、类型及fixture。

顺序是：**核验现有成果 → 明确接口与状态 → 贯通页面和业务 → 集中验证 → 记录并正常提交推送。** 页面接入真实数据时就采用v2风格，不能先堆一批假数据页面，再等待最后接业务。一个功能批次内部可以分几个3–5核心文件的小步，批次完成才集中向用户展示，不要求逐按钮验收。

用户已认可视觉方向，后续可按现有授权继续范围内实现，不需要为复用组件、拆组件或普通样式选择重复询问。本文本批仅补齐实施文档；本次未实施页面/接口，也未重跑业务验证。下一次执行从新第二批客户原型接续，不从身份迁移重新开始。

## 4. 组件和数据组织

以下组件名为实施建议，不代表已有文件；优先在迁移具体行为时创建，不一次性生成空组件树。

- App.vue保留登录会话和角色入口；抽取共用AppShell，集中页头、角色导航、身份/退出、错误反馈。
- CustomerWorkspace承接订单、申请列表、当前申请状态和请求代次；按需拆订单列表、申请表、申请详情。当前问题和历史从客户投影读取。
- MerchantWorkspace承接队列/视图、负责人和当前详情；继续嵌入已有来源、引用、人工处理组件。不要只改ReviewerWorkspace.vue却遗漏App.vue中的旧核验/批准入口。
- 管理员人员/概览/政策视图放在共用商家外壳内，使用专用管理API；未实现权限前不打开可执行入口。
- 沿用现有Vue、TypeScript、client、事件流、pnpm锁和Java/Python栈。导航可用现有URL/History能力逐步组织；本批不默认引入新路由、状态管理或UI依赖。
- 退出/切换账号清空当前详情、草稿、请求及事件订阅；请求返回和SSE更新必须核对当前会话、工单与版本，迟到结果不得覆盖新页面。
- 列表目前采用cursor分页；图中的总页数、数字分页和全量计数不保证现有API提供。该批明确契约前，使用诚实的“加载更多/上一批”或页内计数，不能根据已加载条数伪造总数。

## 5. 从下一批开始的具体顺序

### 新第二批：客户完整申请，第一批身份成果直接沿用

1. **收口未提交原型。** 审阅客户Controller/Service/Repository、V20和OpenAPI变更，核对客户最小投影、分页游标、期限与允许动作。先补关键失败回归：同商家另一客户借相同幂等key/请求体重放创建不得读到他人工单；问题超期/旧问题/旧版本不可回答；已消费不可追加/撤销；材料不泄露工作人员内部信息。
2. **同步契约与入口覆盖。** 新增路由数量/登记测试按实际契约更新，不删断言；保持旧接口兼容。新增客户类型和client调用，并用对应fixture验证生产者/消费者一致。
3. **订单→申请→详情。** 02/03采用真实商品/金额/资格，不输退款金额；创建成功进详情；已有活跃申请可直接找回。已创建但初始材料失败时保留文本，只重试未保存材料。
4. **我的申请→回答→重新调查。** 04列表可筛选/继续分页；05原始申请、已提交文本、当前问题与两轮历史可读；回答自动携带当前question_id和case.version，成功后进入新调查，不再手填ID。
5. **撤销和公开结果。** 使用服务器允许动作；消费后只读；UNKNOWN仅显示待确认并读取更新；用户看到公开原因，不泄露内部工具/授权信息。实现空态、401/403/404/409、网络写入未知和会话草稿边界。

本批验收：客户A从订单申请→我的申请可找回→工作人员要求补证→A回答→新调查→人工拒绝或批准模拟退款→A看懂结果；刷新后重新登录仍能找回申请。客户B与另一商家不能看到A的申请。不以预览图或四项原型测试替代完整闭环。

### 新第三批：多人审核与最小账号管理

先定负责人/独立协作版本和原子领取/释放/转交/管理员接管合同，再追加迁移与服务端守卫，最后接07/14/10/11/16的界面。覆盖所有人工写入口，包括核验、两类补证路径、人工方案、批准/拒绝；管理员必须先明确接管。

本批验收：两专员争抢同工单只一人成功；他人只读；转交后旧负责人不能写；等待客户期间保留负责人；领取/转交不触发新调查；禁用/角色调整/密码重置拒绝旧会话；本商家最后管理员受保护；跨商家账号管理拒绝。

### 新第四批：共用商家详情、管理员页面及桌面体验收口

按08/09/15重组真实资料、Agent建议、绑定来源和人工操作；按18/19明确失效、失败、有效审批、授权消费和结果。补10概览及12政策只读投影，统一全部导航、真实显示名、卡片、表格、弹窗及13公共状态。

本批验收：材料卡能进入核验；核验/回答后旧建议失效；有效当前方案才可批准；来源定位绑定原文而非另一政策；Agent失败能走人工方案，复核失败留草稿；消费后所有人工输入冻结；UNKNOWN只有原操作跟踪。无需修改现有AgentScope循环或另建支付系统。

### 新第五批：整体验收与体验说明

用现有启动入口在正式浏览器跑多客户、两专员、管理员和双商家场景，集中检查申请、补证、核验、拒绝、批准模拟退款、转交与冲突，以及账号/隔离边界。录入样例明确标合成；live/mock和真实/合成分别标注，复用已有live结果，不为截图反复付费调用。

以1440/1680桌面宽度比较预期图的结构、层级与操作位置，1280确保内容和按钮可达；文案/编号/计数取真实API，允许正常长内容滚动。生成图中的字面差异按v2合同修正，不把商品图、政策例文或状态板写进业务数据库。

交付实际截图、演示顺序、通过/失败/未运行及剩余限制；保留`.\demo.ps1`自行启动、status、stop及数据。整体验收后才称双端闭环和预期图改造已完成。

## 6. 验证与提交节奏

文档批次检查链接/对应关系/Git差异；业务批次运行相关Java、前端测试和build，按变更范围选择，出现新失败再扩展。前端现有入口：`pnpm --dir web test`、`pnpm --dir web build`；Java21及Maven入口见[工程约定](engineering.md)，CustomerWorkspaceApiTest仍须在接续时实跑，历史4项通过不是当前证据。

范围涉及客户入口时覆盖CaseApiTest、客户工作台测试、问题/材料/撤销及消费冻结；涉及协作时补真正并发/所有写入口回归；涉及RAG展示时复用引用/来源/调查分项测试，不只验证截图文字。

相关契约、类型、fixture、源码、必要测试和账本记录一起精确提交；原未提交业务原型与他人修改保持边界，不能把工作区所有改动一起推送。普通通过小步的正常commit/push已有授权；按功能批次集中汇报，无需每小步用户确认。

本文件不记录勾选进度，也不承诺未经验证的工期。范围内关键规则仍是单订单行全额模拟退款、当前负责人、当前有效方案、授权消费冻结、同行至多一次成功及UNKNOWN不换ID重付。
