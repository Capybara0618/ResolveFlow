# 客服重构：用户端、商家端与多租户架构草案 v0

日期：2026-10-12。用户要求项目具备用户端、商家端和多租户架构，并明确选择：商家第一版查看调查报告/依据/建议，在工作台处理；商家政策沿用受控导入与版本管理，后台查看本店内容。本草案补充[客服设计](customer-agent-design-v0.md)，新会话协议/表/测试未实现，实际进度只看 [todo 顶部](../tasks/todo.md)。

同日用户进一步确认：换商品进入/恢复独立咨询并保留本人历史；转交前客户预览摘要及材料，商家可追溯相关原文。用户明确人工咨询不限于退款，以下以独立咨询核查单支持商家接续。这些是产品决定，业务对象和实现仍待正式契约。

## 1. 已有基础与当前目标

当前 [平台买家协议](platform-buyer.md)允许一个平台买家购买多个商家的商品、汇总本人订单与售后；[三角色协议](merchant-role-merge.md)定义买家、单账号商家及平台管理员。每店一个商家账号的既有决定保持，多租户不自动扩大为多人客服组织或商家计费平台。

本轮阅读核对了 `RequestPrincipalResolver` 与 `BuyerScopes`：平台买家通过可信买家/商家/客户绑定，按实际订单行或工单转换为有限业务主体；商家身份固定本店。旧兼容身份保留，新咨询不把平台买家固定成一家商家的客户。政策选择按[当前合同](core-contracts.md)使用订单支付时间，并在正式工单中钉住版本/hash。

本轮是架构设计与只读核查，未重跑既有隔离测试或宣称新客服会话已经具备隔离。新工作要把上述归属扩展到 conversation、turn、申请摘要和咨询执行。

## 2. 主体模型与端的职责

建议租户继续以商家为单位，用现有 `merchant_id` 表达；第一版沿用一家商家对应一家店铺，不额外增加一套与 merchant 重复的 tenant 身份。若以后一家企业运营多店，再另行讨论 tenant/store 层级。

| 主体 | 范围与职责 |
| --- | --- |
| 平台买家 | 全平台身份，统一查看自己的跨店订单/申请及咨询历史；每个实际咨询绑定选中的订单行及对应商家 |
| 商家 | 一个租户的工作台，处理本店订单/售后、读取调查结果与本店政策；第一版不新增案件问答助手 |
| 平台管理员 | 沿用现有基础管理职责，不自动获得各店私有咨询内容或退款审批权限 |
| Agent | 共享执行框架，按当前咨询/工单取得独立上下文与有限工具身份，不代表任意商家或买家 |

公开商品目录等平台公共资源与订单、会话、工单等私有资源分别处理；多租户不能让买家本人跨店订单列表变成只能看一家店。

## 3. 会话及交接：待写入正式契约的边界

- 聊天入口可以汇总本人订单。选定商品后，由后端从真实归属确定商家、客户及订单行，不能只接受模型/前端填写的商家身份。
- 每个咨询上下文绑定一个订单行与一家商家；换商品打开/恢复该商品的独立咨询，入口仍可回看本人历史。用户已接受，历史布局在预期图细化。
- conversation 保存买家所有权、商家/客户/订单行归属及工单关联；turn 关联当前输入版本，run 独立管理执行。字段命名、唯一性及状态仍待契约设计。
- 申请摘要属于当前咨询、当前订单行和当前有效输入；客户确认后创建/接续该商家的 Case。涉及订单/政策变化时重新校验，不把旧摘要自动迁往新商家。
- 商家看到关联本店咨询核查单/退款工单所需的客户材料和交接内容；客户提交前预览摘要及材料，商家可追溯相关原文，未提交的全部私人咨询不默认交给商家。用户已接受，原文范围与预览布局在图文合同细化。
- Agent 生成期间发生纠正/切换时，旧回复的发布依据当前输入版本判定；工单 revision、执行 fence 和会话版本各有职责，不用租户标签代替版本管理。

### 3.1 人工咨询与退款申请是两条路径

用户可只要求核实物流、解释政策或帮助处理订单问题，不必表达退款意图。显式请求人工，或Agent提出需要商家核查且用户选择转交时，提交本店咨询核查单。转交卡片展示当前问题、已查事实、待核查事项及将提交的材料；客户可修改/补充后发送，无需填写退款金额或退款原因。

| 对象 | 目标 | 关联及业务影响 |
| --- | --- | --- |
| 咨询会话 | 持续客服问答和当前订单上下文 | 可关联人工咨询记录及退款工单，聊天本身不生成退款授权 |
| 咨询核查单（建议技术名support_ticket） | 商家异步接续非退款咨询、核查并回复 | 在Case服务管理，关联buyer/merchant/customer/line/conversation；不占退款槽、不建资金预留或授权 |
| 退款工单（既有Case） | 客户明确申请退款后的调查、审批及执行 | 仍由客户确认申请摘要后创建/接续，沿用现有资金/状态/版本约束 |

商家在同一工作台按“咨询核查/退款申请”查看，咨询侧可记录核查结果、回复客户、要求补充信息及结束处理；客户从原会话收到问题与回复。第一版使用已有工作台的异步处理方式，非新增实时坐席聊天，也不要求商家先询问另一个Agent。

咨询记录应能表达待商家处理、处理中、待客户补充、已回复/已解决等不同业务状态；“已回复”不自动等于“已解决”。具体状态枚举、谁能关闭/重新打开、用户追加问题如何接续，随契约一起设计，当前未加入生产协议。同一问题存在未结束核查单时继续原单；已关联适用退款工单时通过该工单继续沟通，具体匹配/幂等规则待细化。

人工核查发现可以申请退款时，在会话提出下一步并展示退款申请摘要。客户确认后新建或接续退款工单，与原咨询记录建立关联；复用客户已提供的有效材料并重新取得必要业务事实。咨询单不原地改造成退款命令，客户也可以选择仅得到答复后结束咨询。

Agent可继续帮助解释政策、查看处理进度或整理补充信息；商家的核查结论作为明确来源的回复记录进入会话，Agent不能冒充人工已核实结果。

该对象增加是根据用户“人工咨询不限退款”的业务需求作出的设计选择。现有`POST /api/v1/cases`只接受`requested_actions=[REFUND]`，不能用空动作或假退款来承载；后续须定义新的咨询核查契约，不在本轮修改旧Case/OpenAPI。

## 4. Agent 与 RAG

保留一个 AgentScope 执行框架；客服咨询和工单调查是运行场景，不是给每个商家另部署一套 Agent。不同租户、会话和 run 的上下文、来源、结果独立组织。共享模型客户端/连接池不共享客户记忆。

正式调查继续使用既有 case/run/revision 及商家/客户绑定；未建工单咨询需要新身份和只读工具契约，不伪造 case_id 套用旧接口。商家查看报告不额外触发模型请求；人工补证/重新调查按既有业务状态启动。

政策沿用每店受控导入、不可变版本和后台只读。检索范围应由后端确认的商家、订单适用政策版本/manifest决定，候选召回前就限定范围，不能先跨店检索再依靠模型挑选。正式案件继续使用其已绑定版本。

平台通用使用说明可以作为独立公共知识范围的后续建议；本店退款资格仍以本店适用政策为依据。公共知识分类/展示尚未冻结，外部原文检索评测材料不自动成为某商家的生效政策。

RAG 缓存需包含影响检索结果的商家、版本/manifest、索引及查询条件。订单/会话缓存按具体主体和资源归属设计，不只给所有缓存增加一个 merchant 前缀；用户自己的跨店聚合列表仍以买家身份区分。

## 5. 部署、数据与验收

沿用共享 Gateway、Case、Commerce 与 Python Agent 服务，以及 Case/Commerce 各自 MySQL、Agent PG/pgvector、Redis和RocketMQ。建议以共享服务和明确的数据归属完成个人项目多租户，不新增每商家一组微服务、独立模型部署或数据库。

新私有记录的查询、写入、后台任务、事件回写和日志/轨迹读取都需要携带并核验对应归属。数据库唯一性/索引按具体对象设计：商家局部业务键含商家，平台会话所有权含买家，不能盲目把所有ID都改成复合主键。模型输出不决定真实资源归属。

多租户验收至少覆盖以下新增客服行为，原业务隔离测试继续复用：

| 验收情形 | 预期 |
| --- | --- |
| 同一买家在A/B两店有订单 | 列表可汇总本人订单；每次咨询与政策依据只对应当前所选店铺商品 |
| A/B店存在相同局部客户/规则标识 | 身份与政策版本仍按商家区分，不因名称/编号相同混用 |
| 买家从A商品切换到B商品 | A的未确认摘要、业务陈述和异步旧回复不成为B的申请输入 |
| 商家查看/处理案件 | 只能取得本店允许的咨询核查/退款案件内容，平台买家可查看自己的跨店申请 |
| 两店使用相似问法但适用政策不同 | 检索返回各自依据，答案跟随实际规则，不把差异归结为随机话术 |
| 缓存命中与后台回写 | 命中结果、回复、报告和处理结果归属正确，覆盖相同查询及输入更新 |
| 客户只请求人工咨询 | 能提交/接续咨询核查单并收到商家回复，退款工单/预留/授权不增加 |
| 咨询后客户选择退款 | 明确确认摘要后关联真实退款工单，材料与来源可追溯，不能由商家回复自动提交 |

相同签收争议必须人工等平台/领域约束不会为测试两店差异而放宽；可使用不同有效区间/表述/必要材料构造检索差异，保留固定业务事实。指标分商家/场景报告，结合完成率、政策支撑、纠正采纳、成本和耗时；数据为合成时明确标注。

## 6. 需要继续细化的产物

1. 首场景规格和对话样例增加两店维度，定义咨询、申请、人工交接各自的完成标准；加入“只核查不退款”及“人工咨询后申请退款”。
2. 五类预期视图体现当前店铺/商品、切换历史、申请确认及商家案件信息；确定交接会话片段的客户可见范围。
3. 冻结会话/turn/咨询核查单/case/run关系、咨询回复/补充/结束状态、身份转换、未建工单工具范围、政策版本选择与缓存键；再定义接口、类型、表与迁移。
4. 开发一条跨端完整链路，再扩场景。按功能批次验证新增租户行为，既有业务/恢复和旧实验不重写。

产品选择及独立人工咨询方向已确定，会话/数据/公共知识和咨询核查状态仍要在详细设计中落地。下一步仍是首场景规格和样例，再绘制预期图，不因多租户重新启动旧CXX任务或全栈迁移。
