# 客服 Harness 与上下文量化方案 v1

2026-10-26，用户认可将 Harness 与上下文工程合成一个简历技术点，并授权开始准备评测。范围为当前 `orchestrated-v1` 客服，不重测已冻结 Agent/RAG、不修改桌面简历或生产策略。当前进度只维护在 tasks/todo.md 顶部；本文件固定实验设计，不是完成清单。

## 1. 两项实验和指标

上下文实验：相同模型、SDK循环、提示、权限、工具与来源、8192输入/1024输出上限，比较当前分层上下文与直接拼历史超限删最早消息。模型使用与已有客服评测一致的 DeepSeek Flash、temperature=0、非thinking/JSON；真实发送版本及usage另记。主指标为关键上下文处理通过率，辅助为累计输入token；质量相当/改善时才写token减少。每个检查点的全部模型请求、纠错及原文/历史读回引起的请求均计入，不以单份prompt长度替代usage。

恢复实验：当前SupportRuntime/SupportStore，五种任务各三个位置，每位置两组独立前缀与中断，合计15配对/30故障前缀；比较从头执行和原run恢复。主指标 `(从头新增请求-恢复新增请求)/从头新增请求`，只算中断后的新增provider请求；辅助为输入/输出token、恢复完成与结果正确性、耗时。同时报告包含前缀的总成本。重复运行不是独立新业务情形。

## 2. 上下文材料与判分

固定 [cases.json](../evals/customer-harness-context-v1/cases.json)：四家族各4段，共16段、两检查点、两组共64个回答轮。家族为早期信息引用、纠正后采用最新陈述、插问后恢复、避免重复排查。每家族分别插入0/8/24/48组客户与助手背景消息：0组为短上下文控制，另外三档用于观察长距离差异；实际token及是否触发8192裁剪由准备/正式报告记录，不保证每档对应某个比例。不给基线更小窗口，不事后按分数改长度。

第一检查点正常回应早期客户问题并生成状态；第二检查点前插入预先固定的合成背景，再让客户继续原问题。两组第一轮回答由各自模型真实生成、写入自身后续历史，不能将优化组答案移植给基线；材料中的背景助手消息是固定作者合成事件，显式标记，不冒充真实模型生成。背景阶段不逐轮调用模型，因此这是机制级检查点实验，不能称完整长会话端到端成功率。

优化组只继承第一检查点生产逻辑实际接受的陈述/任务状态（包括合法conversation_update）；不得人工根据rubric构造记忆。基线保留全部相同原始客户材料及自身实际助手回答，不继承跨检查点结构化状态；当前轮的解析、工具结果、预算、来源/权限/引用检查仍与优化组相同。原文与历史工具的可读范围保持相同，不禁止基线补读以人为制造差距；补读成本计入。

原始材料与可观察rubric放在同一固定数据文件，但送入模型的public_case仅含产品/历史/背景/当前文本；family、rubrics及恢复方案不得进入请求。判分依据客户原文、工具事实和实际发布答案逐项源审，允许等价正确表述，不按内部task字段或关键词命中计分。技术失败、没有回答或第一检查点未正确提取信息的后果保留，不补造状态、不移出分母。

每个检查点：①当前诉求正确处理；②使用正确的当前陈述/未完事项；③不重复要求已经明确完成的必要排查；④客户陈述不冒充系统确认，不能声称未执行的提交/退款。各题rubric指定具体内容。通过率按全部32检查点，两组分别统计；第一/第二检查点及四家族另列。旧陈述误用、重复追问、错误事项恢复逐项计数，未涉及项不填作正确。

计量同时展示完整64轮、每段两检查点合计、双方均通过的配对子集，不以失败提前终止造成token更少为优化。小样本相当仅是描述，不声称统计非劣效或真实客户总体收益。实际usage缺失记录为未知；官方本地tokenizer估算与provider usage分栏。冷启动/状态准备/模型往返分开；原首正文3.37秒不被本实验覆盖。

## 3. 当前客服恢复的真实边界

旧15组16.4%来自旧Case调查的DurableRun，不能直接迁移到客服SupportStore。当前源码 `support/store.py` 将调用先写STARTED，再存COMPLETE。cached遇STARTED模型调用明确抛UNKNOWN_MODEL_RESULT；STARTED工具抛INTERRUPTED_TOOL_RESULT。模型响应未持久化的窗口目前不会自动重发或被当作可复用，不修改生产来迁就评测。

| 故障窗口 | 注入位置与现有预期 |
| --- | --- |
| 模型返回未保存 | provider返回后、SupportJournal.complete提交前退出；保留STARTED，恢复应明确报告未知，不重置预算，当前不预设任务完成 |
| 模型已保存 | COMPLETE事务提交后、动作被引擎消费前退出；恢复重放已存响应，不重发对应模型调用 |
| 业务工具已保存 | ORDER/SHIPMENT/POLICY结果提交后、下一模型调用前退出；不把启动时自动读取的GUIDE当业务故障命中 |

五种任务为物流查询、政策条件、退款摘要、订单/物流/政策复合查询、独立商家核查。正式前仍需绑定统一合成订单/物流/政策快照并验证每题真实到达目标工具；未到达、技术失败、未知结果均原样报告，不换任务刷命中。订单/资金/权限仍由Java/原工具边界管理，本实验没有退款、审批或建单调用。

正式故障使用真实子进程os._exit和新进程接管，保留原manifest、相同run输入、绝对deadline、已消费预算和调用日志。仅使本实验租约可接管；从头组新run继承既花预算和原deadline，不拷贝可复用结果、不续命。fence必须增加，旧持有者写入被拒。未知窗口失败必须保留在15组总分母，不能用“少请求”掩盖没完成；恢复效率还需按可完成的已保存窗口分列。

## 4. 实施分步与运行边界

1. 固定方案、原始16段/五任务及rubric；实现无Gold输入适配、raw上下文对照和64脚本SDK接线，验证来源/状态和8192预算。保存production代码/tokenizer/锁及本批文件hash，不改原生产文件。
2. 接真实模型计量/有界发送与逐轮持久化，原始usage、实际body、accepted状态和失败全保留。恢复另接SupportStore真实PG/进程注入，不复用旧DurableRun驱动冒充新链路。
3. 无网络桩和隔离临时PG通过后，确定实际请求总上限及累计账本起点，再进行明确授权的有限真实运行；当前准备命令不接受execute参数，也不读取凭据或发收费请求。64个回答轮不等于64次模型调用。
4. 逐项源审/聚合。原Agent/RAG成绩和原15组恢复/18包回放保留；本次没有运行回放就不把旧18/18写成新版验证。无收益也完成记录，不追加网格、换标签或默默改基线。

本机命令（先设置PYTHONPATH为仓库、agent/src、agent）：

```powershell
agent/.venv/Scripts/python.exe -m pytest agent/tests/unit/test_customer_harness_context_v1.py -q
agent/.venv/Scripts/python.exe -m scripts.evaluation.customer_harness_context_v1 prepare
agent/.venv/Scripts/python.exe -m scripts.evaluation.customer_harness_context_v1 check
```

prepare只执行脚本模型/真实SDK与本地tokenizer，不访问网络/数据库；已有输出拒绝覆盖。check只核对材料及准备hash，不重跑模型。脚本接线成功不能被写成理解通过率，输出质量/真实usage保持null。真实模型/故障驱动就绪状态分别显式记录。
