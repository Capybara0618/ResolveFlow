## 1. 唯一主链路

2026-10-22 用户授权[后端深化与商品评价](backend-deepening-v1.md)：先开发文档/预期图，再按小步完成正式查询与 Redis 接线、已签收本人订单行评价/商家回复、评分摘要缓存/账号限流以及模拟付款后台恢复。沿用三 Java 服务，评价归 Commerce，Java 持续拥有资格/版本/资金；评价不作为退款事实。未引入库存、营销、真实支付或新微服务，旧数据/冻结实验保持。

2026-10-20按用户授权接入[持久会话与独立人工核查](customer-support-workspace.md)及[Agent只读咨询/来源与确认共享报告](customer-agent-implementation-v1.md)，复用Case服务、唯一AgentScope循环和现有双端网页；人工咨询不创建退款Case/授权。聊天退款确认后续接入，原三Java+Python与资金职责不变。本批工程以脚本模型和真实本地dense检索验证，真实模型问答质量单独评测。

2026-10-14用户授权先实现[物流场景模拟器](logistics-simulator.md)：本地工具为已模拟发货订单追加运输/延迟/签收/丢失/未知事件，并提供可恢复查询故障，供客服设计与评测设置事实。只推进版本、不覆盖历史、不改资金/原实验；继续Commerce内模拟适配，不新增履约微服务或公开物流编辑入口。实际实施状态看todo顶部。

2026-10-12用户明确客服重构中的人工咨询不限于退款。设计纳入订单行关联的咨询会话及独立咨询核查单，商家通过现有工作台异步核查/回复，客户在原会话查看并补充；之后客户确认退款摘要才创建/接续原退款工单。商品切换使用独立咨询上下文并保留本人历史，转交前预览摘要/材料及相关原文范围。细化见[多租户客服草案](customer-agent-multitenant-v0.md)，当前未实施；不改变原退款动作/审批/金额约束，不扩实时坐席聊天或新微服务。

2026-10-03用户进一步批准[三角色合并](merchant-role-merge.md)：售后专员与商家管理员合并为商家；基础可用账号14个，新申请自动绑定本店唯一商家账号，商品/订单/售后统一工作台。取消新环境人员协作入口，保留退款/权限/版本约束和历史兼容；只转换账号/归属，不再次清空交易。

2026-10-03用户新增批准[干净演示基础管理](demo-foundation.md)：三店30商品45SKU、20个简短演示账号、独立平台管理员、受控商家/买家创建及本商家商品管理；明确授权备份后清理当前隔离演示环境，初始化不预造交易/退款。该授权不涉及共享环境、Git历史或旧验收报告，不扩展真实支付/库存/移动端/开放自助入驻。

2026-10-03用户批准多商家购物上游，见[实施对应](marketplace-implementation.md)及[目标图文合同](ui-marketplace-v1/README.md)：平台买家可买多店商品，跨店本人订单/申请；公共商品目录、按店购物车/单店多行草稿与模拟付款、本商家模拟发货接入原售后。沿用三个Java进程与模拟外部系统，不升级完整商城/库存/营销/真实支付/公开入驻/移动端。下列售后主链与资金约束保留；多行限制在第四批先定义并验证行级资格/剩余额度，未发货政策在第五批追加不可变版本，不能按图片提前放开。

用户提出退款诉求 → Agent自主调查订单/物流与政策 → 缺证追问或转人工 → 形成有引用的方案 → Java复核及必要审批 → 模拟退款可靠执行 → 工单展示结果与调查轨迹。

核心处理物流异常与商品损坏退款；错漏发、补发、库存、退货入库不实现。用户单方损坏陈述必须人工核验，不开发图像识别。退款只支持一个订单行全部数量、原行实付金额、CNY整数分。不支持行内部分退款或迁入历史混合售后。用户批准的购物上游允许同一新多行订单各行独立整行退款；本行槽和整单余额同时复核，见[多行规格](cart-multiline-checkout.md)。

## 2. 必做与非必做

| 能力 | 核心版必须交付 | 非核心：未经新授权不启动 |
| --- | --- | --- |
| Java | Gateway、Case、Commerce，独立业务库、鉴权、事务、索引与一项有证据的查询/缓存优化 | Fulfillment独立部署、库存、补发、跨动作权益Saga |
| 执行 | 退款幂等、金额预留、Outbox/inbox、UNKNOWN对账、旧授权拒绝 | 跨服务reserve/start/commit/release权益协议、执行中取消 |
| Agent | 单Agent动态决策、真实MCP、政策检索、有限追问、人工接管 | 多Agent、自进化、Skills市场、模型路由平台 |
| Harness | 分层上下文、预算/防循环、引用验证、调用记录、受限持久恢复 | 通用插件框架、任意版本热迁移、复杂任务调度平台 |
| 回放 | 选定完整合成轨迹的strict离线回放，明确不支持的记录 | counterfactual-recorded/world、合成世界回放器 |
| RAG | 商家/版本硬过滤、真实dense检索、BM25基线、引用校验 | hybrid/RRF/rerank全家桶、HNSW、四组强制消融 |
| 评测 | 一组固定workflow基线、核心Agent对比、代表性故障与安全测试 | 原240+60+120及每组3次的全量研究矩阵 |
| 展示 | 工单/审批/轨迹轻量界面，关联日志及有限指标 | 多角色完整管理后台、全套观测集群、商业级运营功能 |

缩减能力后必须缩减对应主张：不写“跨动作权益”“补发Saga”“反事实回放”或“生产高可用”。同一保留链路内的权限、资金和故障语义不能随意裁剪。

## 3. 部署与已有资产

2026-10-01用户批准[双端与多人协作补齐方案](product-completion-review.md)：在个人项目范围内增加两逻辑商家持久账号、客户申请工作台、领取/转交/接管与最小商家人员管理、站内待办。上述最小双端能力取代表中“多角色完整管理后台”的笼统延期描述；仍不做公司级IAM、公开入驻、租户计费或商业运营平台。本次网页体验统一人工最终审批，Agent只提供建议；不据旧自动路径完成标准增加新的自动审批。资金不变量、进程与模拟外部系统范围不变。

目标为Gateway + Case + Commerce三个Java进程与一个Python Agent服务。Case/Commerce各自MySQL库，Agent用AgentScope 2.x Python SDK、PG领域运行快照/调用账及pgvector，Redis用于非权威缓存或入口限流，RocketMQ用于退款命令/结果。非Agent框架继续使用已实测版本锁；仅AgentScope及必要适配由AS01先验证、AS02再锁定，不重开整个T00。

物流作为Commerce内明确标识的模拟外部数据适配模块，不冒充真实承运商接口；不再维护独立履约数据库。退款provider-stub仍需持久化和可注入故障，但不计核心微服务。

Nacos、Sentinel及完整OTel/Prometheus/Grafana/Tempo不是核心交付门槛；保留已验证依赖，默认核心运行可用Compose DNS/显式服务地址，不依赖这些配套。不能为瘦身全量重搭脚手架。

已有fulfillment骨架、v1协议、fixture及测试保留为兼容资产，默认不部署，不据此宣传完成该能力。AS00–AS02保留为AgentScope迁移历史；是否完成某项能力以当前账本和验收证据为准，不因文档更新自动成立。

## 5. 核心完成标准

1. 用真实业务服务与持久退款stub完成自动退款和人工审核两条路径。
2. 相同诉求配不同证据可改变模型后续行动；没有隐藏的固定全量工具链。
3. 越权、重复退款、旧revision、UNKNOWN和worker崩溃均有可定位测试。
4. 有冻结的真实模型对照报告、成本/失败分母、少量strict回放包及一个查询性能对照。
5. 本地可重复启动，能讲清5个演示中的实现和取舍；每项简历主张关联代码与证据。

核心版通过即可称“核心版完成”，不必补齐延期项。目标是若干可深入解释的亮点，不承诺必须写满某个条数；不用减少测试断言来营造规模更小。
