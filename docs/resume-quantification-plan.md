## 3. RAG 五组对照

| 组别 | 路径 | 固定配置 |
| --- | --- | --- |
| A | BM25 | 现有jieba与rank-bm25，按原来源范围过滤 |
| B | dense | 现有 BAAI/bge-small-zh-v1.5，512维，沿用实际snapshot |
| C | BM25→rerank | BM25前20候选，BGE-reranker-base重排 |
| D | BM25+dense→RRF | 每路前20，RRF常数60，输出融合前20 |
| E | BM25+dense→RRF→rerank | 对D的前20进行同一reranker重排 |

各来源可用块不足20时取全部。重复候选按来源/快照/子块ID合并，RRF使用排名而非原始分数相加；输出前三和前五。reranker默认CPU、FP32、batch_size=8、max_length=512，记录实际输入长度及截断；评分输入不改写原文，最终证据仍沿原完整来源读取。实际模型revision在下载后写入本轮manifest。索引向量可以预计算；计时中的query向量不从历史报告缓存读取。

### 指标定义

一条query可有多个等价充分依据集合：集合内为“且”、集合间为“或”。复用来源审查的块/表格行定位和覆盖逻辑。

- 单query `Recall@3 = max(各等价依据集合被前三覆盖的原子项数 / 该集合项数)`；主报告对17条完整可答query求平均。
- `完整依据命中率@3 = 前三找齐至少一个完整充分依据集合的query数 / 17`。
- `MRR`使用首个相关证据子块在完整排名中的倒数，未找到为0；报告@3/@5截断值及完整候选值。
- 先报告检索子块直接覆盖，再附上沿现有8000字符规则展开父章节后的覆盖，避免将两个结果混成同一指标。
- 计时包含query编码、实际检索/过滤、融合和重排。各组先做5次预热，随后29条×3轮；记录逐请求时长、均值及p95。模型首次下载/加载和文档索引不计入在线查询耗时。

每轮轮换五组顺序，共用同一资源设置。不做大规模调参或新增HyDE、多查询、GraphRAG。本轮要得到可解释的五组比较。

### 方案选择及商城补充

按完整依据命中率@3、Recall@3、MRR依次选择；质量相同选延迟更低的方案。使用已有样本作工程候选选择即可，不将本轮包装为盲测研究。

商城60条查询比较当前dense与外部选中方案：质量测一次、计时测3轮；再由完整Agent对照记录实际query。商城采用质量更好、同质量时更快的方案，固定后供两组Agent共用。外部方法胜出不要求商城也胜出；简历可分别展示外部检索收益及业务接线。

复用[外部检索与融合代码](../scripts/policy_fusion_eval.py)、[结构实验记录](../reports/rag-structure-v1/README.md)及来源缓存，主要新增统一计时、reranker和五组汇总。

## 4. Agent 自主调查对照

### 两组定义

- 动态组：唯一生产AgentScope循环，模型按Observation决定工具与终局。
- 固定组：评测专用固定流程，读取订单→物流→材料；由同一LLM基于已读事实生成政策query→调用同一政策检索→由同一LLM形成终局。分页沿现有有界分页读完。读取失败保留为Observation，继续由模型判断建议。
- 固定组复用同一上下文构建、工具身份、来源引用、最终verifier与一次有限纠错；不另写一套业务判断。它不调用退款/审批，也不替换生产循环。一次纠错仅修正建议，不变成第二条动态调查循环。

两组共同使用实际 `deepseek-flash` 配置、temperature=0、JSON输出、单次输出上限1024、单run模型调用上限12、同一deadline及工具边界。记录实际请求参数和provider别名，模型用量沿现有账本累计。基础规则、来源信息和可选输出动作相同；工具选择方式不同。

### 样本与评分

32例每组各2次，每组64次，共128次。按场景逐对执行，第一轮固定→动态、第二轮动态→固定；每次使用独立实验run和相同源快照。

正式运行前按输入事实标记复杂子集：存在冲突、资金占用/UNKNOWN、上游失败或资料不足、政策条件/例外、人工核验依赖中任一项即为复杂。形成逐例分类表，不依据结果选择子集。

一个有效建议须满足动作合理、事实有依据、政策适用、补证/核查责任可执行。合理转人工可算有效；未形成有效建议的Harness停止、超时和异常计入全部64次分母。原自动动作检查另报，简历“建议准确率”指本轮有效建议率。

报告每组：总体有效建议n/64、复杂子集有效处理n/M、每家族结果、平均模型/工具调用、输入/输出token、案例耗时均值/p50/p95。提升百分点为动态比例减固定比例。保存两次逐例结果与代表性轨迹，不只保存聚合数字。

正式128次前用4个现有代表场景、两组各一次验证接线，8次作为开发试跑另报；试跑不进入正式成绩。依赖或输入需要修复时，在正式运行前统一完成，随后固定版本，不按正式结果继续追加运行。

## 5. 版本化授权：8类×10轮

| 场景 | 竞争或失效条件 | 预期 |
| --- | --- | --- |
| V1 | 客户补证提交后使用原授权审批 | 原revision被拒 |
| V2 | 人工核验更新后使用原授权审批 | 原revision被拒 |
| V3 | 授权已批准、尚未消费时更新材料，再消费原授权 | 原授权失效，资金未预留 |
| V4 | 补证与审批竞争，用屏障使补证先提交 | 旧审批不能通过 |
| V5 | 更新输入与消费竞争，用屏障使更新先提交 | 旧消费不能成功 |
| V6 | 授权撤销与消费竞争，用屏障使撤销先提交 | 已撤销授权不能消费 |
| V7 | 新revision建立后，旧run终局迟到并尝试使用旧方案 | 旧结果不覆盖，也不建立可用旧授权 |
| V8 | 连续两次材料更新后分别尝试rev1/rev2的授权 | 两个旧版本都失效 |

每轮同时准备独立的当前有效授权作正向对照；另检查消费先提交时更新输入应被拒。使用现有Java服务/真实MySQL测试基础，屏障固定竞争窗口，不靠随机sleep碰运气。

分母是实际过期授权尝试数：V8一轮有两次，因此80次场景实验中默认有90次过期尝试；有效对照80次。报告分别计数。核对服务返回、授权消费标记及资金状态；拦截率目标100%，非法消费目标0。

复用[审批测试](../java/case-service/src/test/java/com/resolveflow/caseservice/casefile/ReviewDecisionApiTest.java)、[方案复核](../java/case-service/src/test/java/com/resolveflow/caseservice/casefile/ProposalReCheckApiTest.java)及[证据核验](../java/case-service/src/test/java/com/resolveflow/caseservice/casefile/ReviewedEvidenceApiTest.java)，需要的竞争测试追加在本轮专用文件。

## 6. 可靠退款：6类×10轮

| 故障 | 固定操作 | 核对 |
| --- | --- | --- |
| F1 重复退款命令 | 同操作命令投递10次 | 本行一次成功、同一外部操作 |
| F2 同行并发 | 同行10个并发消费/接受请求 | 一份有效预留与一次成功 |
| F3 跨行并发 | 同订单两行并发退款 | 两行各一次，整单余额一致 |
| F4 成功响应丢失 | provider已持久成功后丢失响应 | UNKNOWN保留占用，原操作查询收敛 |
| F5 资金结果持久后中断 | Commerce结算后、结果发送前终止进程再恢复 | 不重复扣账，结果事件最终到达 |
| F6 结果重投 | 同退款结果投递10次 | inbox与Case终态只应用一次 |

使用真实Case/Commerce、MySQL、MQ与持久模拟provider，专用合成订单/标识及隔离测试环境。每轮最多120秒等待预期终态，超时保留为未收敛。核对provider真实成功记录、退款操作、行槽、整单账本与本地事件。

重复成功笔数按每行独立成功退款交易数超出1的部分累计；重复查询或同幂等交易回执不计新交易。超额笔数按出现`已退+预留>实付`的订单计，另记最大超额金额；预留/结算边界都读回核对。UNKNOWN收敛率以实际进入UNKNOWN的操作为分母。正常终态达成及耗时另报，目标重复/超额0。

复用[多行资金测试](../java/commerce-service/src/test/java/com/resolveflow/commerce/refund/MultiLineRefundDatabaseTest.java)、[消息消费测试](../java/commerce-service/src/test/java/com/resolveflow/commerce/messaging/RefundCommandConsumerApiTest.java)和[既有退款链](../java/case-service/src/test/java/com/resolveflow/caseservice/casefile/RefundChainSystemTest.java)。单元/HTTP桩接线与真实故障实验分别记录。

## 7. Harness：恢复请求与token同时收集

采用既有三个窗口：模型返回但未落库、模型结果已落库、工具结果已落库且尚未进入下一模型调用。每窗口5对；每对两组都经过相同前置任务与中断，随后分别执行持久恢复与从头重新调查，共30次故障运行。

先用mock/HTTP桩验证故障点、调用计数和fence，再用真实LLM运行这15对并收集usage；mock试验不填真实token结果。两组从相同源事实出发，使用独立实验run，保留相同的原deadline和中断前累计预算，从头执行组重复此前调查，不重置生产run记录。外部读取次数也计入报告。

统计仅以中断后的新增调用为恢复收益：

- `请求减少量 = 从头执行新增模型请求 - 持久恢复新增模型请求`，同时报告总数、平均每对及各窗口结果。
- 输入、输出token分别求和；`token降低比例 = (从头执行新增token - 恢复新增token) / 从头执行新增token`。汇总总token比例与输入/输出分项；两组完成率、结果质量和耗时一起报告。
- 中断前已发生的请求/usage和未取得usage的未知请求也保存，未知不当0，不估算成真实计费。供应商实际usage是token依据，费用不是本轮主指标。

复用[跨进程故障验收](../agent/tests/integration/test_c09_acceptance.py)及[恢复报告](../reports/c09-production-recovery.md)。strict复用已有18种轨迹；若生产Python源码/manifest改变则导出新版本包，旧包保留。本轮生产Python源码与锁未改变，重跑当前18包并核对绑定，不伪造新的导出版本。匹配需重新处理记录并核对动作、引用与终态，另检查缺记录、篡改和禁网；报告m/18及首个差异。

## 8. Redis与SQL：三条件性能及故障回源

复用[现有压测入口](../scripts/c11_review_benchmark.ps1)及[测量报告](../reports/c11-review-query.md)。默认窗口已有30/60秒，但脚本当前仅2轮；实施时改为本轮显式3轮参数，不使用`-Trial`成绩。

- 数据：独立测试schema，20000工单、4000待审、2商家；分布沿现有80%商家一首页、10%下一页、10%商家二首页，seed=42。
- 正常三条件：原索引且缓存关；优化索引且缓存关；优化索引+2秒TTL缓存。各10/30并发、30秒预热、60秒测量、3轮，共18个测量窗口。每轮轮换条件顺序，记录机器、JVM/MySQL/Redis资源与配置。
- 指标：成功请求p95、成功RPS、总错误率、Mapper实际查询数/成功请求、缓存命中率。每轮原始时延保留；简历采用同并发下3轮指标的中位数，报告同时展示各轮及汇总请求分布。索引收益A→B、缓存收益B→C分别计算，避免混称。
- 故障四条件：热key到期、Redis断连、Redis命令超时、故障解除后恢复。32并发，每条件预热10秒、测量30秒、3轮；回源K=8、等待100ms沿当前实现。记录真实回源峰值、拒绝率、延迟及恢复后的正常请求。受控阻塞数据库的并发测试另证明压力足够时峰值仍≤8。
- 冷缓存样本与热稳态、成功时延与503时延分别列出。审批和金额复核继续读取权威数据库，列表缓存不是授权来源。
