## 维护方式

- 出现架构或职责边界调整、通用模块缺陷、重要实验结论时，随相应工作批次补充条目；普通变量改名等无需记录。
- 每条保留业务问题、实际症状、排查证据、根因及确认程度、方案取舍、实施内容、验证结果和经验。关联规格、报告、源码或已核实的提交，避免只留下结论。
- 先有方案、尚无实现或真实结果时，明确记录为设计选择或待验证假设；后来补上带日期的结果，不抹掉原失败或把离线重放改写成真实成功。
- 历史报告不随最新结论覆盖。本文件归纳经验，具体逐次命令和完整输出继续留在报告中。
- 面试表达从实际记录提炼，明确个人项目、合成业务和模拟支付的范围。工程测试、真实模型、真实网页和性能测量分别描述；不同版本、数据集和评分条件不直接计算提升率。

每个新条目可以沿用以下结构：

1. **背景与问题**：用户要完成什么，原方案在哪个场景遇到什么困难。
2. **定位证据**：实际请求、工具Observation、状态、回答和错误反馈说明了什么。
3. **根因判断**：区分已确认直接原因与设计层假设，说明排除了哪些有证据的解释。
4. **方案与取舍**：考虑了什么，为什么选择当前方案，成本是什么。
5. **落地变化**：调整了哪些职责、合同或模块，哪些原有机制被复用。
6. **验证与后续认识**：实际做了什么验证，哪些通过、失败或未验证。
7. **可复用经验与面试表达**：给出具体经验，能经得住来源、实现和结果追问。

## E01：客服Agent职责分离与运行编排

### 背景与演进路径

用户围绕一个订单行自由表达物流、商品、退款或人工咨询诉求，允许插问、暂停、恢复、纠正和撤回。系统要按需要读取业务事实与政策，并在本人确认后才进入正式申请或共享流程。

| 版本 | 主要设计 | 模型与程序的边界 |
| --- | --- | --- |
| single | 一套模型决策协议中同时处理任务理解、事项变化、工具选择和答复 | 已有Harness、预算、来源和发布检查；模型承担较多语义及结构声明 |
| staged-v1 | 先理解，再进入工具调查与回答循环 | 理解明确focus/needs等；模型仍输出事实字段、操作步骤、引用及摘要等声明，程序校验并渲染 |
| orchestrated-v1 | 理解→调查→组织回答，由程序维护证据就绪与回答装配 | 模型处理语义理解、自主选工具、相关政策引用和原因；程序装配确定性事实字段及页面操作，并沿原规则发布 |

这里的“阶段”是同一Agent运行中的职责分离。一条用户消息可能消耗多个模型请求，ReAct次数取决于工具选择与观察，不是三个阶段等于三个Agent或固定三次模型调用。

### 第一类坑：工程桩能执行，真实模型却不遵守动作协议

2026-10-21的44轮自主组和44轮固定流程组都没有发布答案。176个真实模型决策缺少顶层`kind`，解析在识别动作前失败，业务工具和RAG均未执行。源码核对发现精简提示时删掉了完整动作示例，纠错又没有明确指出缺失的字段。

**已确认的是动作协议无法解析；“模型单次职责过多”是设计层问题假设，不能拿这一次失败证明它是唯一原因。**这批数据也不能用于判断RAG检索或自主调度是否优于固定流程，因为两组都未进入调查。

经验：验证真实模型收到的请求和原始输出，先分清协议错误、取证错误和回答错误，再讨论架构。详见[原评测与诊断](../reports/customer-agent-eval-v2/README.md)。

### 第二类坑：拆出理解阶段，接口负担仍可能阻断业务

2026-10-22做了同批各6轮的single/staged-v1真实比较：single发布4轮、完整满足4轮；staged-v1发布5轮、完整满足4轮。两组都没有完整通过签收四轮对话。

两阶段在暂停原事项、回答插问时有可观察的局部收益。但随后模型把记忆替代目标写成字符串或助手建议文本，无法满足旧陈述ID协议；另一条混合问题漏ORDER，拿商品展示金额称为实付。拆阶段没有自动解决引用管理、依据选择和事实资格的问题。

经验：把确定性的陈述ID管理交给程序，模型表达原句和语义关系；来源具备和字段合法仍需独立核验。该比较同时改变了阶段与needs检查，不能把全部差异归因于拆阶段。详见[配对比较与离线诊断](../reports/customer-agent-staged-live-v1/README.md)。

### 为什么选择程序参与编排

最近的设计目标是减轻模型处理协议细节的负担，同时保留按Observation选工具的自主性。

| 考虑的做法 | 本次取舍 |
| --- | --- |
| 继续把更多规则放进一次输出 | 没有解决语义、事实声明、步骤和摘要合同同时耦合的问题；仅补规则不足以承担职责调整 |
| 固定读取全部工具再回答 | 对简单入口或政策假设也读订单/物流，成本和依赖增加；本项目仍需要按场景调查 |
| 多Agent或额外模型分工 | 已定位的缺陷多在接口和职责衔接，缺少证据说明额外协作能解决；本次采用单Agent内部阶段分离 |
| 程序管理就绪与确定性输出，模型自主调查和解释 | 采用。实现更明确，但程序与模型、旧校验及前端投影之间必须共享一致的业务含义 |

这些是基于本项目证据的取舍，不是对其他架构的普遍优劣结论。

### 实际落地了什么

- 理解阶段一次接受`EXPLAIN`、`PREPARE_REFUND`或`MERCHANT_REVIEW`目标，保留原事项、客户陈述和原文锚点。
- 程序逐事项维护合法已读来源、缺口和真实不可重试阻碍。依据未齐的提前回答返回缺口、继续原循环；每次调用仍计原预算，连续无进展有界终止。
- 订单和物流由Agent按观察选择工具读取，政策按需要调用RAG；程序通过原账本提供所需受控指南。READY仅说明必要来源具备，不证明语义正确或政策适用。
- 模型以`RESPOND`组织解释、相关政策引用和退款/人工原因。程序从当前来源选择确定性事实字段并装配操作，再走原引用、金额、完成及发布检查。
- 旧版已经有事实和步骤的程序渲染；此次进一步收回了这些字段和操作声明的装配职责，不应描述成此前完全没有程序约束。
- 调查阶段不投影正文，进入组织回答阶段后才流式投影；持久结果、manifest、预算、fence和Java的确认/金额职责沿用。

[设计合同](customer-agent-orchestration-v1.md)；主要实现：[orchestration.py](../agent/src/resolveflow/support/orchestration.py)、[stages.py](../agent/src/resolveflow/support/stages.py)、[engine.py](../agent/src/resolveflow/support/engine.py)、[navigation.py](../agent/src/resolveflow/support/navigation.py)。

### 一个完整的修复案例：模型把人工摘要只写在正文

2026-10-24有限真实验收中，一条人工请求已正确接受MERCHANT_REVIEW目标，ORDER/SHIPMENT/GUIDE依据齐备，却两次把拟共享摘要写进正文，遗漏独立`handoff_reason`，最终发布失败。

对比实际请求后发现：通用输出例子只有parts，原因字段在通用Schema中可选，当前goal对应的必填要求没有编译成具体输出示例。根因位于**已接受业务目标与实际模型输出合同的衔接**。

修复是在本轮system中按goal、生命周期和就绪状态生成完整输出示例及条件原因字段。没有把正文自动冒充摘要，也没有删除原校验。随后一条预先固定的不同措辞人工消息实际4请求、0修正成功，并完成客户确认共享及商家投影；原失败保留。这是对已定位合同问题的有限确认，不是整体通过率。

实现提交`f94ede7`；[原失败、离线修正及真实确认](../reports/customer-agent-orchestration-acceptance-v1/README.md)。

### 更大范围验证暴露了哪些新问题

2026-10-24固定新版执行14组44轮、131次真实模型请求：37轮发布，27轮完整满足业务判据，10轮已发布但有遗漏或错误，7轮未发布。全轮完整通过4/14会话。这是开发可见合成回归和Codex源审，不是独立盲测准确率，也不能据此计算相对最近staged-v1的提升率。

| 观察 | 根因定位 | 截至该批证据的判断 |
| --- | --- | --- |
| 隐私共享/默认接收人被归到OTHER或POLICY，出现错误私密建议 | 指南需求与领域分类不足；模型自报needs可漏项 | 未解决，不能称流程知识已完整 |
| 正确解释提到页面却被拒绝 | compose按intent装步骤，旧校验按正文页面标签要求步骤，两端含义不一致 | 是程序合同衔接缺陷，不能统称模型能力不足 |
| “目前没有已提交核查记录”的正确临时解释在最终回答消失 | `guide_only`根据仅GUIDE引用推断整段都是步骤，替换了全文 | 9个成功轮次至少一段被替换；需保留直接解释 |
| 长历史摘要没采用尾部纠正，旧照片陈述在假设澄清后仍生效 | 历史可读取和记忆有结构，不保证模型实际采用与正确替代 | 上下文机制存在，效果仍需业务验证 |
| 未发货规则漏版本1及ORDER_PAID | 本轮已读完整政策，生成解释省略关键前提 | 是回答完整性问题，不是RAG没召回 |

原始`first_retained_ms`只代表最后未reset的候选attempt。进一步按完整投影段是否保留到最终答案核验后，30轮有保留的流式段，7轮只能以最终返回作为稳定正文可观测时刻；失败轮没有正式首正文。完整44轮服务端完成p50/p95为3.76/6.38秒，37个发布轮稳定正文为3.04/4.40秒，均不是浏览器或生产p95。

### 从这次演进得到的经验

1. 职责分离应减少模型需要维护的确定性细节，同时保留理解、选择工具、处理不确定性和解释能力；阶段数量不是成熟度指标。
2. 程序校验也会出错。尤其要检查“理解目标→来源需求→操作装配→最终校验→流式/最终展示”是否共享相同合同。
3. 取证就绪、模型正常返回、正式发布、完整满足用户需求，是不同层次的结果，需要分别验收。
4. 先看实际模型输入、原始响应和Observation，再判断是上下文、工具、文献、协议还是渲染的问题。
5. 小规模功能链路成功后仍需多轮场景验证。保留失败、部分满足和未知范围，才能准确说明架构收益及后续代价。

可用于面试的表达：

> 我做售后客服时，最初让模型同时处理事项理解、工具选择和结构化答复。拆出理解阶段后，发现记忆引用和事实、步骤声明仍会阻断回答，便把证据就绪、确定性事实及操作装配收回程序，模型继续自主调查和解释。一次人工请求失败定位到目标没有编译成具体输出合同，修正后真实确认通过；扩大到44轮又发现旧页面校验和渲染与新合同冲突。因此我分别记录发布率、业务完整性和流式最终一致性，并用原始轨迹定位具体模块，而不只增加提示词。

追问准备：为什么用Agent而非固定流程；哪些规则应程序化；如何从观察决定下一个工具；READY为何不等于正确；为什么不加多Agent；不同版本成绩怎样公平比较。回答依据均可回到本条关联的报告与源码。

## E02：RAG先区分知识领域，再比较检索算法

### 问题与定位

客服回答不好可能有不同原因：查错了知识领域、文档没有适用规则、排序遗漏关键证据，或生成时丢了已读条件。必须沿实际query、命中文本、绑定商家/版本和最终回答定位。

2026-10-24轨迹中，“能否只共享几句话”需要应用指南，却被送去六条退款政策检索；未发货规则的版本1及ORDER_PAID已在结果中，回答却省略。前者应改善需求与知识域选择，后者应改善回答完整性，继续更换embedding不能直接修正这两类问题。

### 采用的取舍与证据

| 场景 | 采用/验证的方式 | 结果与代价 |
| --- | --- | --- |
| 商城绑定的小政策集合 | 受规则数/字节上限约束的完整输入；超限再走排序 | 实测每次6规则，9查询×10轮热态必要规则覆盖90/90；覆盖来自完整输入，会占模型上下文，不是排序击败其他算法 |
| 较大外部原始政策 | dense＋正文BM25＋标题BM25，RRF融合 | 17个可回答问题Top5完整证据16/17，正文BM25为13/17；Top3均12/17，仍有退化样本，非所有k都提升 |
| 运行效率 | 加载预热与工具热态、整轮Agent分开计量 | 独立商城热态p95 5.84ms；Agent实际15次政策工具p95 11.09ms；44轮完成p95 6.38秒，不能把整轮等待都归检索 |

外部比较用保留原文、原子证据标签和同输入缓存向量，没有新生成模型调用；不是商用问答准确率。CrossEncoder等已有实验资产可查，但本批默认路径没有临时加重排或GPU实验，不能将候选技术写成实际部署能力。

经验：技术取舍要匹配语料规模和业务知识类型；RAG是Agent按需调用的证据工具，不能替代实时订单/物流，也不能保证模型完整使用已检索条件。

## E03：评价Redis缓存如何处理迟到回填和依赖故障

### 问题与方案取舍

商品评价首页及评分可缓存，但评价编辑、商家回复后，旧读请求可能晚于新写入才填缓存。仅按同一个key删除再回填，无法表达读结果属于哪个数据版本。

2026-10-22采用商品epoch代际key：评价修改/回复和epoch在MySQL同事务更新；读取先验证商品可见性和epoch，缓存key带product/epoch。迟到的旧结果只会写旧代，不覆盖新代。默认首页及评分一起缓存30秒，更多页或自定义页大小直接查库。

**代价**是命中仍含一次epoch数据库读取，不能宣称数据库访问归零；收益要另测，不能用缓存存在推导延迟提升。回源入口共享8并发/100ms门控，避免缓存异常时无界打数据库。

### 依赖故障不能只用一种降级方式

评价读取缓存异常可回源，并受门控限制；评价写入限流则以已认证账号和动作执行Redis Lua原子计数，6次/60秒，Redis异常返回可重试503，不能退化成无限写入。业务唯一性仍由MySQL保证。

### 实际验证与经验

已有真实MySQL/Redis测试覆盖代际更替、旧代晚写、损坏JSON、并发门控及Redis暂停超时；真实HTTP与网页集中验收包含缓存和账号429。107项Java集中测试包含评价、缓存、限流和交易恢复等多个范围，不能把107全部说成缓存测试或压测。

经验：缓存优化要讲数据版本、并发和故障时的业务含义。一次缓存命中、正确性故障测试和压力测试证明的事情不同。
