# 候选产物冲突后的受控目标核对

2026-10-24，针对[十轮真实验收M02/2](../reports/customer-agent-close-v1/README.md)。模型正确生成给商家的摘要，却因理解阶段误选退款目标被程序要求改成退款原因。原话出处合同只能证明出处，不能证明操作类别。

## 运行合同

继续采用唯一AgentScope循环及orchestrated-v1。正常链路不增加模型轮次；COMPOSE提供的退款/人工产物与当前可用目标不一致时，程序撤回候选正文，返回GOAL_CONFLICT，使下一轮进入INVESTIGATE。此时只允许REVIEW_GOAL，不能直接读工具或发布。

模型根据当前用户原话确认或修正一个活跃事项的目标。字段包括task_id、previous_goal、goal、operation_request和reason。程序验证事项范围、旧目标一致、动作原话确实属于本轮，并重新执行TurnPlan合同；动作类别仍由模型判断，不能把关键词或原文匹配当作语义证明。允许确认原目标，避免盲信候选产物。

每run至多接受一次核对；再次产物冲突以GOAL_REVIEW_EXHAUSTED停止。无冲突时不允许主动改目标。格式纠正仍用原一次修正额度，目标核对不重置预算、deadline、manifest、权限或fence；额外模型请求计入原12次/120秒上限。

核对保留事项编号、客户记忆、陈述状态、原事件、已取证结果及原needs。改成退款准备时新增必要ORDER后重新检查证据就绪；不重复应用理解事件，不自行发送或建单。对应任务和对话事项intent同步更新。

恢复沿用原模型/工具journal，从原顺序重建核对状态；不新增旁路循环或假定SDK会话保存等于可靠恢复。旧run按原manifest保持，不静默升级。

## 验证与边界

先用原失败的三个模型决定（错误计划、订单读取、正确人工摘要）原样复现，再接一次核对与原正确摘要；同时覆盖陈旧目标、历史原话、非活跃/其他事项、确认原目标、二次冲突及新退款所需证据。真实PG中验证核对后的任务意图和调用序列可重建，重取租约后不新增模型/工具发送。候选正文撤回，核对JSON不投影给客户。

工程结果见[报告](../reports/customer-agent-goal-review-v1/README.md)。随后最多20次真实请求，固定3组4轮新措辞，覆盖人工摘要→撤回、能力咨询和退款准备；先冻结数据、判据、源码及权重，各轮一次，不追加追成功测试。原业务HTTP采用冻结合成快照、PG政策真实读取，只写独占临时run schema，不创建Case/核查单/退款。

小样本通过不能证明语义永不误判。若真实模型直接选对目标，没有触发核对分支，必须明确该分支只有离线SDK与PG恢复证据，不能宣称已观察到真实模型纠错。
