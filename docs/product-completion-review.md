用户已确认本文推荐方案并要求开始实施；第10节八项决定采用推荐值。本文是业务模块、规则、依赖和验收依据；实际进度仍只在 [tasks/todo.md 顶部](../tasks/todo.md)维护。新功能优先以离线和mock验证，不自动开展批量收费评测。

## 1. 项目应当交付什么

目标是一个桌面网页售后系统：多个客户申请退款，同一商家的多个审核员协作处理，Agent/RAG提供调查建议，客户和工作人员都能找到工单、完成各自操作、看懂最终结果。

基本链路：

```text
客户登录 → 本人订单 → 提交退款申请 → 我的申请与进度
                                ↓
                       商家的工单队列
                                ↓
                      Agent/RAG调查与建议
                                ↓
                      审核员领取并核对资料
                                ↓
              要求补证 / 人工核验 / 人工方案 / 审批
                   ↓                          ↓
             客户回答、新调查              模拟退款或拒绝
                   └───────────────→ 双方查看结果
```

“完整”以双方能从正常页面完成流程为准，不能仅以API可调用、测试数量、预制截图或准备好的待审样本判断。允许种子创建合成账号、订单和物流；申请、回答、领取、审批和结果查看应通过正式页面完成。

继续沿用个人项目边界：现有Gateway、Case、Commerce三个Java服务与Python Agent；桌面网页；一个订单行全部数量、原行实付金额的CNY模拟退款。不新增购物商城、真实支付、补发、库存、移动端、多Agent或企业级运营平台。

- 旧CXX/C12不会恢复；本文件模块名称仅用于讨论，不建立第二套进度账本。

以下根据2026-10-01源码和既有报告核查；本次没有重新运行业务链路或调用模型。

| 领域 | 已有能力 | 需要补齐 |

## 3. 角色、租户与关联关系

### 3.1 推荐角色

| 角色 | 负责的工作 | 访问范围 |
| --- | --- | --- |
| 客户 | 查看订单、申请退款、回答问题、查看结果、允许时撤销 | 本租户内本人的订单和申请 |
| 审核员 | 领取工单、核验、补证、人工方案、审批、跟踪异常 | 所属商家；写操作还受负责人和当前状态约束 |
| 商家管理员（新增建议） | 管理本商家账号、查看全队列、处理无人负责和转交 | 仅所属商家；不突破金额、授权或消费冻结 |
| 本地OPERATOR | 启动、导入、诊断等已有开发运维职责 | 不作为日常商家管理员入口，不自动获得新管理功能 |
| Agent服务身份 | 受run/case/revision限制的只读调查、建议回调 | 不领取工单，不管理账号，不审批或退款 |

商家管理员与审核员是两个职责。推荐管理员可以通过明确接管成为当前负责人，然后执行审核工作；不设置隐含的“管理员跳过流程批准”能力。

### 3.2 推荐关系

- 一个商家拥有多个客户账号、多个工作人员账号、多个订单和工单。
- 一个客户可以创建多张工单；每张工单明确属于一个客户、一个商家和一个订单行。
- 一个审核员可以处理多张工单；一张工单可由多人先后处理，但同一时刻至多一个当前负责人。
- 客户和审核员通过工单关联，不建立无业务依据的“客户—审核员绑定表”。
- 推荐首版保持账号绑定单一商家，沿用现有身份模型。统一消费者跨商家购物、员工跨租户兼职、租户切换留待另行确定。
- 租户采用现有共享业务表中的merchant_id逻辑隔离；客户不能通过请求参数伪造商家或申请人。

### 3.3 工单状态与负责人状态分开

继续使用现有QUEUED/ANALYZING/WAITING_CUSTOMER/PENDING_REVIEW/AUTHORIZED/EXECUTING/RECONCILING/终态。不要把“已领取、已转交”混入退款领域状态。

负责人变化是协作信息，不是退款新证据：**领取、释放、转交、已读操作不得增加input_revision，不重排Agent，不重算金额或替换政策。**新增独立协作版本保护并发写入；原case.version和authorization_version的审批校验继续有效。

## 4. 六个需要补齐的模块

### 模块一：商家与账号基础

目标：正常登录的多个账号来自持久化配置，明确属于哪个商家，角色与启停状态可管理。

实施范围：

1. 增加最小商家登记与账号持久化，复用现有密码哈希和JWT实现。商家由本地受控种子/导入创建，首版不做公开入驻或计费。
2. 平滑迁移现有演示用户名、merchant_id、customer_id和角色；保持历史审核actor可追溯。已有订单、工单和政策不批量改归属，不以清库替代迁移。
3. 用户名首版保持全局唯一，沿用“用户名＋密码”登录，避免引入未经设计的重名租户选择流程。
4. 给账号增加显示名称、启用状态和身份版本；登录后显示当前商家、姓名与角色，不能把所有审核员显示成同一个人。
5. 禁用和改角色必须作用于已有登录会话：相关服务通过受控身份验证检查当前状态/版本。不能只阻止下次登录，却让旧token继续写业务；具体校验方案先补契约，再接入Gateway/资源服务。
6. 新角色加入时审核所有“非CUSTOMER即工作人员”的旧检查，按动作明确允许角色，防止角色扩展放大权限。客户永远不能自行选择管理员角色。
7. 普通入口默认使用持久化账号；固定DemoAccounts可保留为隔离测试夹具，不能同时成为冲突的第二个生产账号权威。

验收：两个商家均可登录；每商家至少两个客户、两个审核员和一个管理员；A商家管理员不能创建或修改B商家账号；禁用后的旧会话不能继续业务写入；普通启动不依赖改Java常量新增账号。

### 模块二：客户工作台与退款申请

目标：客户无需知道内部编号，也能从订单开始完成申请、补证和结果查询。

页面范围：我的订单、申请退款、我的申请、申请详情四类页面/视图。

- 订单显示商品名称、规格、实付金额、商家和可申请状态。已有活跃工单给出“查看当前申请”，已成功退款给出明确状态，不能继续引导重复申请。
- 申请表展示固定全额金额，客户填写情况说明与文本材料；前端不允许任意输入退款金额。若新增“问题类别”，只作为客户主张，不能直接替代物流或人工核验事实。
- 创建成功进入申请详情；幂等提交与失败反馈沿用后端，不因重复点击创建多张活跃工单。初始材料提交失败要明确提示，不显示成全部成功。
- “我的申请”支持待补证、处理中、待审核、已结束等筛选及分页；列表和按订单查询都由后端按当前商家和客户筛选，不能在前端过滤商家全队列。
- 详情显示原始申请、提交材料、补证问题、回答历史、当前进度、人工理由和执行结果。用“待回答问题”卡片回答，question_id由系统关联，支持现有最多两轮/等待期约束。
- 客户可见内容单独定义投影：展示必要进度和可公开理由，不默认返回工作人员账号信息、内部完整工具记录、模型请求、租约/fence或审批内部依据。已有Case读取仍按兼容方式过渡，不能把共享页面简单复制后暴露所有审查数据。
- 接入已有授权消费前撤销能力；由服务端决定是否可撤销。消费后、执行中或UNKNOWN禁止撤销；不在客户端猜测“超时就是失败”。
- 刷新后可从列表重新找到申请；路由可保存当前case_id，身份重新核验。若保存会话，明确登出和过期处理，不在URL中传token。

首版推荐只支持文本材料。图片/视频上传是单独的范围决策，见第10节；不制作可点但不保存的假上传按钮。

验收：客户从订单页创建新申请，退出后重新登录仍可找到；能直接回答指定问题；另一个客户不能读取或回答；执行结果与服务端一致；不再需要复制工单UUID或手填问题ID才能正常使用。

### 模块三：审核队列与多人协作

目标：多个审核员知道哪些工单待处理、谁负责、自己下一步做什么。

推荐采用**公共队列＋领取制**，不做自动轮询派单或绩效系统。

| 动作 | 推荐规则 |
| --- | --- |
| 领取 | 只领取本商家、可人工处理、未被负责的工单；同一人重复请求返回当前归属；不同人并发只有一个成功 |
| 查看 | 本商家工作人员可查看公共详情；其他负责人存在时明确只读和姓名 |
| 人工写入 | 核验、补证、人工方案、审批和拒绝必须由当前负责人执行；原有状态、修订和授权检查同时成立 |
| 释放 | 负责人主动释放，工单回到无人负责；不改变业务状态；填理由并保留记录 |
| 转交 | 负责人或管理员发起，目标必须是本商家启用的工作人员，记录理由与协作版本 |
| 管理员接管 | 先显式改变负责人、记录原因，再执行人工操作；原负责人的旧提交失效 |
| 客户补证/新调查 | 推荐保留负责人；待回答期间不在“现在可审核”中显示，回答后的新调查不会取消归属 |
| 执行与终态 | 不提供新的批准/拒绝/核验；保留最后负责人用于追溯，退款仍由原执行系统推进 |
| 负责人被禁用 | 禁止其继续写入；管理员可释放或转交未结束工单；不自动发起新调查 |

队列新增“未领取”“我的工单”“全部工单”范围，与既有待审核/待补证/处理中/需关注/已结束阶段组合。我的工单再区分“现在可处理”“等待客户或系统”；显示申请人摘要、金额、提交时间、负责人和下一步，避免仅有描述和更新时间。

补充当前负责人、协作版本、领取/释放/转交记录；推荐用独立协作记录存储，不让所有权修改原始诉求或授权载荷。事务统一锁顺序，在人工作业写入时原子检查负责人、启用状态、协作版本和原业务版本；查一次负责人后无锁提交会留下转交并发漏洞。

现有人工写入口必须全部覆盖，不能只给新页面按钮加判断。Agent回调、客户回答、消费与退款结果处理不要求审核员持有领取凭证。单次操作是短事务，禁止把网络或模型调用放进领取/审批事务。

兼容策略：已有未领取历史工单可由审核员首次领取；旧客户端直接写入不能悄悄自动抢占，返回明确冲突并要求刷新。领取记录不等同于资金授权，不能创造第二套付款状态机。

验收：两个审核员同时领取只成功一个；另一人不可核验/审批；转交后旧页面提交失败且能刷新显示；客户补证后负责人保留，旧方案失效；领取/转交前后input_revision、run数量和模型调用数量不变。

### 模块四：双端待办、问题与结果同步

目标：客户知道需要回答什么，审核员知道新增哪些任务，双方看到同一个权威结果。

首版使用站内待办、详情SSE与队列定时/手动刷新，不加短信、邮件或新的消息基础设施。

- 客户待办：新的补证问题、审核结果、模拟退款成功或结果待确认。回答后待办更新；已读不等于已回答。
- 工作人员待办：新待审工单、转交给我、客户已回答、调查失败需接管、退款异常。公共队列与“我的工单”计数应来自真实查询，不能把当前分页条数称为总数。
- 无需为每次模型工具调用发送通知。一个业务事件重复投递不生成重复提醒；待办投影可从已有事务事件产生，不能让通知失败回滚已成立的财务结果。
- 用户详情明确区分“审核通过”“正在退款”“结果待确认”“退款成功”“明确失败”；界面显示模拟退款标识。
- 等待客户/Agent失败/执行失败的页面给出真正允许的下一步；终态只读。SSE断开后提供重新读取，不能假装持续实时。
- 客户补证、人工动作和退款回传后，双方详情与列表能刷新；切换账号或工单时迟到响应不能覆盖新页面。

验收：浏览器甲提交申请后，工作人员浏览器乙能在声明的刷新周期内发现；乙要求补证后甲出现正确问题；成功与UNKNOWN分别显示正确文案；重复事件不叠加待办；提醒和计数均不跨主体。

### 模块五：商家轻量管理

目标：管理员能维护本商家的工作人员和处理归属，避免项目只能靠改代码操作。

范围：

- 本商家账号列表、新增工作人员、启用/禁用、显示名称、角色维护；客户账号首版推荐种子或管理员创建，是否提供自助注册由用户确认。
- 禁止管理员改变账号所属商家、订单或工单申请人；不能通过改归属“修复”演示数据。不允许禁用/降级最后一个启用管理员导致无法管理。
- 支持管理员设置初始/重置密码，保留操作审计；密码不可回读，禁止持久存储明文。首版不做邮件找回、OAuth或复杂组织树。
- 工单全队列与释放/转交入口复用模块三，不另造管理端审批状态机。
- 政策只读展示当前已导入的商家政策、有效时间和索引状态；缺配置如实提示。正文发布仍通过现有受控导入，不实现在线编辑/发布平台，不用新政策覆盖历史工单绑定。
- 显示必要的真实待办与异常数量；不建设大屏、团队绩效、客户画像或虚构退款总额。

验收：管理员新增的第二审核员可以登录、领取；角色修改/禁用及时生效；跨商家管理拒绝；无审批特权绕过；缺政策不会借用别的商家政策；历史记录仍显示稳定actor身份。

### 模块六：数据准备与完整流程验收

目标：启动后有完整可体验的数据，验证覆盖真实使用关系，而非只有固定截图工单。

数据范围：

1. 两个商家，各两个客户、两个审核员和一个管理员；账号、订单、物流、政策、索引归属一致。
2. 修复M-1002/M-2002错配时选择受控新配置或补齐对应账号/政策，保持已导入政策不可变、已绑定工单不改写。不得改已执行迁移或原政策hash来凑一致。
3. 每个客户准备少量未申请、可申请的订单行，另有成功、拒绝、待补证、UNKNOWN等只读样本；当前准备好的成功退款行不能作为可反复审批订单。
4. 导入可重复运行而不重置已处理工单；需要再次体验时显式新增合成订单或数据集，保留原结果，不重置金额账或运行预算。
5. `.\demo.ps1`、`-Live`、status、stop沿用现有入口，页面标明合成数据与模型来源。启动本身不得自动创建并调查大量新申请。

集中验收应包含：

| 场景 | 通过条件 |
| --- | --- |
| 两个客户提交 | 均从正式订单页面新建，分别在本人申请列表可查；另一客户不可读 |
| 两个审核员处理 | 同商家队列看到真实申请；分别领取，当前负责人独立，人工操作可追溯 |
| 同单并发领取 | 一胜一冲突；冲突方只读，不能绕过旧核验或审批接口 |
| 补证闭环 | 审核员提问，客户页面直接回答；新修订/run携带问题答案，负责人保留，旧审批拒绝 |
| 批准闭环 | 人工批准有效授权，模拟执行成功，客户与审核页均显示最终成功；不会重复退款 |
| 拒绝与撤销 | 理由对客户可读，工单进入正确终态；允许时撤销有效，消费后撤销被拒绝 |
| 转交与禁用 | 转交后旧负责人写入失效；被禁用账号旧会话无法写；管理员能处理无人负责工单 |
| 两个商家 | 两边都有可运行链路；订单/申请/政策/人员/待办读写都不串租户 |
| Agent失败 | 工单仍可查、可领取和人工接管，不显示为调查成功 |
| UNKNOWN | 真实显示待确认，冻结输入，不换operation重付；对账仍沿既有机制 |
| 刷新与重启 | 登录、刷新、退出再登录和保留卷重启后，申请/负责人/决定/结果可重新找到 |

多角色网页验收用不同浏览器会话，不能在同一会话反复覆盖身份后宣称同时协作。主要协作和权限矩阵先用mock，不凭mock宣称模型语义正确；最终选择少量新合成申请跑真实DeepSeek，记录失败和usage。不要为每个账号组合重复付费。

## 5. 页面信息结构建议

| 工作台 | 首版导航 | 默认进入 |
| --- | --- | --- |
| 客户 | 我的订单、我的退款申请、待回答问题 | 我的订单或我的申请，无需输入工单ID |

页面必须提供空列表、加载、过期登录、403/404、版本冲突、网络中断、调查失败和终态说明。首版仅按桌面浏览器验收，参考图指导布局，不能据图虚构会员、优惠券、支付流水、媒体真实性或审批额度。

## 6. 数据与契约原则

不重构已有交易核心表。以下为设计方向，不是最终Schema或已实现端点：

| 数据/契约 | 所属位置与原则 |
| --- | --- |
| 商家与账号 | Case侧最小持久化身份；稳定account_id/登录subject、merchant_id、role、customer_id、显示名、密码hash、状态、身份版本；不跨库直读 |
| 工单协作 | Case侧独立负责人、协作版本和操作历史；与人工写入事务校验；不得改变材料修订 |
| 客户申请列表 | 新增按当前身份读取的分页契约；按merchant/customer及筛选查询，索引对应实际排序；不能复用管理员列表返回全部再过滤 |
| 客户详情与问题 | 最小客户投影、待回答/已回答问题及回答关系、公开理由、允许动作和阻塞原因；来源为Case持久事实 |
| 审核队列投影 | 添加申请人显示摘要、已校验/订单金额的来源标识、负责人和可处理状态；不可跨服务直接读Commerce数据库 |
| 站内待办 | 接收人或角色/租户范围、来源事件、去重键、已读/待处理语义；与原始事件可追溯 |
| 管理接口 | 本租户账号管理、审计和政策只读；不接受前端选择任意merchant来扩大权限 |

新增API的路径、字段、空值、权限、分页、幂等、版本及错误码先写入核心契约，并同步Java/Python消费处、前端类型与fixture。既有端点有意改变权限时要列兼容影响，保留测试，不能只改按钮。

数据库只追加迁移；新的必填字段需旧数据回填/兼容策略，历史actor缺失不能臆造。身份禁用检查和协作权限覆盖Gateway、Case以及相关Commerce入口；内部Agent服务凭证保持原独立权限，不套用客户会话。

## 7. Agent/RAG与退款核心的复用边界

本轮不重做AgentScope迁移、现有工具、向量检索、原始记录投影、补证快照或资金可靠执行。

- 用户新申请、真正的新材料/回答/核验才按已有规则产生新修订调查。负责人、显示名称、已读和列表筛选不产生模型调用。
- 客户材料仍是非可信内容；客户填写的原因类别不等于已核验损坏/丢失。模型建议和置信度不是授权。
- 缺证可追问或人工接管；Java继续决定允许动作、金额、引用及授权有效性。多人机制只限制谁能进行人工动作，不放宽业务条件。
- 并发、补证、禁用和转交不能使旧revision/授权重新有效；授权消费后继续冻结输入，UNKNOWN保持原operation与占用。
- 当前真实模型样例有受控失败和人工建议，不能据此承诺自动判断准确率。体验完整度与模型质量分别报告。
- 现有文档曾描述自动处理条件，本方案不凭旧文档推断当前存在完整自动退款路径。推荐本次演示统一人工最终审批，是否新增/启用自动审批须单独确认与核验。

## 9. 首版退出范围与可选增强

**首版退出**：公开商家入驻、租户计费、多组织/跨租户员工、商城购物下单、真实承运商与支付、部分退款、多级审批/额度、执行中取消、退货入库、补发、库存、绩效/SLA平台、短信邮件、移动端、图像真实性识别。

**可选但需要额外确认**：图片/视频附件、本地客户自助注册、在线政策发布、客户拒绝后再次申诉、统一消费者跨商家账户。没有确认时不能画假入口，也不能以这些企业级或扩展能力阻塞推荐首版闭环。

若选择附件，需另写存储与下载权限、大小/类型限制、元数据、失败恢复、来源引用及删除保留规则；不能把本地路径放进材料当上传成功，不将文件已上传等同于人工已确认。没有新增视觉模型时Agent只能使用已保存的描述/人工核验事实。

## 10. 已确认的业务决定

2026-10-01用户批准下表推荐值；后续用户可以逐项修改，其他常规实现细节在已批准范围内由执行者处理。

| 编号 | 已决定的问题 | 已批准方案 | 选择其他方案的影响 |
| --- | --- | --- | --- |
| 1 | 首版是否保留多商家 | 两个商家都能跑完整流程，逻辑隔离；不做公开入驻 | 只做单商家可减少配置，但不能再以完整多租户体验为目标 |
| 2 | 账号怎样产生 | 客户由种子/管理员创建；管理员可管理工作人员；不做公开注册 | 自助注册要增加安全默认角色、商家归属及注册流程 |
| 3 | 谁决定最终退款 | 本次网页演示统一人工审批；Agent只建议 | 自动处理需要明确规则、路径和单独验收，不能由模型自行批准 |
| 4 | 工单怎样分工 | 公共队列＋领取制；负责人可释放/转交；管理员可接管 | 自动派单要增加分配规则、负载和人员可用性管理 |
| 5 | 补证期间谁负责 | 保留负责人，等待态从可审核列表移出；新结果回来后恢复待办 | 回公共队列会改变接续和协作规则，必须明确何时释放 |
| 6 | 管理员是否参与审批 | 显式接管后可审核，始终遵守同一资金和状态约束 | 纯管理角色可更简单，但要有人处理孤立工单 |
| 7 | 首版材料形式 | 文本＋人工核验，先完成完整闭环 | 如果必须上传图片/视频，应把附件模块列入正式范围与批次 |
| 8 | 客户是否需要跨商家统一账户 | 首版一个账号绑定一个商家，符合现有模型 | 跨商家统一账号需重设计成员关系和订单归属导航 |

推荐首版完成标准：**你无需脚本代替客户回答、无需手填内部ID、无需改Java常量加审核员，就能在两个商家下分别演示多客户提交、多审核员协作和明确的最终结果。**
